## Scope and frozen target

The P4.2 traceability table required a frozen record schema, but the real fixture

adds the missing closed 0.1 schema, a canonical **pending** record, an offline

Review target remains source commit
`0d1ed98d3aaa84bfaa83aed44c12761d8b592bfd`, with frozen evidence commit

and immutable; acceptance belongs to the separate review record.

## Admission and review semantics

- Only the canonical record can return `gate_ready`. Even a syntactically
  complete approved draft cannot authorize acceptance.
- All four roles require an actual independent review, reviewer public ID,
  independence basis and review date. Maintainer acceptance is separate and
  cannot precede the reviews. Dates cannot precede evidence freeze or be future.
- Open or accepted critical/high findings block approval. IDs must be unique,
  resolved findings need resolution text, and severe counts must be accurate.
- Missing/extra fields, changed bindings, unreadable/malformed/non-UTF-8 or
  oversized records, arbitrary paths and reparse-point paths fail closed.
  Record reads allocate at most 32 KiB plus a one-byte overflow probe; output
  contains fixed status/boolean fields, never reviewer text or arbitrary paths.
- `--contract-only` always reports `gateReady: false`; its exit 0 is a preflight,
  not an approval. Direct approval validation of the pending canonical record
  returns `gate_not_ready`, exit 3 (npm may wrap this as exit 1).

Reviewer assertions are governance data, not signatures. No validator can prove
that a person performed an independent review. Authenticity depends on actual
human review and trusted repository change control. This is offline tooling for
a trusted checkout, not a concurrent hostile-filesystem security service.
Bounded review text is not automatically redacted; reviewers must exclude
credentials and user data. All test approvals use synthetic identities and are
never copied to the canonical record.
