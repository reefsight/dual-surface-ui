# P4.3 S3 semantic action design

Status: Proposed documentation only. No implementation or native execution
is authorized by this brief. Date: 2026-10-04, Asia/Bangkok.

Owner: coordinating agent `/root` under the existing
[maintainer delegation](../reviews/phase4-agent-review-authorization-2026-10-03.md).
Independent accessibility, security and protocol/package reviewers must review
the actual final design; a separate later entry decision remains required.

This brief prepares the action slice of the
[accepted implementation sequence](P4.3-implementation-slices.md). It specifies
how an owned synthetic Windows fixture could execute semantic requests without
turning descriptive accessibility data into authority. The
[S2 design](P4.3-read-only-capture-projection.md) permits preparing S3 from
descriptive action comparisons, but its read-only snapshots still have
`actions: []`. Nothing here grants an action capability or accepts S2 runtime.

## Entry conditions and unchanged scope

Before any S3 source implementation, require all original S2 real capture
criteria, the planned positive first/repeat pair, genuine independent original
artifact reviews and a separate accepted S2 runtime decision. Require an
independently approved version of this design and a separately dated S3 entry
bound to that exact version. Green pure tests or the retained
[D2 negative checkpoint](../evidence/p4.3-native-suite-d2-development-2026-10-04.md)
cannot satisfy those prerequisites. Its host-context question and controlled
continuation requirement remain unresolved; this proposal does not authorize
another attempt or explain the refused guard's underlying cause.

The later implementation remains a private owned-fixture reference, using the
already accepted fixture, goldens and protocol 0.1. No user application,
arbitrary executable/PID/HWND/selector, process/desktop traversal, model call,
secret/environment read, installer, elevation, desktop switch, security-setting
change, input injection, daemon, remote transport or production support enters
this slice. Rust qualification, authenticated local IPC, macOS and release
remain separately gated. Do not change any existing S1/S2/C0/D1/D2 source,
review, freeze, original evidence or fixture/golden binding by implication.

The proposed implementation directory is a new internal action harness beside
the managed reference, not `src/` or a public package export. Any reuse of S2
code must be explicitly source-bound in the later candidate. Historical DLLs
and their review pins are not automatically approvals of a rebuilt binary.

## Existing contracts and proposed action profiles

The existing [core types](../../src/types.ts),
[constant failure messages](../../src/errors.ts),
[native execution schema](../../src/native-protocol/execution-schema.ts) and
[native session verifier](../../src/native-protocol/session.ts) are oracles,
not files to extend for this slice. Strict protocol parsing and current
session/capability/revision admission precede any native operation.
The independently identified historical-replay revision defect requires its
own [pure protocol remediation](native-protocol-replay-revision-remediation.md),
review and fresh gates before these contracts can be relied on for S3 entry.
That separate correction cannot serve as native action implementation or proof.
`action-request` has only its existing correlation, opaque references, revision,
action, optional JSON input and optional idempotency key. Caller risk, principal,
policy, confirmation, effect, native identity and executable path are forbidden.

An executable catalog, if later authorized, is minted from the current trusted
binding plus a package-owned closed profile table. Descriptive P4.2/S2 action
metadata does not authorize it. Preserve the original golden-comparison view
separately and explain any profile/input differences in independent review;
do not edit a golden or claim exact executable-catalog equality by dropping
descriptors. Existing core action names are extensible strings; adding a
reviewed profile must not add a schema field or change web/DOM behavior.

All profiles below require explicit current nonsensitive, enabled and onscreen
target observations, fresh owned-window/current-tree proof, the stated pattern,
host-owned write policy, schema admission and a bound expected effect. Unknown
safety is not false. Unknown Value/Range read-only state cannot authorize a
write; structural nodes remain non-actionable. No first-ID/name match, cached
pattern peer or provider default supplies eligibility.

| Pattern family | Proposed profile and input | Additional current eligibility | Sole allowed mutation and required postcondition |
| --- | --- | --- | --- |
| Invoke | `click`; input absent | Reviewed control type and closed host-owned effect for this exact current button | One `Invoke`; a fresh capture and authoritative fixture state prove the declared change, such as `count` increasing exactly once |
| Value | `set_value`; JSON string, maximum 64 UTF-16 code units, well-formed Unicode | Value pattern explicitly writable; reviewed Edit target; no sensitive/unknown classification | One `SetValue`; fresh observed value and fixture `value` equal the submitted nonsensitive string, with no unrelated effect |
| Toggle | `toggle`; input absent | Reviewed two-state CheckBox; current state explicitly On or Off | One `Toggle`; fresh checked state and fixture `toggle` are the opposite of the admitted before-state; never loop to a desired bit or accept Indeterminate |
| Selection | No independent mutation profile or caller-selected container | Current reviewed single-selection List/ComboBox/Tab container; current selected peers independently qualified and bounded | Read current selection only; verify the SelectionItem postcondition and current container relation; never treat pattern presence as a select operation |
| SelectionItem | `select`; input absent when the request targets the opaque current option/radio/tab reference | Reviewed item type; exact same-generation membership under the applicable List/Tab/Combo container or the closed fixture-radio profile below; no arbitrary item ID supplied as input | One `Select`; item IsSelected, the applicable independently proved selected relation and fixture selection/combo/radio/tab state agree; no duplicate-label first match |
| ExpandCollapse | `expand` or `collapse`; input absent; expose only the action appropriate to the current state | Reviewed Group Expander only; state explicitly Collapsed or Expanded, not LeafNode/unknown/partial | One corresponding call; desired Group state, current descendants and fixture `expanded` agree; Combo expansion is not an executable S3 profile |
| RangeValue | `set_range`; finite JSON number within 0..10 | Slider explicitly writable; explicit finite current value/minimum/maximum with ordered bounds; requested number satisfies both fixed profile and observed bounds | One `SetValue`; fresh range and fixture `range` equal the exact requested value; no inferred step/grid, clamping or accepted rounding mismatch |

These are proposed fixture profiles, not claims that every UIA provider has
these behaviors. Radio/List/Tab item selection is target-based; a future
container-string convenience action would need another explicit profile and
input schema. The current fixture manifest gives ComboBox no executable
action. ComboBox open/close remains separately frozen trusted synthetic setup,
not an executable S3 action. The fixture's `expanded` field belongs to the Group
Expander and cannot prove ComboBox.IsDropDownOpen; `combo` records selection only.
Fresh UIA expansion and admitted popup membership/retirement can verify capture
eligibility, but do not become dual fixture proof of a Combo expansion effect.
A future executable Combo expansion profile would require separate design and
evidence review; selection must not secretly expand it inside `select`.

For List/Tab/Combo selection, require fresh explicit SelectionContainer equality
to the qualified current container, reciprocal Selection/SelectionItem state,
and bounded current selected-peer membership. Radio is a different closed
fixture profile: freshly qualify exactly the trusted radio-a/radio-b definitions
under the admitted current main ancestry and same surface/window generation,
with neither missing, duplicated, ambiguous, unknown nor replaced. Both peers
must have explicit reciprocal selected bits, exactly one selected before and
after, agreeing with fixture `radio`; the selected target must be the requested
current radio. The host-owned two-member profile establishes the fixture group,
not provider text, GroupName, a graph parent or a fabricated Window Selection
pattern. Never read/infer a required radio SelectionContainer or accept a null
default as proof. These checks need their own later pure/native evidence.

Current-state-only Group descriptors are the chosen catalog rule: Collapsed
exposes `expand`, Expanded exposes `collapse`. A fresh already-satisfied opposite
intent is `action_not_found`; a changed observed revision is rejected as stale.
Neither becomes a successful zero-call no-op. Exact admissible recorded replay
is the separate zero-new-call path. Do not force a revision change by repeating
a provider operation. Toggle means exactly one transition, not setting a Boolean
or a safe automatic retry.

The Range profile accepts finite numbers, including fractions, within 0..10 and
the explicit freshly observed ordered minimum/maximum. It requires current
value and IsReadOnly=false, not SmallChange/LargeChange or a legal-value lattice.
TickFrequency, snap settings, provider defaults and increment amounts cannot
define a step restriction. Exact requested/UIA/fixture equality is mandatory;
any rounded or mismatching result follows possible-effect verification failure,
never no-effect rejection. This is a host profile, not a provider guarantee.
No AddToSelection/RemoveFromSelection, multi-select, text injection, fuzzy
matching, numeric clamping or culture-dependent string conversion is included.

Microsoft documents [Invoke](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.invokepattern.invoke?view=windowsdesktop-10.0)
as activating a control, [Toggle](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.togglepattern.toggle?view=windowsdesktop-10.0)
as cycling states, and [SelectionItem.Select](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.selectionitempattern.select?view=windowsdesktop-10.0)
as selecting one item after deselecting existing selection. The
[Selection family](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.selectionpattern?view=windowsdesktop-10.0)
supports selection observation. [Value](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.valuepattern.setvalue?view=windowsdesktop-10.0)
and [RangeValue](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.rangevaluepattern.setvalue?view=windowsdesktop-10.0)
set values; a range provider may round. [Expand](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.expandcollapsepattern.expand?view=windowsdesktop-10.0)
can block. These API facts motivate the proposed closed policy and verification
rules; they do not prove native conformance, correct provider behavior or a
particular outcome on this host. Documentation examples using first-match or
input simulation are not permitted implementations here.

## Host authority and confirmation

Risk, principal, action definition, preconditions, effects and confirmation come
only from trusted package-owned state. Every native mutation has at least write
risk; unknown profiles fail closed. Synthetic increment, replacement, reset
and confirmation operations receive conservative consequential policy in the
private executor. The original descriptive golden risk remains comparison
metadata, not a permission or proof that an effect is harmless.

Default write policy is deny, consistent with the existing
[policy contract](../../src/policy.ts). An allow decision never bypasses a
profile marked as requiring confirmation. Absent, false, expired or mismatched
confirmation prevents mutation. A confirmation receipt is private, single-use,
bounded and bound to the trusted principal/session generation, surface/window/
element/container generation, descriptor/effect digest, exact copied input,
current revision and deadline. A fixture modal or caller `confirmed:true` is
not a trusted policy receipt. The modal-confirm button itself needs independent
eligibility and policy; it cannot mint its own consent.

This harness has only a fixed synthetic trusted principal and package-owned
policy/confirmation test callbacks. That is not authenticated peer identity,
human consent or a product authentication implementation; P4.5 still owns those
claims. Provider text cannot select or modify callbacks, risk or effects. No
callback receives an AutomationElement, COM/pattern peer, native ID or arbitrary
operation delegate. Callback outputs are closed, bounded decisions.

## Ordered action boundary

1. Strictly admit and copy bounded bytes/input through the existing protocol
   grammar, session state and capability rules. Resolve the opaque surface,
   element and profile only inside the host. Do not read a native pattern for
   a malformed or unadmitted request.
   After pure admission, the exact owned supervisor reserves the bounded sole
   attempt slot before launching or dispatching any mutation-capable worker;
   refuse capacity before dispatch. Steps 2/3 run under that reservation, not a
   worker-private slot, and do not move native proof into the supervisor.
2. Serialize the owned surface, capture a fresh bounded before-state and prove
   current user/session/desktop, process birth, window liveness/generation,
   current target ancestry, reviewed control/pattern qualification, sensitivity,
   revision and expected-effect preconditions. Resolve single-selection peers
   only within the applicable proven current container or separately closed
   radio profile and shared S2 graph limits.
3. Obtain trusted policy and any required confirmation. After every asynchronous
   policy/confirmation/precondition wait, discard temporary provider peers and
   repeat the complete current binding/safety/revision/effect proof. A principal,
   policy, generation, descriptor, input or revision change invalidates the
   earlier receipt; do not silently refresh the request's observed revision.
4. Verify that the same supervisor-owned attempt/replay reservation is still
   current, without allocating a fresh slot or replacing its binding; consume
   confirmation once. Immediately
   before the sole pattern call, recheck all authority plus cancellation and
   deadline in the same serialized operation. There is no await or caller
   callback between that final fence and the call. Scope one temporary current
   peer to this invocation; never use a retained peer from a prior capture.
5. Mark the private attempt as mutation-may-have-started before invoking the
   provider. A thrown/blocked/timed-out call is not proof of no effect. Never
   invoke again to determine whether the first call succeeded.
6. Capture fresh state, check current relationships and generation, and compare
   the separately admitted authoritative fixture before/after state against the
   exact closed expected effect and unrelated-field exclusions. A provider
   return, UI event, task completion or submitted value alone proves no success.
7. Admit any response with the existing core and native validators and apply
   the independently corrected session correlation/revision rules. Release
   scoped managed peer references (no arbitrary COM-release operation);
   invalidate uncertain references and retain the bounded private outcome.

These sequential fences are not atomic protection against a hostile provider
or every ABA race. A detected replacement/race invalidates the operation; an
unresolved relation/effect prevents success. Real adversarial OS/provider scope
and resource limitations must remain explicit rather than being inferred from
the controlled fixture.

## Outcomes without new protocol fields

The private attempt state distinguishes no mutating call, a call that may have
started, and an independently verified effect. That state is development proof,
not a new public `uncertain` status, error or retry permission.

| Observed boundary | Existing result boundary | Required proof or handling |
| --- | --- | --- |
| Invalid action/input, denied policy, missing confirmation or failed current precondition before the mutating call | Core failed outcome using the applicable constant `action_not_found`, `invalid_input`, `authorization_required`, `confirmation_required` or `precondition_failed` message | Zero mutating-pattern calls; authoritative before/after fixture effect fields unchanged; no provider-text interpolation |
| Unknown/closed surface, missing session permission, stale protocol revision, protocol replay conflict or resource admission failure | Existing `request-error` code such as `surface_unavailable`, `permission_denied`, `stale_revision`, `request_conflict` or `resource_limit` | Preserve the protocol/core boundary; do not invent a native core failure code or reveal a catalog before admission |
| Effect established by both fresh UIA and fixture state, with correlation/generation intact | Existing core succeeded outcome and admitted `action-response` | Correct previous/current host revisions, action/target and targetPresent; bounded node required when true and forbidden when false, optional bounded output; fixture revision is not the live host revision |
| Call may have started but effect cannot be established, or provider throws after possible mutation | Core `verification_failed` if an authoritative current surface/revision is still available | Fixed message; retain private uncertainty, suppress action capability until refresh; no automatic retry or false cancelled/no-effect claim |
| Surface/window/session lost, or authoritative revision cannot safely be returned after possible mutation | Existing `surface_unavailable`/`resync_required` at the protocol boundary, consistent with the session verifier | Never fabricate a revision or move the result onto a replacement surface; retain private possible-effect evidence and invalidate old bindings |

Only a fresh independent postcondition may establish success after a provider
fault. If the original request's generation/correlation cannot be preserved,
even apparently matching fixture state cannot revive its authority. A changed
host revision concurrent with response follows the existing third-revision
resync rule. Failure is not a promise that an effect did not occur.

Combo selection may retire a popup target. Same-surface/generation success with
`targetPresent:false` needs newly proved selected relationships and the exact
fixture selection effect, without re-calling the retired target or transferring
its authority to a fresh reference. Otherwise retain uncertainty, not success.

## Replay and lifecycle minimum for S3

Consequential profiles are keyed. The private ledger binds the accepted key to
trusted principal/session generation, surface/element/container generation,
descriptor/effect digest, exact admitted request/input and original revision.
Reserve before dispatch/mutation and retain completed and uncertain outcomes.
Exact historical disclosure requires freshly proved trusted identity, current
permission/policy and disclosure eligibility, exact generation/binding and
current authoritative host revision equal to the stored terminal outcome
revision. Equality of generation alone is insufficient. Recheck after any wait
and before admission; a third revision during response cannot be rolled back.
Matching keyed retries return only the exact admissible recorded outcome with
zero new pattern calls. An old terminal revision must never overwrite newer
host or verifier state.
Changed bound content conflicts; loss of identity or uncertain authority fails
closed. A full ledger cannot evict a live tombstone to permit a duplicate.

Use the existing protocol replay/correlation transcript rules, including the
exact accepted request/response fingerprints. Do not invent a stale-revision
bypass for a new requestId carrying an old key. A key alone grants neither
execution nor historical-result disclosure. Generation reset invalidates old
references and replay authority together; it is not a way to resume an uncertain
old action. If protected replay cannot be supplied, use the following closed
decision rules; do not replace an exact cached response with a new error merely
to satisfy its fingerprint.

| Request/replay condition | Required boundary; zero new mutating calls |
| --- | --- |
| Same completed requestId/key and exact canonical request; current authority and terminal revision still admissible | Exact recorded response only; unchanged request/response fingerprints and current terminal revision |
| Same completed requestId with changed request or replay response fingerprint | Existing verifier `request_conflict`, terminal closure; do not emit or apply a response into the closed verifier |
| New requestId with old key and old request revision | Ordinary `stale_revision` admission refusal, terminal verifier closure; no completed-request revision exemption |
| New requestId with old key and current revision or other changed bound content | Host replay-ledger conflict; for an admitted pending request, existing fixed `request_conflict` at the protocol boundary; never mint a new action attempt |
| Exact completed replay but newer current revision, lost permission/policy/disclosure, uncertain outcome or generation loss | Terminally close/invalidate the old session and bindings before disclosure; a negotiated session-invalidated event only where allowed, otherwise close without inventing one; do not rewrite the cached response or invent an action outcome |
| Capacity refusal for a new otherwise admitted pending request | Existing fixed `resource_limit` before dispatch/reservation; no tombstone eviction |

A protocol-verifier rejection closes its session; its exception code is not an
admitted wire response. Only an admitted pending request may receive a matching
fixed `request-error`. Later resynchronization requires a separately fresh
session/admission, never automatic continuation of the old key or uncertainty.

The exact owned supervisor, not the worker's volatile ledger, owns the bounded
attempt slot before dispatch. Until it admits a complete terminal response,
that slot is conservatively possible-effect even if the worker reports nothing.
Hard termination, no output, malformed output or loss of the worker closes the
original session/generation and retires all its bindings. Retain a bounded
redacted tombstone/negative evidence outside that worker; no raw input, provider
text or native ID is needed. Expiry retires authority, not permission to retry.
A missing ledger/file, reconnect or replacement worker cannot resume the old
request/key. Capacity is checked before dispatch and live uncertainty is never
evicted. Late return cannot publish success into the closed session. This is
local supervised single-attempt retention, not durable recovery, authenticated
IPC or cross-process business deduplication. Supervisor loss permits no automated
resume; any later manual fresh command needs separate authority and cannot be
claimed a safe retry of the uncertain action. Full S4 recovery remains separate.

Cancellation observed before the final mutation fence prevents the call. After
a call may have started, cancellation cannot report false no-effect success;
the authoritative final outcome or refresh boundary wins. S3 proves these
minimum serialized safety cases. S4 still must separately implement/review and
prove full cancellation scheduling, concurrent requests/events, local event
observation, loss/reordering, provider disconnect, replay/reconnect and soak
behavior. S3 does not advertise cancellation/events/deltas without that evidence.

## Proposed bounded resource profile

These limits are proposed for review, not accepted measured budgets. Do not
widen the existing S2 limits or worker deadlines to make a test pass.

| Resource | Proposed S3 bound |
| --- | --- |
| Current graph, auxiliary relations, depth, children, copied text and opaque bindings | Existing shared S2 limits: 256 nodes, depth 16, 64 children, 131072 text characters, 256 bindings |
| Patterns and executable descriptors | Seven families; at most one appropriate executable descriptor per node and 64 per surface; descriptive comparison stays separate |
| One request frame / encoded outcome / snapshot | 1048576 / 262144 / 262144 bytes; strict parsing and existing smaller applicable limits before allocation |
| Action input | No payload for click/toggle/select/expand/collapse; Value string 64 code units; Range finite number 0..10; no nested operation arguments |
| Owned surfaces / simultaneous native mutations / queued operations | One owned surface generation; one mutation; no implicit queued request or parallel provider worker |
| Replay entries / confirmation receipts | 64 entries per synthetic session generation, including the supervisor's one pending attempt slot / one current receipt; retained inputs/outcomes obey their caps; refuse capacity before reservation or mutation |
| Total admitted action proof, policy, confirmation, pattern and verification interval | One shared 10-second cooperative deadline; no reset after an await or postcapture |
| Pure / real native worker / retained stdout and stderr | Existing 30 / 240 seconds and 1024 / 256 bytes; hard supervisor bounds apply to blocking provider calls |

A cooperative deadline cannot preempt a blocked native call. Only the exact
owned supervisor may terminate its own worker at the accepted hard deadline;
possible effects remain uncertain and preserved. Do not spawn an unbounded
helper, probe another app, raise a deadline or retry a timed-out action. Fixture
recorder budgets and evidence CreateNew/identity rules remain unchanged.
Invoke may block too: the fixture modal handler calls ShowDialog. No helper or
second mutation may be launched to unblock a pattern call or manufacture a
positive modal result. A blocked/hard-killed attempt remains uncertainty under
the supervisor rule, not proof that this provider blocks or made no effect.

## Required verification before later acceptance

Pure tests must use copied synthetic observations and never substitute for UIA
action evidence. At minimum cover all profile/input edges; explicit unknown
safety/read-only/range/toggle states; absent/wrong patterns; hidden/disabled/
sensitive and ambiguous targets; container swap; stale references; malformed
decisions; deny/default policy; confirmation binding/expiry/reuse; principal or
revision changes during every wait; budget exhaustion; replay content changes,
capacity and uncertain-outcome retention; before/after-call cancellation;
provider fault before/after possible effect; response admission and the
third-revision race. Explicitly include revision advance before exact replay,
permission/policy revocation before historical disclosure, new-requestId stale
key versus changed-bound-content conflict, and hard-kill/no-output/malformed-
terminal/late-return/recovery vectors. Call-count spies distinguish zero from
exactly one and prove no automatic continuation after uncertainty.

Later real native evidence must separately prove:

- Invoke, Value, Toggle, RangeValue and ExpandCollapse effects through the
  executor, not the S2 trusted setup driver; Selection and SelectionItem together
  across List, Tab and ComboBox current container/selected-peer proofs. Radio
  instead proves the separately closed two-member SelectionItem profile and
  both explicit selected bits against fixture radio state.
- ComboBox popup open/close is trusted setup only. Prove fresh admitted popup
  wrapper capture, newly captured opaque item references, and executor selection
  without an implicit expand/collapse. Retired target handling must remain
  truthful; no executable Combo expansion or dual popup-state oracle is claimed.
- Disabled, read-only, sensitive, hidden/offscreen, unsupported, unknown,
  invalid range/input, policy/confirmation and stale generation refusals with
  zero mutating calls and unchanged authoritative effect fields.
- Still-callable detached controls and readable destroyed-window metadata do
  not authorize a call; same-ID/type/container duplicates and container swaps
  fail closed rather than choosing a seemingly safe candidate.
- Actual replacement/reset/restart and modal ownership invalidate the affected
  references; a fixture confirmation window is never an authorization source.
- Bound keyed repetition causes one consequential effect, conflicting content
  causes none, and unknown post-mutation outcomes never produce a second call.
- Genuine first/repeat artifacts, case-specific fixture state, raw copied
  observations, schema-valid public outcomes, no secret/native-ID leakage and
  zero unapproved operations under a frozen fixed case order and fail-first stop.

Freeze the final case IDs/counts, setup operations, expected before/after
effects, budgets, source manifest, source/fixture/worker binaries, original-byte
artifact grammar, independent verifier, reviewer roles and execution entry
before observing native results. Do not reuse the D2 freeze as S3 authority.
Keep all 22 original S2 golden scenarios and 32 captures as accepted prerequisites;
the S3 action matrix is additional evidence, not a renaming of those captures.

Actual independent source and original-artifact reviews must cover
accessibility/current membership, authorization/confirmation/redaction,
protocol/outcomes/replay/races, and package/evidence integrity. Every finding
and failed run remains visible. Only a separate evidence-bound S3 runtime
decision may accept implemented behavior; it cannot close S4, real OS permission
negatives, P4.3, P4.4 or Phase4 automatically.

## Review and stop conditions

This proposed document may be reviewed and committed independently while S2
is waiting for human host context. Review disposition must say design-only and
must not be encoded as S3 entry/runtime acceptance or a new native execution
permission. Preserve the approved S2/D2 artifacts and stop native execution
until its existing human-context and separate continuation requirements are met.

confirmation authority or existing outcome/session semantics cannot satisfy the
brief, retain the finding and refine the design before implementation. Do not
add a protocol status, copy an oracle value into an observation, lower thresholds,
change the fixture, manufacture a diagnostic change or retry until green.
