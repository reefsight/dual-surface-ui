# P1.4 — Deterministic Policy and Confirmation Boundary

Status: Implemented and verified; awaiting maintainer review

Phase: 1 — Core contract and DOM reference

Required approver: Repository maintainer

## Problem and user outcome

The runtime currently accepts a boolean authorization callback. It cannot
represent a deterministic deny reason, require a trusted confirmation step, or
bind policy evaluation to principal and origin context. Actions marked
`requiresConfirmation` can therefore be allowed by the legacy callback alone.
P1.4 introduces an explicit policy decision contract and prevents policy waits
from creating a stale-state execution window.

## Scope

- public `allow`, `deny`, and `require_confirmation` policy decisions;
- policy context bound to action, target, risk, principal, origin, surface, and
  observed revision;
- trusted host confirmation callback;
- mandatory confirmation for actions declaring `requiresConfirmation`;
- deny-by-default behavior for writes when no policy or legacy authorizer is
  configured;
- a second revision check after asynchronous policy/confirmation and before
  handler execution;
- stable confirmation and invalid-policy error codes;
- compatibility fallback for the existing boolean `authorize` callback.

## Non-goals and prohibited changes

- no role/permission DSL, origin allowlist, policy persistence, or remote policy
  service;
- no precondition/effect verification, idempotency cache, or audit transport;
- no confirmation UI implementation inside the package;
- no raw-input logging or confirmation-text generation;
- no WebMCP, MCP, framework, Playwright, extension, or native code;
- no package publication or version bump.

## Trust boundaries and data classification

Model requests and action input are untrusted. The application-supplied policy
and confirmation callbacks are trusted host boundaries. Page text cannot make a
policy decision. Principal identifiers and roles are internal metadata and are
passed only to trusted callbacks; they are not added to snapshots or results.
Credential and secret values remain excluded from snapshots, errors, fixtures,
and logs.

## Compatibility

Existing `authorize` callbacks remain supported when no `policy` callback is
configured. The explicit policy callback takes precedence. Existing actions
with `requiresConfirmation: true` now require the trusted `confirm` callback;
this is an intentional security correction in the pre-release API.

## Acceptance criteria

| ID | Requirement |
|---|---|
| AC-01 | Policy receives the current principal, origin, action, target, risk, surface, and revision. |
| AC-02 | `allow` permits execution after the final revision check. |
| AC-03 | `deny` blocks execution and the handler is not called. |
| AC-04 | `require_confirmation` blocks unless the trusted confirmation callback returns true. |
| AC-05 | Action metadata `requiresConfirmation: true` forces confirmation even when policy returns `allow`. |
| AC-06 | Missing or rejected confirmation exposes stable `confirmation_required` failure. |
| AC-07 | Invalid policy output fails closed with stable `invalid_policy_decision` failure. |
| AC-08 | A semantic mutation while awaiting policy causes stale-revision rejection before execution. |
| AC-09 | Legacy boolean authorization remains functional for actions that do not require confirmation. |
| AC-10 | Typecheck, build, tests, audit, ESM import, and package dry-run pass. |

## Design

- `AgentPolicyDecision` is a discriminated union with `outcome` equal to
  `allow`, `deny`, or `require_confirmation`.
- `AgentPolicyRequest` extends the existing authorization request with origin
  and optional principal metadata.
- `policy` is evaluated for every action when configured. Without it, read
  actions are allowed and non-read actions use the legacy authorizer or deny.
- `confirm` is called only after a non-deny policy decision and only when the
  decision or action metadata requires confirmation.
- The runtime snapshots again immediately before execution and rejects any
  revision drift.

## Rollback / disable strategy

Revert the single P1.4 commit. Applications can omit `policy`, `confirm`, and
`getPrincipal` to retain the P1.3 legacy authorization path, except that actions
explicitly marked as requiring confirmation must remove that metadata only as a
temporary pre-release rollback.
