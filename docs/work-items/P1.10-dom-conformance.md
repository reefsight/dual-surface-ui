# P1.10 — DOM Visibility and Native Form Conformance

Status: Implemented and verified; awaiting maintainer review

Phase: 1 — Core contract and DOM reference

Required approver: Repository maintainer

## Problem and user outcome

The semantic surface can currently expose controls hidden by an ancestor or CSS
and advertises actions for disabled controls. Selects use a generic action and
forms cannot be submitted natively. P1.10 aligns discovery and execution with
the current human-visible DOM state and completes the Phase 1 native action set.

## Scope

- explicit ancestor-aware visibility rules and hidden-input exclusion;
- effective native, fieldset, option, inert, and ARIA-disabled handling;
- no actions on disabled controls and no execution of hidden guessed IDs;
- native `select` action with enabled-option input enum and exact verification;
- native form `submit` through `requestSubmit()` with transition verification;
- option state and dynamic visibility/enablement/choice revision coverage;
- reusable DOM conformance HTML fixtures, README, and deterministic tests.

## Non-goals and prohibited changes

- no Shadow DOM, iframe, canvas, visual occlusion, viewport clipping, or
  browser screenshot/layout proof;
- no async navigation observer or claim of real-browser conformance;
- no custom validity-message serialization or form business-rule duplication;
- no change to custom domain-action verification requirements;
- no WebMCP, MCP, framework, Playwright, extension, or native code;
- no package publication or version bump.

## Trust boundaries and data classification

DOM content, attributes, option values, and guessed IDs are untrusted. Hidden
subtrees and hidden inputs are excluded before serialization. Disabled state
removes authority rather than merely advising the agent. Select values are
limited to visible control options and validation errors never echo the raw
requested value. Native form submission remains behind existing policy and
verification boundaries.

## Compatibility

Visible enabled text controls, toggles, buttons, links, and custom actions keep
their behavior. Select callers migrate from `set_value` to `select`. Hidden or
disabled operations that were previously discoverable are intentionally
removed as a security correction. No serialized field or schema version
changes.

## Acceptance criteria

| ID | Requirement |
|---|---|
| AC-01 | Elements hidden by self/ancestor HTML, ARIA, inert, supported CSS, closed dialog/details, or hidden input type are absent from snapshots. |
| AC-02 | A guessed ID cannot execute an action on an invisible element. |
| AC-03 | Disabled native, fieldset-descendant, option, and ARIA controls expose `state.disabled: true` and no actions. |
| AC-04 | A guessed action on a disabled control is rejected before policy or mutation. |
| AC-05 | Enabled non-sensitive selects expose `select` with a deduplicated enum of visible, enabled option values; sensitive selects omit values and no eligible choices means no action. |
| AC-06 | Valid select dispatches input/change, verifies exact state, and returns the new revision; invalid/disabled choices fail before policy. |
| AC-07 | Forms expose `submit`, call `requestSubmit()`, and succeed only after an observable semantic transition. |
| AC-08 | Invalid native action/control combinations fail without mutation. |
| AC-09 | Dynamic hide/show, disable/enable, option, and selection changes advance revision and update the action catalog. |
| AC-10 | Password and sensitive values remain absent from snapshots/results/errors. |
| AC-11 | Existing policy, stale-state, verification, audit, and result behavior remains compatible. |
| AC-12 | Typecheck, build, tests, audit, ESM import, and package dry-run pass. |

## Design

ADR 0004 defines the public behavior. Visibility and effective-disabled helpers
are shared by candidate discovery, state compilation, action inference, and ID
resolution so the catalog and execution boundary cannot drift. Select option
constraints are generated from current enabled options and therefore participate
in revision hashing. Form submission uses native browser APIs and the existing
post-action snapshot verifier.

## Rollback / disable strategy

Revert the single P1.10 commit. No persisted data or migration exists. A form
whose successful submission has no semantic DOM transition should use a custom
domain action with declared effects rather than weakening native verification.
