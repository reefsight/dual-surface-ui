# P1.7 — Idempotency Keys and Replay Protection

Status: Implemented and verified; awaiting maintainer review

Phase: 1 — Core contract and DOM reference

Required approver: Repository maintainer

## Problem and user outcome

Actions advertise an idempotency policy, but requests cannot carry a key and a
lost response or concurrent retry can execute the same consequential operation
more than once. P1.7 adds surface-local replay protection that deduplicates
successful keyed actions without storing raw action input.

## Scope

- optional `idempotencyKey` in the action-request contract and schema;
- explicit runtime semantics for `none`, `keyed`, and `safe-retry`;
- mandatory URL-safe keys for actions declared `keyed`;
- SHA-256 request fingerprint bound to surface, revision, target, action,
  principal, origin, and canonical JSON input;
- deduplication of sequential and concurrent identical keyed requests;
- immutable cloned replay results without re-running policy or execution;
- conflict rejection when a key is reused with different bound context;
- failed executions are removed from the cache and may be retried;
- bounded per-surface successful-result cache with settled-entry eviction;
- stable idempotency error codes and conformance fixtures.

## Non-goals and prohibited changes

- no distributed or persistent idempotency store;
- no cross-tab, cross-process, server, or restart deduplication guarantee;
- no automatic compensation for partially completed failed actions;
- no logging or persistence of raw action input or fingerprint source text;
- no WebMCP, MCP, framework, Playwright, extension, or native code;
- no package publication or version bump.

## Trust boundaries and data classification

The idempotency key and action input are untrusted. Keys are constrained to
URL-safe opaque values and are scoped to one surface, target, and action. Input
must be canonical JSON for keyed actions. The cache stores only a SHA-256
fingerprint and a detached successful result; it never stores canonical input,
credentials, or a raw principal payload. Current principal and origin are
re-evaluated before a replay is accepted.

## Compatibility

Requests without a key retain existing behavior for actions whose policy is
missing/`none` or `safe-retry`. `keyed` actions now require a key. Supplying a
key to a non-keyed action is rejected to prevent callers from assuming replay
protection that is not active.

## Acceptance criteria

| ID | Requirement |
|---|---|
| AC-01 | The request contract accepts an optional URL-safe idempotency key of 1–128 characters. |
| AC-02 | A `keyed` action rejects missing or malformed keys before policy/execution. |
| AC-03 | A non-keyed action rejects a supplied key rather than implying protection. |
| AC-04 | An identical successful retry returns the original result without re-running policy, confirmation, handler, or verification. |
| AC-05 | Concurrent identical requests share one execution and receive equivalent detached results. |
| AC-06 | Reuse of a scoped key with different revision, input, origin, or principal fails with `idempotency_conflict`. |
| AC-07 | A failed execution is not cached and the same request may retry. |
| AC-08 | Replay succeeds after the original action changes revision or removes its target. |
| AC-09 | `safe-retry` actions execute normally on each request without a key. |
| AC-10 | Cache size is bounded and evicts settled entries only. |
| AC-11 | Fingerprints do not expose raw input and errors do not echo keys, input, or principal data. |
| AC-12 | Typecheck, build, tests, audit, ESM import, schema sync, and package dry-run pass. |

## Design

- `idempotency: "keyed"` activates deduplication; the default is `none`.
- A replay lookup occurs before stale-revision and element lookup so a lost
  response can be recovered after the successful action changed the surface.
- The runtime resolves the current principal and hashes canonical request
  context using Web Crypto SHA-256. Only the digest is retained.
- The first in-flight promise is installed atomically in the surface cache;
  matching concurrent calls await that promise.
- Successful results are JSON-cloned when stored and whenever returned so a
  caller cannot mutate the replay record.
- Rejections remove their cache entry. When the configured bound is exceeded,
  the oldest settled entries are evicted; active executions remain protected.

## Rollback / disable strategy

Revert the single P1.7 commit. No persisted data or migration exists. Existing
actions can remain `none` or `safe-retry` until their application integration
is ready to supply stable keys.
