# P2.5 — Vue Lifecycle Adapter

Status: Implemented and verified on 2026-09-18

Phase: 2 — Web and framework adapters

Required approver: Repository maintainer

## Goal and proposed outcome

Vue applications can provide an application-owned `AgentSurface` through a
Vue plugin and bind an explicit `AgentElementDefinition` to a native template
ref through one Composition API helper. The adapter owns Vue lifecycle only.
It does not create policy, infer agent metadata, execute an action, subscribe
to snapshots, or export WebMCP tools.

The additive `dual-surface-ui/vue` subpath currently exports:

- `createAgentSurfacePlugin(surface)`, which provides the exact surface at the
  application boundary;
- `useAgentSurface()`, which returns that surface during component setup and
  fails deterministically when the plugin is absent;
- `useAgentElement(definition)`, which returns a shallow native-element
  template ref and accepts a value, ref, or getter for the definition.

The adapter is verified by focused client lifecycle, real Node SSR, real
SSR-to-client hydration, packed compatibility consumers, and the full package
gate recorded below.

## Vue compatibility basis

Vue 2 reached end of life on 2023-12-31 and is outside this adapter's scope.
The initial peer range is Vue `>=3.3.0 <3.6.0`: Vue 3.3 introduced the
`MaybeRefOrGetter` and `toValue()` APIs used by the public signature, while the
upper bound avoids claiming compatibility with an unverified future minor.
The planned compatibility checks cover Vue 3.3.13 and the current development
baseline, Vue 3.5.43.

## Lifecycle design

`useAgentElement()` must be called synchronously during component setup. It
returns a `ShallowRef<T | null>` for use as a native element's template ref.
Registration starts only after Vue mounts or activates the component. A
post-flush watcher observes the current element and resolved definition, calls
the exact disposer returned by core before a replacement becomes live, and
stops on deactivation or before unmount.

Supporting both mount/unmount and activation/deactivation is required because
`KeepAlive` removes a cached component tree from the document without
unmounting it. A deactivated registration must not retain an agent ID or block
another visible component. The paired hooks may both run during the initial or
final lifecycle, so cleanup and start behavior must remain idempotent.

The helper accepts only a native `Element`. A component-instance ref, missing
provider, missing definition, duplicate ID, or core registration error must
fail closed. Definition updates are identity-based; callers should replace a
definition value rather than mutating nested properties in place.

## Trust and security boundaries

The surface and definitions are explicit trusted application inputs. The
adapter must not derive descriptions, action names, schemas, risks, labels,
ARIA text, values, errors, URLs, or credentials from the Vue tree or DOM. It
must not log definitions or application state.

Core remains the sole authority for schema validation, revision checks,
authorization, confirmation, idempotency, replay protection, preconditions,
handler execution, effect verification, structured failures, and redacted
audit events. Vue event handlers and application services remain the same
human-visible path used without the adapter. Adapter errors and core denials
must not be swallowed or converted to successful results.

## SSR and hydration constraints

Server rendering must emit only the human markup. It must not call
`surface.register()`, touch a global `document` or `Element`, or emit
`data-agent-id`. Vue does not run mounted or unmounted hooks during SSR, so all
DOM work must stay inside client lifecycle callbacks.

`useAgentElement()` captures an optional surface during setup and requires it
only when the component mounts in a browser. A server application therefore
does not install the plugin or construct a DOM-backed surface. A missing plugin
still fails closed with a fixed error during client mount.

Hydration requires a real server-render-to-client-hydration check. The client
must hydrate unchanged server markup without mismatch warnings, then create
exactly one registration after mount and remove it on unmount. Server-render
tests, ordinary client mounts, or production builds alone do not justify a
hydration compatibility claim.

## Package boundary

Vue is an optional peer rather than a root runtime dependency. Root, WebMCP,
React, and Angular consumers must not resolve or execute the Vue entry point.
The `dual-surface-ui/vue` subpath emits ESM and declarations under `dist/vue`;
it must retain `vue` as an external import rather than bundle a second Vue
runtime.

The peer range and package layout are claims that require clean packed-tarball
consumer builds. Source-path imports from this repository do not prove the
published secondary entry point works.

## Explicit non-goals

- No Vue-owned policy, confirmation, execution, or verification behavior.
- No automatic DOM, component, slot, ARIA, or credential inference.
- No automatic WebMCP export or snapshot subscription.
- No global mixin, render wrapper, hidden component, or second UI tree.
- No Vue 2 or `@vue/compat` support.
- No open-ended Vue 3.6+ compatibility claim before a packed consumer passes.
- No hydration claim before a real SSR-to-hydration test passes.
- No root contract, schema, error-code, or serialization change.

## Acceptance criteria

| ID | Requirement |
|---|---|
| AC-01 | The plugin and `useAgentSurface()` expose the exact supplied surface; calls outside setup and missing providers fail deterministically. |
| AC-02 | `useAgentElement()` registers only a mounted or activated native element with the exact current explicit definition. |
| AC-03 | Existing Vue markup, bindings, and human event behavior remain unchanged. |
| AC-04 | A new definition or element disposes the previous registration before registering the replacement and leaves one live binding. |
| AC-05 | Conditional removal, unmount, and remount remove the owned marker and registration without leaks or duplicate IDs. |
| AC-06 | `KeepAlive` deactivation disposes the binding and activation recreates exactly one current binding. |
| AC-07 | Component refs, missing definitions, duplicate IDs, and core errors fail closed and are not swallowed. |
| AC-08 | Core remains the sole execution and security authority, including when a consequential action is denied. |
| AC-09 | Server rendering emits unchanged human markup without registration, marker attributes, or global DOM access. |
| AC-10 | Client hydration produces no mismatch warning, registers once after hydration, and cleans up on unmount. |
| AC-11 | Packed Vue 3.3.13 and Vue 3.5.43 consumers pass type checking and production builds through the published subpath. |
| AC-12 | A clean root consumer installed without optional peers imports core successfully and has no Vue installation. |
| AC-13 | Full deterministic tests, frozen-contract check, audit, package inspection, and diff checks remain green. |

## Threat and negative cases

| Case | Expected disposition |
|---|---|
| No plugin in a client app | Throw a fixed adapter error; do not register. |
| Composable called outside setup | Throw a fixed adapter error. |
| Template ref resolves to a component instance | Reject it; do not guess its root element. |
| Duplicate agent ID | Preserve the core failure and never replace another element's ownership. |
| Definition changes repeatedly | Dispose-before-register for each completed update; retain one live binding. |
| `v-if` removes the element | Dispose the current registration and marker. |
| `KeepAlive` deactivates the tree | Dispose while hidden; register once when activated. |
| Server render | Render only the human surface and perform no DOM side effect. |
| Hydration | Do not mutate server markup before Vue completes hydration. |
| Root package imported without Vue | Do not resolve or execute the Vue subpath. |
| Consequential action denied by core | Preserve the denial and do not invoke the handler. |

## Verification evidence

- Repository baseline: Node.js `24.16.0`, Vue and server renderer `3.5.43`,
  TypeScript `5.8.3`, and Vitest `5.0.1`.
- `npm run typecheck`, `npm run build`, and focused tests passed. The client
  suite covers exact injection, client-only registration, native events/core
  denial, definition and element replacement ordering, unmount/remount,
  `KeepAlive`, duplicate IDs, invalid component refs, and hydration.
- The separate Node-environment SSR test passed with no DOM globals and no
  provider, producing exactly `<button>Confirm</button>`.
- Fresh packed SFC consumers on Vue `3.3.13` and `3.5.43` each passed
  `vue-tsc --noEmit` and Vite `8.3.0` production builds.
- A separate root consumer installed with `--omit=peer`, imported core, and
  confirmed Vue was absent.
- `npm run test:gate` passed 19 files and 191 tests; `npm run contract:check`
  preserved 32 root exports, six declaration hashes, and five schema hashes.
- `npm audit --json` reported zero vulnerabilities. `npm pack --dry-run
  --json` contained 72 intended entries, including `dist/vue`, in a
  51,706-byte tarball (262,350 bytes unpacked). `git diff --check` passed.

## Frozen-contract constraints

P2.5 is an additive package subpath. It must not change the 32 frozen root
runtime exports, six frozen declaration hashes, five generated schema hashes,
contract version `0.1`, serialized fields, error codes, or default policy and
execution semantics. Vue declarations are outside the Phase 1 root contract
but become public API once approved and therefore require explicit review.

## Rollback

Remove the Vue secondary export and optional peer, stop emitting `dist/vue`,
and remove the plugin/composable source and tests. Existing core, WebMCP,
React, Angular, and human UI behavior require no data migration because the
adapter changes no serialized contract or persisted application state.
