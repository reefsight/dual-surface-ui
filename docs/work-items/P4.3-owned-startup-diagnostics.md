# P4.3 owned startup diagnostics — proposed development increment

Status: proposed on 2026-10-04, requiring actual independent design/source review
before a distinct-source native attempt. This is not an identity-slice decision,
timeout remediation, fixture change, action slice or new implementation language.

The [retained incomplete pair](../evidence/p4.3-identity-continuation-2026-10-04.md)
passed its first 15 decisions but timed out at repeat `launch-window` before any
fixture state/acknowledgement. The owned process was still alive in the existing
wait; neither normal-desktop probes nor an empty directory establish the cause.
Do not repeat the unchanged candidate to search for a successful pair.

## Diagnostic scope and fixed limits

- Keep the accepted fixture source/DLL, startup/observation 10 seconds, unit
  worker 30 seconds, native worker 240 seconds, assertions, case order, admission
  and first-failure stop unchanged. No retries, sleep/cooldown, input injection,
  installer, elevation, tracing service or new dependency.
- Observe only the `Process` instance created and retained by `OwnedFixture`.
  Never accept PID/HWND/path selectors, enumerate other processes/threads,
  read process memory, inspect credentials or collect provider text.
- On a terminal `launch-window` or `launch-state` failure only, best-effort
  record one bounded diagnostic in that already-owned output directory, before
  normal disposal. A diagnostic fault must not replace the original failure,
  create an identity success report, continue the cases or permit repeat.
  Trigger at the explicit respective startup `Wait` catch boundary, never from
  mutable Scenario/Stage alone; later admission failures are not startup waits.
- Fixed envelope: `schemaVersion: "0.1"`,
  `kind: "p4.3-owned-startup-diagnostic"`, fixed failure `stage`, and closed
  string categories only. Exact additional keys: `process`, `window`,
  `stateRecords`, `resetAckRecords`, `cpu`, `resident`. Process: `alive`, `exited`, `unknown`; main window:
  `present`, `absent`, `unknown`; initial state and reset acknowledgement:
  `present`, `absent`, `unknown`. No native identity or authoritative values.
- At most one fresh owned-process CPU-time and working-set read. Coarse CPU
  categories: `zero`, `under_100ms`, `under_1s`, `at_least_1s`, `unknown`.
  Coarse resident-memory categories: `under_64mib`, `under_256mib`,
  `at_least_256mib`, `unknown`. Invalid/unavailable metrics are unknown, not
  zero. No numeric counters, machine/process IDs, paths, user names, exit codes,
  provider errors, streams, stack traces or unbounded text in the diagnostic.
  CPU intervals in milliseconds are exactly zero, 0 < CPU < 100,
  100 <= CPU < 1,000, and CPU >= 1,000. Resident intervals in bytes are exactly
  0 <= bytes < 64 MiB, 64 MiB <= bytes < 256 MiB, and bytes >= 256 MiB;
  negative/unavailable metrics are unknown. These are metadata observations,
  not validated Loaded/readiness or managed/WPF execution-stage proof.
- JSON cap 1,024 bytes and depth 3; publish once with `CreateNew`, never replace
  a prior file. Fixed filename: `startup-diagnostic.json`. Diagnostic reads have
  no success eligibility role. Existing
  OS calls/record enumeration keep their known outer-worker containment limits;
  this is not a new hard per-call latency/allocation guarantee.
- Keep fixture stdout/stderr private. Do not add raw-stream logging or attempt
  to infer a cause from absence of a fixed fixture-failure category.
- Separately add fixed stages immediately before the three window-replacement
  waits: new window, former-window destruction and new-window initial state.
  These are context only, not assertions that earlier timeouts happened there.

## Verification and truthful interpretation

Unit cases cover every category boundary, negative/unavailable metric handling,
closed stage rejection, small JSON shape and no-overwrite behavior. Faults in
optional diagnostic collection/publication must preserve the original terminal
exception. Source review must verify diagnostics cannot alter timeout/assertion
decisions or invoke UIA/action/provider APIs.

After design/source review and passing units, one new-source serial first/repeat
attempt may collect actual diagnostic evidence, with every failure retained.
No heavy browser/full/native test runs concurrently. A diagnostic is not success
or a measured managed/WPF startup phase. CPU/memory categories cannot establish
lock, scheduling, IO, antivirus, thread deadlock or a host-load cause. Any actual
first/repeat success remains separately subject to the original identity review
and gate; historical startup failures are not erased or silently accepted.

Public SDK/protocol/corpora, package allowlist, P4.2 source/golden/canonical
acceptance and production-language decisions remain unchanged. No later slice
starts until identity evidence has its own actual delegated acceptance.
