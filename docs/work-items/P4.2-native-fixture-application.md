# P4.2 — Controlled Windows Fixture Application and Golden Trees

Status: Planned; documentation complete; implementation blocked until P4.1
independent review is approved

Phase: 4 — Native surfaces

Required approver: Repository maintainer; fixture architecture also requires
the technical maintainer; security cases require the security owner

## Problem and user outcome

A native adapter cannot be verified against mocks alone. The project needs one
controlled Windows desktop application whose real Microsoft UI Automation tree,
control patterns, state transitions, and failures are deterministic enough to
become reviewed evidence. Without that fixture, a future adapter could map a
handwritten fake tree correctly while failing against real provider behavior.

P4.2 creates the test subject and evidence oracle before implementing the
Windows adapter. It does not create the adapter, daemon, transport, or agent.

## Dependencies and entry gate

- P4.1 must have an approved independent protocol/security/interoperability/
  package review and a passing canonical review record.
- The language-neutral protocol 0.1 schemas and corpora must be frozen.
- Work runs on a recorded physical or virtual Windows host with UI Automation
  Core available. A mock-only environment cannot complete P4.2.
- The fixture technology decision in ADR 0016 must be accepted before source
  implementation or SDK installation.

Planning may proceed while P4.1 review is pending. Runtime implementation,
toolchain installation, and native claims may not.

## Scope

- a deterministic, single-window Windows desktop fixture application;
- stable fixture-owned control IDs and resettable scenario state;
- real UI Automation exposure through supported framework providers;
- representative Invoke, Value, Toggle, Selection, SelectionItem,
  ExpandCollapse, and RangeValue controls;
- disabled, read-only, hidden, off-screen, duplicate-label, dynamic,
  unsupported, sensitive, and replacement cases;
- fixture-owned authoritative state evidence after each semantic action;
- raw UI Automation captures plus normalized expected core snapshots;
- event, process restart, window replacement, scaling, and keyboard-layout
  evidence where relevant;
- deterministic launch/reset/teardown scripts and package-exclusion checks.

## Non-goals and prohibited changes

- no Windows adapter, protocol server, daemon, named pipe, socket, listener,
  remote access, or agent integration;
- no Rust/.NET language selection for the future bridge; fixture technology is
  a test-subject choice only;
- no mouse/keyboard injection or arbitrary process/window inspection;
- no secure-desktop automation, UAC bypass, credential entry, real password,
  production application, user document, or production identifier;
- no macOS/mobile fixture and no cross-platform support claim;
- no npm publication, release tag, installer, signing key, deployment, or
  native-support marketing claim;
- no committed compiled binary, SDK cache, trace containing user data, or
  generated machine-specific path.

## Fixture scenario matrix

| Scenario | Real control/provider behavior | Expected semantic evidence |
|---|---|---|
| Invoke | Button with stable AutomationId | `click` action and authoritative count increment |
| Value | Editable text box | bounded `set_value`; current value reflected after mutation |
| Sensitive value | Password box | sensitive classification/presence only; value never captured or writable through the protocol fixture |
| Toggle | Check box with indeterminate disabled | deterministic boolean transition; disabled state fails closed |
| Selection | List and combo box | one stable selected option; duplicate visible labels remain distinguishable by fixture ID |
| Selection item | Radio group and tabs | mutually exclusive current selection |
| Expand/collapse | Expander or tree item | collapsed descendants excluded until expanded |
| Range value | Slider with fixed min/max/step | bounded numeric mutation and authoritative value |
| Read-only/disabled | Text and action controls | state exposed; unsupported mutation rejected |
| Hidden/off-screen | Collapsed and scroll-contained controls | no hidden secret/value disclosure; visibility semantics recorded |
| Dynamic replacement | Control removed and recreated with same label | old native identity becomes stale; new fixture revision required |
| Modal confirmation | Fixture-owned modal dialog | separate window/surface and deterministic cancellation/success state |
| Unsupported custom control | Provider without an accepted pattern | safe metadata only and stable unsupported disposition |
| Injection text | Labels containing markup/prompt/Unicode controls | inert text, bounded and redacted according to the core contract |
| Process/window restart | Fixture closes and relaunches | old process/window/surface bindings invalidated |

## Deterministic fixture contract

The fixture starts from a frozen manifest and reset seed. Every control has a
fixture-owned ID independent of runtime handles. The application exposes no
network endpoint. A test run receives a host-created evidence directory and
writes bounded JSON state records there using atomic replacement. Those records
are authoritative only for the synthetic fixture and are excluded from npm.

Raw UI Automation evidence must retain control type, framework ID, automation
ID, name, enabled/off-screen/focus state, bounding rectangle classification,
supported patterns, process identity hash, window identity hash, and event
ordering needed for review. Raw runtime handles, object addresses, access
tokens, usernames, machine names, and unrestricted application text are not
persisted.

Each golden case contains:

1. fixture manifest and initial state digest;
2. recorded Windows/build/runtime/display settings;
3. bounded raw UI Automation tree capture;
4. reviewed normalized semantic snapshot;
5. requested pattern operation, if any;
6. fixture-owned before/after authoritative state;
7. expected event sequence and stable disposition;
8. screenshot only when necessary for human mapping, with synthetic content;
9. deterministic artifact digest and redaction scan result.

## Acceptance criteria

| ID | Requirement |
|---|---|
| AC-01 | P4.1 independent review is approved before fixture runtime implementation begins. |
| AC-02 | The fixture runs on a recorded Windows host and exposes a real UI Automation tree; mocks cannot satisfy completion. |
| AC-03 | Launch, reset, scenario selection, authoritative state capture, and teardown are deterministic and bounded. |
| AC-04 | Stable fixture IDs never depend on PID, HWND, pointer, tree position, localized name, or generated runtime address. |
| AC-05 | Invoke, Value, Toggle, Selection, SelectionItem, ExpandCollapse, and RangeValue behaviors have real provider evidence. |
| AC-06 | Disabled, read-only, hidden, off-screen, unsupported, duplicate-label, and dynamic replacement cases fail or map exactly as specified. |
| AC-07 | Password/sensitive controls never expose values; fixtures, logs, screenshots, state records, and errors contain no secret sentinel. |
| AC-08 | Process restart, window replacement, modal lifecycle, and control replacement invalidate old identity evidence deterministically. |
| AC-09 | Injection/Unicode labels remain inert bounded text and cannot alter actions, policy, evidence format, or expected result. |
| AC-10 | Every raw tree has a reviewed normalized core snapshot and traceable control/action mapping. |
| AC-11 | Golden artifacts record OS build, architecture, runtime, display scale, locale, keyboard layout, fixture commit, scenario seed, and capture-tool version. |
| AC-12 | Evidence captures no raw OS handle, username, machine name, user path, credential, token, production identifier, or signing material. |
| AC-13 | Fixture state evidence is synthetic, bounded, atomically written, and unavailable as a production control channel. |
| AC-14 | No fixture binary, source-only experiment directory, SDK/cache, or native artifact enters the npm tarball. |
| AC-15 | Tests cover manifest validation, deterministic reset, golden drift, redaction, resource budgets, failure cases, and package exclusion. |
| AC-16 | Repeated clean runs produce identical normalized semantics and digests except explicitly excluded host metadata. |
| AC-17 | Typecheck, existing full/browser/conformance/contract/audit gates remain green after fixture tooling is added. |
| AC-18 | Independent accessibility, security, interoperability, and package review reports no unresolved critical/high finding before P4.2 completes. |

## Rollback and compatibility

The fixture is development evidence, not a public API. Before its golden format
is accepted, it may be replaced without migration. After acceptance, scenario
or expected-tree changes require a new fixture version, an explained semantic
diff, and reviewer approval. Removing the fixture must not alter the web SDK,
framework adapters, protocol 0.1, npm root exports, or production data.
