# P1.9 — Redacted Lifecycle Audit Events

Status: Implemented and verified; awaiting maintainer review

Phase: 1 — Core contract and DOM reference

Required approver: Repository maintainer

## Problem and user outcome

Hosts cannot currently explain whether an action was requested, allowed,
confirmed, started, verified, replayed, or failed without unsafe wrapper logs.
P1.9 adds a deterministic metadata-only lifecycle stream suitable for transport
correlation and host-managed persistence.

## Scope

- public event-name, outcome, event, and observer types;
- opt-in observer and trusted correlation-ID factory surface options;
- observation and action lifecycle instrumentation at actual boundaries;
- fixed redacted failure outcomes using the P1.8 normalizer;
- explicit idempotent replay event semantics;
- observer failure and re-entrancy isolation;
- versioned JSON Schema, generated artifact, fixtures, README, and tests.

## Non-goals and prohibited changes

- no durable log store, transport, batching, retry queue, or retention policy;
- no target ID, request input/output, node data, principal, origin, policy
  reason, idempotency data, exception message/cause/stack, prompt, or page text;
- no action behavior, policy, verification, or `perform()` result changes;
- no metrics backend or Phase 1 benchmark report;
- no WebMCP, MCP, framework, Playwright, extension, or native code;
- no package publication or version bump.

## Trust boundaries and data classification

The observer is trusted host code; emitted records may cross into a less trusted
logging system. Events are therefore safe by construction rather than by
post-processing. Only catalog-resolved action names are emitted. Early failures
omit the action. Sink return values and failures are ignored and cannot affect
policy, mutation, verification, replay, or returned results.

## Compatibility

Instrumentation is disabled when `onAudit` is absent. Existing surface methods,
results, exceptions, schemas, and callbacks retain their behavior. An audited
surface must provide an opaque URL-safe `surfaceId`; this prevents the existing
URL-based default from entering logs. The options and audit schema are additive
public API.

## Acceptance criteria

| ID | Requirement |
|---|---|
| AC-01 | Public `snapshot()` emits exactly one `surface_observed`; internal action snapshots emit none. |
| AC-02 | A successful confirmed action emits the applicable lifecycle events in actual invocation order with one correlation ID and increasing sequence. |
| AC-03 | Policy denial and confirmation rejection emit redacted terminal `action_failed` events with stable failure-code outcomes. |
| AC-04 | Handler exceptions and non-Error thrown values emit only `internal_error`; raw error data is absent. |
| AC-05 | Events never include target, input/output, node, principal, origin, reason, key/fingerprint, prompt/page text, cause, or stack. |
| AC-06 | A successful keyed replay emits request plus `action_verified: replayed` and does not duplicate policy/start events. |
| AC-07 | Observer throws, rejected promises, mutation, and synchronous re-entry do not change action/snapshot behavior or create recursive events. |
| AC-08 | Audited surface and correlation IDs are constrained opaque values; invalid or throwing trusted factories fall back safely. |
| AC-09 | Event timestamp, elapsed duration, surface revision, and schema version are populated without exposing request data. |
| AC-10 | Audit schema accepts valid fixtures, rejects leaky/mismatched fixtures, and stays synchronized with generated output. |
| AC-11 | Existing deterministic behavior and contracts remain compatible. |
| AC-12 | Typecheck, build, tests, audit, ESM import, and package dry-run pass. |

## Design

ADR 0003 defines the boundary. Public observation and action execution create
separate audit contexts. The action name is added only after it resolves against
the current catalog or a trusted replay record. Each emission constructs and
freezes a fresh event. The observer is invoked synchronously for ordering, while
returned promises are detached with rejection handling. A re-entrancy guard
suppresses events caused synchronously by the observer itself.

## Rollback / disable strategy

Omit `onAudit` to disable all event work, or revert the single P1.9 commit. No
storage or migration exists.
