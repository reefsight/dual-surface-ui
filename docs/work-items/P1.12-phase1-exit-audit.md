# P1.12 — Phase 1 Exit Audit

Status: Audit in progress

Phase: 1 — Core contract and DOM reference

Required approver: Repository maintainer

## Problem and user outcome

P1.1–P1.11 have implementation evidence, but Phase 2 cannot begin until the
Phase 1 deliverables and exit conditions are reviewed together from a clean,
installable commit. Maintainers need one evidence bundle that distinguishes
deterministic proof from jsdom-only limitations and human gate approval.

## Scope

- map all eight Phase 1 deliverables to implementation and evidence;
- freeze runtime export names, reachable declarations, and five JSON Schemas as
  the `0.1` compatibility manifest;
- add repeated-run determinism and explicit adversarial page/output tests;
- run typecheck, build, full tests, schema/API freeze, audit, packaging, example,
  and baseline verification;
- verify a clean checkout with `npm ci` and an isolated tarball consumer import;
- record unresolved limitations, security disposition, and gate recommendation.

## Non-goals and prohibited changes

- no runtime feature, schema semantic, dependency, version, or release change;
- no WebMCP, framework, MCP, Playwright, model, extension, or native work;
- no package publication, tag, deployment, or claim of browser/device proof;
- no declaration that Phase 2 has started before maintainer approval.

## Trust boundaries and data classification

The audit treats fixtures, page text, action input/output, dependency metadata,
and package contents as untrusted. Synthetic secret sentinels must be absent from
serialized results and reports. The freeze manifest contains only public names
and SHA-256 digests, never runtime data or credentials. Temporary clean-install
directories must contain only repository/package artifacts and are disposable.

## Compatibility

The manifest freezes the existing `0.1` surface at commit `a2a201e`; it does not
change it. Future changes to runtime exports, reachable declarations, schemas,
or contract version must deliberately update the manifest with compatibility
review. Audit scripts/tests are development-only and remain outside npm files.

### Audit finding F-01 — Baseline hash was checkout-dependent

The first clean Windows clone failed the committed baseline-report test because
Git converted the HTML fixture from LF to CRLF while the report stored a raw-byte
hash. No runtime or secret-safety behavior failed. The baseline helper, generator,
and test now canonicalize CRLF/lone-CR to LF before hashing; a focused regression
test covers both line-ending forms. The failed clean run is retained in the final
review evidence rather than reported as a pass.

### Audit finding F-02 — Integration tests exceeded the default timeout

Under sustained shared-host contention, two otherwise passing document-approval
integration tests took 5.3–5.9 seconds and exceeded Vitest's default five-second
timeout. The integration tests first received a scoped 30-second timeout. A
later idempotency test also exceeded five seconds under the same contention, so
the test harness now applies a 30-second timeout consistently. Assertions,
workflow steps, policy, and safety behavior are unchanged. A repeat failure at
30 seconds remains a gate failure.

### Audit finding F-03 — Thread worker startup could false-pass

A focused Vitest run reported an unhandled thread-worker startup timeout but
returned exit code zero after running only one of two files. A process-pool full
run then failed to produce a summary after nine minutes. Neither run is valid
test evidence. `npm run test:gate` now starts each test file in its own Vitest
process, requires a one-file passed summary, and
rejects a nonzero exit, signal, missing count, or any `Unhandled Error` text.
The original `test` and watch commands remain available for normal development.

### Audit finding F-04 — Windows worker startup remained resource-sensitive

On the audit host, both thread and fork workers could exceed Vitest's fixed
startup window while endpoint scanning was active. The gate now starts each
test file in a separate outer process and uses one VM-thread worker inside that
process. Cross-file isolation is therefore retained even though isolation is
disabled inside the one-file run. A test-only setup restores Node's Web Crypto
global in the minimal VM context so idempotency exercises the same SHA-256 path
as the supported Node 20+ runtime. The gate still rejects missing summaries,
partial runs, unhandled errors, signals, or nonzero exits.
