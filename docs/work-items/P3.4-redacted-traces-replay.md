# P3.4 — Redacted Traces and Deterministic Replay

Status: Design accepted; implementation in progress

Phase: 3 — Ecosystem, reliability, and evaluation

Required approver: Repository maintainer

## Problem and user outcome

Maintainers need to diagnose and reproduce failures without retaining secrets,
page content, model prompts, or unrestricted action input. Runtime idempotency
replay and offline fixture replay are different safety boundaries and must not
be confused.

## Dependencies and scope

P3.4 depends on P3.3 revision/update semantics and the P3.2 shared lifecycle.
It defines a separately versioned redacted trace format, a bounded recorder, a
synthetic replay-fixture format, deterministic normalization and comparison,
and replay fixtures for every supported deterministic failure class.

Runtime traces record lifecycle metadata and safe digests, not replayable raw
input. Reviewed synthetic fixtures carry only the explicit non-secret input
needed to execute deterministic tests.

## Non-goals and prohibited changes

- no live production recording or replay service;
- no raw prompt, page text, action input, credential, cookie, storage, selector,
  screenshot, stack trace, or provider response in runtime traces;
- no replay against a live surface by default and no policy bypass;
- no claim that a digest chain is a signature or tamper-proof audit ledger;
- no distributed exactly-once or persistent idempotency guarantee.

## Trust boundaries and data classification

Trace input, fixture files, filesystem metadata, and replay output are
untrusted. Runtime records may contain public/internal identifiers only after
normalization. Credentials and secrets are prohibited. Synthetic fixture data
must pass the secret corpus before commit.

## Compatibility and rollback

Trace/replay formats are additive and independently versioned. Recording is
opt-in and uses the existing audit stream without changing its frozen public
contract. Removing the optional recorder/replay paths leaves runtime execution
unchanged.

## Acceptance criteria

| ID | Requirement |
|---|---|
| AC-01 | The trace format has an explicit version, bounded ordered records, source/fixture identity, revision references, and deterministic normalization. |
| AC-02 | Runtime recording excludes all prohibited raw content by default and emits detached immutable values. |
| AC-03 | Synthetic replay fixtures declare initial state, safe requests, expected lifecycle outcome, authoritative final state, and fixture digest. |
| AC-04 | Replays reproduce invalid input, denial, confirmation decline, stale state, precondition failure, replay conflict, execution failure, output-validation failure, and verification failure. |
| AC-05 | Replay comparison excludes nondeterministic time, duration, correlation IDs, and environment noise without hiding semantic differences. |
| AC-06 | Truncated, reordered, tampered, cross-surface, schema-mismatched, oversized, or secret-bearing artifacts fail closed. |
| AC-07 | Offline replay cannot bypass policy, confirmation, principal, origin, revision, or idempotency checks and cannot silently target a live surface. |
| AC-08 | Trace, replay result, stdout, stderr, and committed fixtures contain zero secret-sentinel occurrences. |
| AC-09 | The documentation clearly distinguishes offline fixture replay from core keyed action replay. |
| AC-10 | Deterministic, contract, package, consumer, audit, and diff gates pass with no frozen-root change. |

## Accepted design and planned evidence

The boundary is frozen in
[ADR 0010](../adr/0010-redacted-trace-replay-boundary.md). Runtime recording is
available only through `dual-surface-ui/trace`; offline synthetic replay is
available only through `dual-surface-ui/replay`. The formats use distinct kinds
and schemas. Replay accepts pure declarative JSON only and internally uses one
fresh shared lifecycle coordinator per run.

Planned tests cover successful and failed lifecycles, all nine required failure
classes, normalization, corruption detection, secret scanning, cancellation,
keyed replay/conflict, authoritative final state, malformed object graphs,
budget boundaries, and deterministic repeated runs. Hash chaining detects
accidental corruption and is not presented as authenticity.

No implementation or replay evidence exists yet; design approval alone does
not satisfy an acceptance criterion.
