# P4.3 — Windows UI Automation Adapter

Status: Planned; implementation blocked until P4.2 is accepted

Phase: 4 — Native surfaces

Required approver: Repository maintainer, technical maintainer, and security owner

## Problem and user outcome

The language-neutral protocol and controlled fixture do not yet let an agent
understand a real Windows application. P4.3 builds the first platform adapter
against Microsoft UI Automation (UIA), maps real control patterns into the
existing core semantics, and proves actions from authoritative postconditions
without exposing native authority to the caller.

The adapter is a local library/harness boundary. It is not yet the persistent
authenticated daemon, installer, updater, or public native package.

## Dependencies and entry gate

- P4.1 protocol and independent review accepted;
- P4.2 controlled fixture, golden trees, and independent review accepted;
- ADR 0017 accepted before implementation;
- a recorded Windows evidence host and exact UIA/fixture versions;
- explicit implementation-spike scope that does not pre-empt P4.4's language decision.

## Scope

- enumerate only explicitly admitted top-level windows for the current desktop user/session;
- bind opaque surface references to trusted process/window/runtime identities;
- capture bounded UIA trees and normalize them into core snapshots;
- emit deltas/events from UIA changes with resynchronization on loss or races;
- map Invoke, Value, Toggle, Selection, SelectionItem, ExpandCollapse, and RangeValue patterns;
- re-resolve and revalidate identity, pattern, policy, confirmation, revision, and effects before mutation;
- verify authoritative postconditions and return stable core outcomes;
- redact sensitive elements and fail closed for privileged desktops, integrity mismatch, unsupported patterns, replacement, ambiguity, and resource exhaustion;
- measure capture/action/event behavior needed by the P4.4 language decision.

## Non-goals and prohibited changes

- no persistent daemon, network listener, remote access, service installation, autostart, elevation helper, credential store, signing, updater, or release;
- no mouse/keyboard injection fallback in P4.3;
- no arbitrary process inspection, memory read/write, shell execution, raw COM pointer, runtime ID, PID, HWND, access token, or selector in public messages;
- no secure-desktop, UAC, login-screen, password-value, or unsupported-control mutation;
- no macOS/mobile adapter or cross-platform completion claim;
- no final Rust/.NET/TypeScript selection before P4.4;
- no compiled native artifact in the npm package.

## Trusted boundaries

Protocol bytes, client requests, model output, UIA names/values/help text,
runtime IDs, process/window events, application behavior, and fixture labels are
untrusted. The adapter trusts only host-observed OS user/session identity,
admitted process/window identity, current UIA element/pattern resolution,
package-owned policy/confirmation decisions, and fixture-owned authoritative
state after each has been freshly validated.

`AutomationId`, `Name`, tree position, runtime ID, HWND, and PID are discovery
signals, never sufficient authority alone. An opaque surface/element binding
contains a host-owned generation and dies on process exit, window replacement,
desktop/session change, provider disconnect, ambiguity, or lost event sequence.

## Mapping rules

| UIA source | Core projection/action |
|---|---|
| Window/control type and localized control type | bounded role hint; normalized role comes from reviewed mapping table |
| Name, help text, item status | bounded untrusted text after redaction; never instruction/policy |
| AutomationId | fixture/application correlation hint; never public authority |
| IsEnabled, IsOffscreen, focus, selection, toggle/range state | bounded semantic state with explicit unknown handling |
| InvokePattern | `click` only when the current element and effect contract match |
| ValuePattern | `set_value` only for non-sensitive writable controls and schema-valid input |
| TogglePattern | deterministic toggle/set behavior with post-state verification |
| Selection/SelectionItem | stable option selection bound to current container and item |
| ExpandCollapsePattern | expand/collapse with descendant-tree refresh |
| RangeValuePattern | bounded numeric input respecting min/max/read-only state |
| Password or sensitive classification | presence/classification only; no value and no write action |
| Unknown/custom provider | safe metadata or stable unsupported failure; never generic input injection |

## Lifecycle and race rules

1. Discover admitted top-level windows from trusted host policy.
2. Mint opaque generation-bound surface references.
3. Capture with budgets, cycle protection, timeout, redaction, and duplicate-ID detection.
4. Before mutation, resolve the current process/window/element and recheck every trusted binding plus policy and confirmation.
5. Invoke exactly one supported semantic pattern.
6. Observe fixture-owned authoritative state and a fresh UIA capture.
7. Return success only when expected effects match; otherwise return a stable failure and force refresh where state is uncertain.
8. Event gaps, provider disconnects, replacement, timeout after uncertain mutation, or a third racing revision require resynchronization.

## Acceptance criteria

| ID | Requirement |
|---|---|
| AC-01 | P4.1 and P4.2 gates are accepted before adapter implementation begins. |
| AC-02 | Real UIA capture on the recorded Windows host maps every accepted P4.2 golden tree to the reviewed core snapshot. |
| AC-03 | Discovery is allowlisted and bound to the current OS desktop user/session; arbitrary process/window enumeration is unavailable to callers. |
| AC-04 | Public protocol data contains no PID, HWND, runtime ID, COM pointer, access token, username, machine name, or native selector. |
| AC-05 | Invoke, Value, Toggle, Selection, SelectionItem, ExpandCollapse, and RangeValue patterns pass real fixture action/postcondition evidence. |
| AC-06 | Every action revalidates session, process/window generation, element identity, pattern, revision, policy, confirmation, and expected effects immediately before mutation. |
| AC-07 | Password/sensitive, secure-desktop, permission/integrity mismatch, unsupported, disabled, read-only, hidden, stale, replaced, ambiguous, and missing targets fail closed with stable errors. |
| AC-08 | No P4.3 path falls back to mouse/keyboard injection, shell commands, arbitrary memory, or unrestricted input. |
| AC-09 | Capture enforces time, depth, node, child, string, action, snapshot, and allocation budgets before public serialization. |
| AC-10 | UIA events produce deterministic deltas or explicit resynchronization; loss, reordering, provider disconnect, and request/event races cannot roll state backward. |
| AC-11 | Cancellation before mutation prevents execution; uncertain or committed mutation reports the authoritative final outcome rather than false cancellation. |
| AC-12 | Process exit, window replacement, desktop/session switch, fixture reset, and reconnect invalidate old surface/element/replay bindings. |
| AC-13 | Injection text and application metadata remain inert untrusted data across snapshots, errors, logs, traces, and model-facing output. |
| AC-14 | Repeated actions follow the frozen idempotency/replay contract and never duplicate a consequential effect. |
| AC-15 | Raw UIA exceptions/platform codes are retained only in bounded redacted development evidence and never enter public errors. |
| AC-16 | P4.4 receives comparable latency, startup, memory, throughput, event-loss, unsafe-boundary, binding, packaging, and maintenance evidence from every viable implementation spike. |
| AC-17 | Existing typecheck/full/browser/conformance/contract/audit/package gates remain green and npm contains no native artifact. |
| AC-18 | Independent Windows accessibility, security, protocol, race/concurrency, and package review reports no unresolved critical/high finding. |

## Rollback and compatibility

P4.3 remains an internal adapter candidate until P4.4 selects the implementation
approach and later host/security gates pass. It cannot change protocol 0.1 or
the frozen web SDK. Replacing a spike is allowed without public migration, but
golden evidence and observed platform limitations remain retained. Any future
public Windows support claim requires the selected implementation to rerun all
P4.3 evidence from a clean checkout on a supported host.
