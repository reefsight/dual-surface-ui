# P3.6 — Cross-Exporter Conformance

Status: Implemented and verified on 2026-09-21; Phase 3 continuation remains authorized

Phase: 3 — Ecosystem, reliability, and evaluation

Required approver: Repository maintainer

## Problem and user outcome

Transport success does not prove semantic parity. Maintainers need one scenario
corpus that verifies that DOM, WebMCP, MCP, and Playwright preserve the same
core lifecycle and authoritative application outcome where their declared
capabilities overlap.

## Dependencies and scope

P3.6 depends on completed P3.2 through P3.5 behavior. It adds a canonical
scenario specification, adapter drivers, a reviewed capability matrix, a
normalized semantic/result oracle, and a machine-readable conformance report.

MCP and WebMCP share one mandatory core corpus. DOM and Playwright run the same
cases where the capability matrix declares equivalent behavior. Native WebMCP,
compatibility-layer, and Playwright-managed browser evidence remain separate
tiers.

## Non-goals and prohibited changes

- no flattening of legitimate transport projection differences;
- no screenshot, callback return, HTTP success, or tool-call completion as the
  authoritative state oracle;
- no optional label for a mandatory security/lifecycle case;
- no native adapter or provider/model evaluation;
- no business rule implemented only inside a conformance driver.

## Trust boundaries and data classification

Exporter projections, protocol metadata, page content, and driver output are
untrusted. Scenario definitions and authoritative fixture state are reviewed
test assets. Secret sentinels must not cross any adapter or report channel.

## Compatibility and rollback

The harness and fixtures are private additive test infrastructure. P3.6 adds no
root export, package subpath, CLI command, runtime dependency, or packed
conformance schema. The frozen Phase 1 contract remains 32 root runtime
exports, six reachable declaration files, and five schemas. Any reusable
public test API requires separate package/API review. Removing the harness
changes no runtime behavior.

## Acceptance criteria

| ID | Requirement |
|---|---|
| AC-01 | One canonical scenario format defines initial state, permitted/forbidden actions, request, expected lifecycle result, and authoritative final state. |
| AC-02 | MCP and WebMCP pass the same mandatory discovery, success, failure, policy, replay, and redaction cases. |
| AC-03 | DOM and Playwright preserve equivalent lifecycle outcomes for every capability declared as shared. |
| AC-04 | Mandatory cases cover invalid input, stale/replaced target, denial, trusted confirmation, precondition, verification, replay/conflict, origin/principal/surface isolation, cancellation/disposal, and secret redaction. |
| AC-05 | Adapter-specific projection differences are normalized explicitly and cannot hide a missing action, weakened risk, or different final state. |
| AC-06 | Unsupported cases require a reviewed capability reason; mandatory cases cannot be skipped. |
| AC-07 | Authoritative fixture state and ordered normalized lifecycle outcomes determine pass/fail. |
| AC-08 | Repeated runs and adapter order produce deterministic reports with exact fixture and source hashes. |
| AC-09 | Browser evidence labels compatibility, native WebMCP, and managed-engine tiers separately. |
| AC-10 | Full deterministic/browser, contract, package, audit, and diff gates pass with zero secret leakage. |

## Accepted design

[ADR 0012](../adr/0012-cross-exporter-conformance-boundary.md) freezes the
private harness, canonical oracle, five exact target/tier identities, artifact
schemas, digest domains, report shape, and package boundary before runtime
implementation begins.

The capability matrix contains exactly 26 cases: two discovery, two success,
invalid input, stale revision, replaced target, denial, two trusted
confirmation, two precondition, two verification, keyed replay, replay
conflict, three isolation, two cancellation, two disposal, and three redaction
cases. Every target/case pair is supported except these four direct-DOM gaps:

| Target | Cases | Closed reason code |
|---|---|---|
| `dom-jsdom` | `CANCEL-01`, `CANCEL-02` | `dom_no_abort_signal` |
| `dom-jsdom` | `DISP-01`, `DISP-02` | `dom_no_disposal_boundary` |

No other unsupported status, reason code, waiver, optional case, or
runtime-generated skip is valid. In particular, MCP and both WebMCP tiers run
the cancellation and disposal cases. Cancellation received after execution
starts is commit-wins only where the current target runtime completes that way;
it does not imply interrupt or rollback. `DISP-02` retains target-specific
expected outcomes with one exact authoritative final state. In particular,
Playwright may commit and then return its fixed `stale_revision` failure after
disposal invalidates post-execution observation; the normalizer must not turn
that safe failure into success. Scenario `perTargetOverrides` is forbidden
except on `DISP-02`, where its only key is `playwright-managed` and its only
fields are the exact failure outcomes and lifecycle. Shared final state remains
exact; all other targets use the shared declared expectation. Matrix, scenario,
and suite validation enforce the restriction.

Scenarios, capability matrix, suite manifest, and reports use four strict
private Draft 2020-12 schemas. The suite proves an exact 26-entry bijection
where `caseId == scenarioId`, binds every scenario digest, and includes the
matrix, fixture-host, exact driver, and sentinel-set digests in its suite digest
payload. Scenario and suite digests also bind the exact sentinel IDs, digests,
channels, and expected counts for reviewed trusted injection. Descriptor-safe
capture, closed identifiers, cross-field validation,
bounded canonical JSON, exact domain-separated SHA-256 digests, exact-path
digest exemptions, and secret scanning run before execution or comparison.
Projection normalization preserves risk, confirmation, idempotency, schema
meaning, target-specific outcome code, lifecycle order, and authoritative
state while excluding declared transport noise. Expected values are
comparison-only and never drive fixture execution.

The harness retains the fixture execution, authoritative-state reader, and
dispose capability. Drivers receive only a detached recursively frozen
`{ scenarioId, driverInput }` plus an abort signal and return untrusted data;
no oracle, cleanup function, host object, closure, or mutable alias crosses the
driver boundary. The fixture host separately receives only a newly captured,
deeply frozen execution plan containing `scenarioId`, actions, initial state,
and requests. Expected values, overrides, original scenario objects, and
aliases never cross into fixture execution.

Compatibility WebMCP, native WebMCP, MCP protocol, in-process DOM, and managed
Playwright evidence remain separately labeled. Native environment
unavailability is run-level evidence, not a semantic skip or compatibility
pass. Reports contain no timestamp, duration, absolute path, hostname, random
ID, raw request/output, page text, selector, screenshot, prompt, exception, or
secret. The suite freezes 13 ordered scan channels covering source artifacts,
fixture input and authoritative state, raw and normalized driver evidence,
reports, process streams, and packed/installed package files. Reports bind the
sentinel-set digest and record per-channel plus total byte counts and exactly
zero egress/artifact matches. The two trusted injection channels record only
expected and observed sentinel IDs, digests, and counts—never sentinel bytes—and
must match their scenario declarations exactly. Unexpected or missing
injection, count mismatch, any egress match, missing/extra channel, digest
mismatch, partial scan, or scanner failure fails the gate without reflection.
The `report_payload` scan covers the exact canonical report projection with
both `scan` and `reportDigest` absent. Complete scan evidence is inserted next,
then `reportDigest` is computed over the completed report with only its own
digest absent; this avoids scanner self-reference while binding the evidence.

Every available target runs at least twice from fresh fixtures and environments
in forward and reverse full-target order, including managed Playwright and
native WebMCP. A run is only `completed` or `environment_failed`. Environment
failure accepts only the closed safe native-API, browser-launch, or protocol
reason, contains no case results, and fails the aggregate gate rather than
becoming a skip or partial pass.

Case status is exactly `passed`, `failed`, or `unsupported`. Passed cases carry
no reason or differences; failed cases carry only a closed failure class and
bounded non-reflective differences; unsupported cases carry only the exact
matrix reason and are valid solely for the four approved DOM cells. Unknown,
missing, duplicate, extra, or structurally inconsistent case results fail the
report and gate.

## Implementation and evidence

Private sources are implemented under `test/conformance/`; reviewed schemas,
matrix, and scenarios are under `fixtures/conformance/`; browser-tier checks
are under `e2e/browser/` and `e2e/native/`. Nothing is emitted as a supported
package API. The aggregate source review also binds the fixture server,
package/config inputs, and TypeScript/Vitest/Playwright configuration so a
tampered resolver or runner cannot produce clean evidence.

The dedicated gates will be `test:conformance`,
`test:conformance:browser`, `test:conformance:native`, and
`package:check:conformance`, followed by typecheck, build, `test:gate`, the
Phase 1 contract freeze, every existing Phase 3 package gate, dependency
audit, and `git diff --check`. The package gate binds and verifies both the
packed tarball SHA-256 and the canonical installed-file manifest digest; every
driver report records the verified values. Every driver and browser fixture
server resolves package modules only from that verified fresh install root;
the gate realpaths loaded modules, checks each against the installed manifest,
and rejects workspace/source resolution, aliases, fallback builds, symlinks,
or any module graph outside the install root.

The release aggregate was captured from clean commit `3191120` and is recorded
in [the machine-readable report](../evidence/p3.6-conformance-report-2026-09-21.json).
It contains two fresh-process target-order passes (forward and reverse),
`summary.failed = 0`, `summary.passed = 126`, and four reviewed direct-DOM
unsupported cells. The report digest is
`sha256:d249bef2bda081a0793e6eb59a33f9b57a0b41ce9bc01d42ff8d8027f4e028e2`;
the source tree is clean at
`sha256:7d0cee4af79f2df1a4f332c231466bb392b4e65122d21f5d4bf2c2748a7ba49d`,
and all 13 scan channels report zero sentinel egress.

conformance (Chromium/Firefox/WebKit, 9/9 including spoof resistance), native

The verified package evidence is tarball

installed manifest

The native oracle is Node-owned and authenticated through a capability-checked
binding; the page driver receives no authoritative-state reader. The managed
Playwright oracle likewise rejects forged page/console signals. These are
tested by dedicated adversarial probes in the browser and native harnesses.
