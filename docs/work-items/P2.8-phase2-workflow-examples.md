# P2.8 — Phase 2 Workflow Examples

Status: Implemented and verified on 2026-09-19

Phase: 2 — Web standards and framework adoption

Required approver: Repository maintainer

## Goal and outcome

Provide three small, auditable examples that prove a visible human workflow and
an agent action reach the same authoritative application state through the same
business command and rules:

1. checkout;
2. document approval; and
3. a migrated legacy form.

The examples are integration evidence, not production templates. They must be
deterministic, runnable without a model or network service, and explicit about
the boundary between application business logic, the visible DOM, the core
surface, strict domain annotations, WebMCP export, and drift evidence.

## Shared architecture rule

Each example owns one application-state model and one business command per
mutation. The human event listener and agent handler may adapt their inputs,
but both must call that same command. Authorization, confirmation,
preconditions, effect verification, input/output validation, revision checks,
and idempotency stay in the existing core execution path; examples must not
implement a second agent-only policy or business rule.

Assertions use authoritative state and structured outcomes as the oracle.
Visible text may be asserted as a projection of that state, but screenshots or
DOM text alone do not prove workflow success.

## Example requirements

### Checkout

- Collect only non-credential order intent through the semantic action.
- Keep payment credentials outside snapshots, results, audit, and action input.
- Treat order placement as consequential and require trusted confirmation.
- Recheck inventory and order readiness immediately before execution.
- Verify the authoritative order status after execution.
- Use keyed idempotency so a retry cannot create a duplicate order.
- Prove human/agent final-state parity, stale-revision rejection, invalid input,
  confirmation cancellation, authorization denial, replay, and secret
  non-disclosure.
- Invoke the actual tool registered by the imperative exporter and verify its
  refresh/dispose lifecycle.
- Keep the saved payment credential outside the scoped agent surface.

### Document approval

- Retain the existing P1.11 approval example and its baseline evidence.
- Prove required-widget preconditions, trusted reviewer/origin policy,
  confirmation, keyed replay protection, effect verification, and output
  validation.
- Keep the same approval command behind the human button and agent action.
- Preserve the benchmark sentinel exclusion from snapshots, results, and audit.
- Compile the approval action once through `defineDomainElement()`, invoke its
  actual exported WebMCP tool, and check reviewed initial drift evidence.

### Migrated legacy form

- Enhance an existing native form without replacing its visible markup or
  submit behavior.
- Keep the native submit listener as the single business submission path; the
  agent handler must request that same path rather than duplicate its rules.
- Expose only explicit safe fields/actions and keep credential/sensitive fields
  projected as presence only or outside action input.
- Prove native human submit and agent execution reach the same authoritative
  state, and cover invalid input, hidden/disabled state, stale revision,
  authorization, and secret non-disclosure.
- Use inferred core actions for safe agent-filled fields, while the credential
  remains user/session owned and excluded from tool input.
- Exercise declarative mount/dispose only as reversible progressive
  enhancement; unsupported forms fail closed without attribute mutation.

## Browser and transport boundary

These deterministic examples prove core integration and shared-state parity in
the test DOM. They do not prove browser-private WebMCP registration, Inspector
display, model tool selection, real payment processing, production identity,
or deployment behavior. Supported-browser manual evidence and the fallback
matrix remain P2.9 and the Phase 2 exit gate.

## Evidence

- `npm run typecheck`: passed.
- Focused example suites: 3 files and 45 tests passed, including shared-command
  parity, invalid/stale input, authorization, confirmation, replay, effect
  verification, secret aggregation, and submit-bypass regressions.
- `npm run example:phase2`: all three deterministic runners completed through
  their actual exported WebMCP tools.
- `npm run baseline:phase1`: 25/25 document-approval runs completed with zero
  wrong actions, secret leaks, or unauthorized consequential actions; the
  committed fixture hash remained unchanged.
- `npm run test:gate`: 23 files and 288 tests passed.
- `npm run contract:check`: the frozen root contract remained 32 runtime
  exports, 6 declaration files, and 5 schemas.
- `npm audit --json`: zero vulnerabilities across 191 total dependencies.
- `npm pack --dry-run --json`: 92 intended entries, 83,313-byte tarball, and
  431,780 unpacked bytes.
- A fresh consumer installed the tarball with optional peers omitted, imported
  root, domain, WebMCP, and drift entry points, and contained no React, Vue, or
  Angular runtime.
- Checkout and approval drift checks use deterministic imported integrity keys,
  independently pinned fingerprints, live application permission/state
  readers, live exporter observations, and negative UI-drift assertions.
- Legacy regression evidence proves that the raw submit button exposes no
  semantic click action, guest human/agent submissions make zero mutations,
  and aggregate evidence excludes PIN and CSRF sentinels.

Browser-private WebMCP evidence is recorded separately by P2.9. The 2026-09-19
native Chrome run and equivalent browser-owned DevTools invocation close that
transport evidence without changing the narrower claims made by this work
item. See `../evidence/phase2-native-webmcp-2026-09-19.md`.
