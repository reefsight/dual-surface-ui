# P1.5 — Preconditions and Authoritative Effect Verification

Status: Implemented and verified; awaiting maintainer review

Phase: 1 — Core contract and DOM reference

Required approver: Repository maintainer

## Problem and user outcome

The runtime currently reports success whenever an authorized handler returns
without throwing. That does not prove the business operation was allowed at
execution time or produced its declared outcome. P1.5 evaluates named
preconditions immediately before execution and verifies effects after execution
against trusted application state or deterministic native-control state.

## Scope

- trusted application callbacks for named preconditions and effects;
- precondition evaluation after policy/confirmation and immediately before the
  handler;
- a revision recheck after asynchronous precondition evaluation;
- authoritative verification of every declared effect after the handler;
- built-in verification for native `set_value`, `toggle`, and `click` actions;
- custom non-read actions without declared/verifiable effects fail closed;
- stable `precondition_failed` and `verification_failed` error codes;
- result envelopes are returned only after verification passes.

## Non-goals and prohibited changes

- no rollback/compensation engine after a verification failure;
- no output-schema validation or handler-output serialization;
- no idempotency/replay cache or audit-event transport;
- no policy DSL, WebMCP, MCP, framework, Playwright, extension, or native code;
- no package publication or version bump.

## Trust boundaries and data classification

Action input and model requests remain untrusted. `checkPrecondition` and
`verifyEffect` are trusted application boundaries and should query the same
authoritative services used by the human workflow. Their inputs are not logged
or serialized. Failure errors contain only the action name and stable category;
raw action input, secret values, predicate details, and stack traces are not
included.

## Compatibility

Actions with declared preconditions/effects must now configure the matching
trusted callbacks. Custom non-read actions must declare at least one effect.
Native set/toggle actions continue working when their DOM state confirms the
requested transition. A click that creates no semantic transition now fails
verification; applications with non-DOM effects should register a domain action
and authoritative effect verifier.

## Acceptance criteria

| ID | Requirement |
|---|---|
| AC-01 | Every declared precondition is checked after policy and before execution. |
| AC-02 | A false or unavailable precondition checker blocks the handler with `precondition_failed`. |
| AC-03 | Semantic drift during asynchronous precondition checks is rejected before execution. |
| AC-04 | Every declared effect is checked after execution by the trusted verifier. |
| AC-05 | A false or unavailable effect verifier returns `verification_failed`, never success. |
| AC-06 | A custom non-read action without declared effects fails verification. |
| AC-07 | Native `set_value` verifies the requested value without leaking credentials. |
| AC-08 | Native `toggle` verifies the checked-state transition. |
| AC-09 | Native `click` requires a semantic surface transition. |
| AC-10 | Verified success returns the final post-verification revision and node state. |
| AC-11 | Failure messages do not contain raw input or secret values. |
| AC-12 | Typecheck, build, tests, audit, ESM import, and package dry-run pass. |

## Design

- `checkPrecondition` receives the named condition, policy-bound request, and
  latest pre-execution snapshot.
- `verifyEffect` receives the named effect plus pre/post-execution snapshots.
- Missing callbacks fail closed before execution when metadata declares checks.
- Native `set_value` compares the resulting value, or only `valuePresent` for a
  sensitive control; `toggle` compares the boolean transition; `click` requires
  the semantic revision to advance.
- Custom read actions may complete without mutation. Custom non-read actions
  require declared effects and the trusted verifier.
- A verification failure reports failure after the mutation; compensating or
  rolling back business state remains the application's responsibility.

## Rollback / disable strategy

Revert the single P1.5 commit. No persisted data or schema migration is added.
During pre-release integration, an application can restore P1.4 behavior only
by reverting; bypass flags are intentionally not provided.
