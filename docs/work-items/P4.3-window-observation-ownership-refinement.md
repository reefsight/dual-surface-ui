Date: 2026-10-15, Asia/Bangkok.
Status: Design investigation; trusted proof unresolved; implementation closed.
Owner: `/root`, under existing maintainer delegation.

## Goal and evidence

Define a safe, explicit response to an unsupported NativeWindowHandle
observation without substituting zero, weakening an ownership gate or hiding
the failed golden case. The actual blocker is the
[admitted walk-child-guard negative](../evidence/p4.3-native-suite-ctx1-first-failure-2026-10-15.md),
not toolchain provisioning or an established Desktop/OS cause.
The [independent outcome review](../reviews/p4.3-native-suite-ctx1-outcome-accessibility-agent-review-2026-10-15.md)
accepts faithful failure preservation only. The diagnostic objective is complete;
the semantic correction, native pair and S2 acceptance are not.

The [proposed ADR0021](../adr/0021-native-window-observation-and-membership.md)
does not select an alternate membership route. Its central open obligation is
the trusted fact establishing scope/ownership beyond provider correlation.
Until that is resolved, preserve current refusal. Do not treat this work item
or an approved investigation plan as implementation/native authority.

## Ordered work and entry gates

1. Document and independently evaluate the trusted mechanism that could anchor
   a member with unsupported HWND to the exact currently OS-admitted root,
   process birth, user/session/desktop and generation. Describe counterexamples
   and guarantees/limits from primary API contracts. If none qualifies, defer.
2. Produce a complete candidate design: typed zero/nonzero/unsupported states,
   proof state machine and ordering, provisional-read permissions, all affected
   setup/collector paths, call/budget inventory, identity/fingerprint changes,
   source/project/script/test/reader/record allowlists, isolation and rollback.
   Existing PID/ID/runtime-ID/parent equality alone is not the missing trusted
   mechanism, and current data does not identify a windowless child.
3. Obtain actual independent security, accessibility/interoperability and
   package design reviews; resolve severe findings. Record accepted ADR or
   explicit superseding decision and a separate implementation entry bound
   to exact reviewed bytes. No implementation before this gate.
4. Implement only the accepted new-candidate allowlist. Preserve every frozen
   R1/CTX1/shared input and output. Adapt existing regressions rather than
   discarding them; preserve original admitted pure lanes separately.
5. Review exact source and pass the full pure/security/browser/package/consumer/
   contract/P4.2 prerequisites. Commit the source checkpoint; qualify two genuine
   serial builds from its actual revision, retaining first observations before
   repeat, real metadata association, closure/provenance and ancestor checks.
6. Obtain actual build and complete-packet reviews and fresh human readiness,
   followed by a separate evidence-bound operator go/no-go. Only then may a
   new candidate attempt one fresh first/repeat pair under unchanged counts,
   guards and deadlines. Stop first failure and retain all evidence.
7. Review actual artifacts and record separate S2 acceptance only if its full
   criteria pass. S3/S4 and P4.4 Rust qualification remain later gated work.

Steps1-3 are unfinished. This file authorizes no source change, getter/probe,

## Preservation and completion

Current R1 and CTX1 entries are consumed. Do not rebuild either frozen DLL or
refresh an old packet to bless changed bytes. Future implementation must use
new paths and exact inventories; this investigation intentionally does not
invent a future candidate artifact or approve a selected proof algorithm.

Completion requires the accepted proof/design, independently reviewed source,
qualified outputs and actual passing native artifacts—not merely this plan,
an ADR draft, green pure tests or a toolchain smoke test. If the proof cannot
qualify, keep the native/release gate open and explain the limitation without
changing the acceptance bar. Qualified Rust native, host/macOS and all later
roadmap gates remain necessary for the requested first release.
