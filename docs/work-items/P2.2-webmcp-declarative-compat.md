# P2.2 — WebMCP Declarative Form Compatibility

Status: Ready for maintainer decision; approval pending

Phase: 2 — Web and framework adapters

Required approver: Repository maintainer

## Problem and user outcome

Simple semantic HTML forms should be able to advertise a browser-native
declarative WebMCP tool without losing their ordinary human workflow. The
current draft does not define portable schema synthesis or a reliable
declarative capability test, and the official polyfill does not implement
declarative forms. P2.2 therefore provides a narrow, reversible progressive
enhancement and an explicit safe fallback path rather than pretending to
polyfill unfinished browser behavior.

## Scope

- mount trusted `toolname`, `tooldescription`, and `toolparamdescription`
  annotations on an explicit form/control allowlist;
- conservative supported control subset and credential/sensitive rejection;
- exact attribute restoration on idempotent dispose and remount safety;
- diagnostic-only capability report with `likely-supported` or `unknown`;
- normal visible form behavior when native declarative WebMCP is absent;
- documented explicit fallback through the P2.1 imperative exporter and core
  domain actions, never automatic dual registration;
- deterministic tests and a real-browser manual fixture.

## Non-goals and prohibited changes

- no `toolautosubmit`, automatic submission, form filling, event/prototype
  patching, synthetic native pseudo-classes, or declarative schema synthesis;
- no claim that `document.modelContext` proves declarative support;
- no official/community polyfill dependency: current official polyfill does
  not implement declarative forms or browser-agent integration;
- no DOM-derived tool/parameter descriptions, credential/file/hidden controls,
  cross-origin form targets, frames, or `exposedTo`;
- no root core/schema/version change.

## Trust boundaries

Tool metadata is explicit trusted application configuration. Labels, ARIA
content, values, current field contents, page text, and agent-filled values are
untrusted and are never copied or read by the adapter. Every successful named
parameter control must be explicitly bound; ambiguous, unnamed, disabled,
hidden, file, password, sensitive, credential-autocomplete, foreign, detached,
or duplicate-name controls reject the entire mount before mutation. Normal
application/server validation, authentication, authorization, CSRF, rate
limits, and idempotency remain authoritative.

## Compatibility and fallback decision

Unknown custom attributes are inert, so native annotation is progressive and
the human form remains functional. Capability signals are diagnostic only:
`document.modelContext`, SubmitEvent extensions, and active-selector parsing
together yield `likely-supported`; every other combination is `unknown`, not
`unsupported`.

An application must explicitly choose one path:

1. native declarative annotations from this PBI;
2. the P2.1 imperative exporter bound to an explicit core domain action and
   therefore `performSafe()`; or
3. human-only form behavior.

The adapter never chooses or registers both paths. Native-to-imperative schema
parity is not claimed while the declarative synthesis algorithm remains TBD.

## Acceptance criteria

| ID | Requirement |
|---|---|
| AC-01 | A valid explicit form allowlist receives exact standard declarative attributes and never `toolautosubmit`. |
| AC-02 | All configuration and controls validate before any DOM mutation; failures leave no partial annotations. |
| AC-03 | Metadata uses developer configuration only, enforces 30/500/150 character budgets, and rejects control characters. |
| AC-04 | Credential, sensitive, file, hidden, disabled, detached, foreign, unnamed, duplicate, unsupported, or undeclared successful controls fail closed without reading values. |
| AC-05 | Form action is same-origin, target is the current context, and no iframe/cross-origin delegation is added. |
| AC-06 | Dispose restores exact original attribute presence/value, is idempotent, and permits a clean remount. |
| AC-07 | A second live mount on the same form fails before mutation. |
| AC-08 | Capability output is diagnostic and tri-state-safe: only all positive signals produce `likely-supported`; absence produces `unknown`. |
| AC-09 | No native support leaves the ordinary human form untouched except inert annotations; no tool or DOM-submit fallback is installed. |
| AC-10 | Imperative fallback is documented as an explicit P2.1/core path and cannot double-register automatically. |
| AC-11 | Root contract, full gate, audit, package, and isolated consumer remain green. |
| AC-12 | Supported-browser Inspector/manual proof is recorded separately; unavailable support is not reported as passed. |

## Rollback / disable strategy

Call the mount handle's `dispose()` or omit the optional WebMCP subpath. Revert
the P2.2 commit to remove the helper and example. There is no stored data,
prototype patch, listener, observer, core migration, or automatic submission.

## Standards evidence

- [Chrome declarative API](https://developer.chrome.com/docs/ai/webmcp/declarative-api)
  documents the form attributes, manual-submit default, SubmitEvent extensions,
  lifecycle events, and active pseudo-classes.
- [WebMCP declarative explainer](https://github.com/webmachinelearning/webmcp/blob/main/declarative-api-explainer.md)
  explicitly leaves portable input-schema synthesis TBD.
- [Current WebMCP draft](https://webmachinelearning.github.io/webmcp/)
  still marks declarative synthesis/execution as TODO.
- [Official polyfill](https://github.com/webmachinelearning/webmcp-polyfill)
  does not implement declarative forms, lifecycle window events, or
  browser-agent integration; P2.2 therefore does not install or imitate it.

## Phase 2 exit evidence update — 2026-09-19

Commit `0c6ace4` makes native activation atomic from the browser's perspective:
every trusted description is installed before `toolname`, and disposal removes
`toolname` before restoring the remaining attributes. Real Chrome
`153.0.8010.50` discovered the browser-synthesized `profile.prepare` tool,
filled the visible form fields, preserved manual submission, returned the
existing submit handler's result through `SubmitEvent.respondWith()`, and
removed the tool after exact annotation restoration.

Official `chrome-devtools-mcp` `list_webmcp_tools` and
`execute_webmcp_tool` calls supplied equivalent browser-owned discovery and
invocation evidence for the declarative form. The visible human submit button
remained required because the package does not install `toolautosubmit`. No
literal Model Context Tool Inspector screenshot is claimed.

[Chrome's imperative API documentation](https://developer.chrome.com/docs/ai/webmcp/imperative-api)
marks JSON-stringified inputs deprecated beginning in Chrome 155. The
evidence-only codec therefore uses strings for Chrome 153/154 and objects for
155+, with a managed-browser boundary test. It does not change the package
contract. Detailed evidence is recorded in
[`phase2-native-webmcp-2026-09-19.md`](../evidence/phase2-native-webmcp-2026-09-19.md).
P2.2 is technically verified; Phase 2 acceptance remains pending the maintainer
decision.
