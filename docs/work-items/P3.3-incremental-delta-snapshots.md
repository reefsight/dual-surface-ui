# P3.3 — Incremental and Delta Snapshots

Status: Planned; next after P3.2

Phase: 3 — Ecosystem, reliability, and evaluation

Required approver: Repository maintainer

## Problem and user outcome

Clients currently need a complete snapshot after every observable change. Large
surfaces need a bounded incremental representation that preserves the exact
surface and revision boundary without turning partial state into action
authority. A client must also know when it cannot safely continue and must
request a complete snapshot.

## Dependencies and scope

P3.2 must first freeze the shared lifecycle and Playwright revision semantics.
This work then defines an additive, separately versioned delta contract,
deterministic snapshot diff/apply helpers, explicit gap and resynchronization
behavior, generated schema, fixtures, and an optional package subpath.

The design uses full-node upserts and removals rather than generic JSON Patch
paths. Revisions remain opaque equality tokens. A delta binds one `surfaceId`,
one exact `baseRevision`, and one target `revision`.

## Non-goals and prohibited changes

- no change to the frozen Phase 1 root exports, declarations, or five schemas;
- no authorization or execution directly from a partial delta;
- no assumption that revision strings are numeric, ordered, or globally unique;
- no lossy merge, best-effort application, cross-surface application, or silent
  recovery from a missing base;
- no streaming transport, persistence service, compression dependency, or
  Phase 4 protocol.

## Trust boundaries and data classification

Delta producers, serialized deltas, cached bases, and transport order are
untrusted. Application requires a locally validated exact base. Redaction is
performed before diffing; removed or replaced sensitive state must not survive
through stale fields. A reconstructed snapshot remains observation data and
must be revalidated against the current executing surface.

## Compatibility and rollback

The contract is additive and separately versioned. Consumers that do not import
the optional subpath continue using complete snapshots. Reverting the subpath,
schema, fixtures, and documentation restores the previous behavior without
data migration.

## Acceptance criteria

| ID | Requirement |
|---|---|
| AC-01 | Applying a valid delta to its exact base reconstructs the target snapshot after deterministic canonicalization. |
| AC-02 | The format binds schema version, surface, base revision, target revision, and generation time without ordering assumptions about revisions. |
| AC-03 | Wrong surface/base, gaps, duplicate IDs, contradictory operations, malformed records, and out-of-order application fail closed and request full resynchronization where applicable. |
| AC-04 | Node upserts/removals and changed top-level fields have deterministic ordering and bounded counts and serialized size. |
| AC-05 | Diff and apply never mutate caller-owned snapshots or delta values. |
| AC-06 | Reconstructed snapshots pass the existing snapshot validator; invalid nested nodes/actions cannot enter through a delta. |
| AC-07 | Sensitive removals and replacements leave zero secret bytes in the delta and reconstructed target. |
| AC-08 | A delta cannot be supplied as current execution authority; retained requests remain subject to current surface revision checks. |
| AC-09 | Round-trip, property-style, malformed-corpus, budget, and secret tests are deterministic. |
| AC-10 | Typecheck, build, full deterministic gate, frozen Phase 1 contract, audit, package inspection, isolated consumer, and diff checks pass. |

## Planned design and evidence

Planned source is `src/delta/`, with Phase 3 schemas and fixtures kept distinct
from the frozen Phase 1 manifest. Tests will cover identical snapshots,
metadata-only changes, node/action changes, removal, reorder normalization,
multi-delta chains, missed updates, tampering, and budget exhaustion.

No criterion is complete until commands, versions, results, and reviewed paths
are recorded in this document. No implementation evidence exists yet.
