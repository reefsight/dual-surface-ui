# P2.4 — Angular Lifecycle Adapter

Status: Implemented and verified on 2026-09-18

Phase: 2 — Web and framework adapters

Required approver: Repository maintainer

## Goal and outcome

Angular applications can provide an existing `AgentSurface` through dependency
injection and bind an explicit `AgentElementDefinition` to a rendered host
element with one standalone attribute directive. The adapter owns Angular
lifecycle only. It does not create a surface, infer agent metadata, execute an
action, implement policy, or export a WebMCP tool.

The additive `dual-surface-ui/angular` subpath is designed to export:

- `AGENT_SURFACE`, the typed Angular injection token;
- `provideAgentSurface(surface)`, a value provider for an application-owned
  surface;
- `injectAgentSurface()`, a deterministic helper for retrieving that exact
  surface;
- `AgentElementDirective`, a standalone directive selected by
  `[dualSurfaceAgentElement]`.

## Scope and lifecycle design

The directive receives one required `AgentElementDefinition`. It waits for an
Angular browser render before calling `surface.register()` for the directive's
host `Element`. When the definition changes, it calls the exact previous core
disposer before registering the replacement. Angular view destruction also
calls the current disposer. A missing provider, missing definition, duplicate
ID, or other core registration error fails closed and is not converted into a
successful binding.

Angular providers are immutable within an existing injector. Moving a binding
to another surface therefore means destroying the old view/injector and
creating the new one. The adapter does not add a mutable surface proxy that
could leave ownership ambiguous.

## Trust and security boundaries

Definitions and surfaces are explicit, trusted application inputs. The adapter
does not derive descriptions from children, labels, ARIA text, form values,
errors, URLs, or credentials. It does not subscribe to snapshots and does not
log definition data.

Core remains the sole authority for input validation, stale revisions,
authorization, confirmation, idempotency, replay protection, preconditions,
execution, effect verification, structured failures, and redacted audit
events. Human event handlers and application business services remain the same
ones used without the directive.

## Compatibility and package boundary

`@angular/core` is an optional peer so root, React, and WebMCP consumers do not
load Angular. The initial compatibility range is Angular 20 through 22. The
repository build baseline is Angular 20.3 with TypeScript 5.8, and the Angular
entry point is compiled in partial-Ivy mode.

The entry point is emitted into the existing package rather than published as
a second npm package. A clean application build from the packed tarball is
therefore mandatory evidence that Angular can link the selected secondary
entry-point layout. Failure of that consumer check must be fixed in packaging,
potentially by moving to `ng-packagr`; it must not be waived or hidden by a
source-path test.

## Explicit non-goals

- No Angular-owned policy, confirmation, execution, or verification logic.
- No automatic DOM/ARIA inference or credential access.
- No automatic WebMCP registration or Angular experimental WebMCP integration.
- No snapshot subscription, change-detection bridge, or mutable surface proxy.
- No NgModule wrapper; the standalone directive can be imported by standalone
  components or an NgModule.
- No claim of hydration compatibility until a real hydration test passes.
- No root contract, schema, error-code, or serialization change.

## Acceptance criteria

| ID | Requirement |
|---|---|
| AC-01 | `provideAgentSurface()` and `injectAgentSurface()` expose the exact supplied `AgentSurface`; a missing provider fails deterministically. |
| AC-02 | The standalone directive registers only a browser-rendered host element with the exact explicit definition. |
| AC-03 | The directive preserves existing human markup, Angular bindings, and event behavior. |
| AC-04 | A new definition disposes the previous registration before registering the replacement and leaves exactly one current binding. |
| AC-05 | View destroy/remount removes the owned registration and `data-agent-id` and creates no leak or duplicate. |
| AC-06 | Host replacement cleans the old element before the new element becomes authoritative. |
| AC-07 | Recreating an injector with a different provider removes ownership from the old surface and registers with the new surface. |
| AC-08 | Missing inputs, duplicate IDs, and core registration errors fail closed and are not swallowed by the adapter. |
| AC-09 | Core remains the sole execution and security authority, including for denied consequential actions. |
| AC-10 | Server rendering produces the human markup without registration, `data-agent-id`, or global-document access by the adapter. |
| AC-11 | The emitted Angular entry point is partial-Ivy and a clean packed Angular application can compile and link it. |
| AC-12 | Angular 20 baseline and Angular 22 compatibility-consumer checks pass before advertising the full peer range as verified. |
| AC-13 | A clean root consumer installed without optional peers imports core successfully and has no Angular installation. |
| AC-14 | Full deterministic tests, Phase 1 frozen-contract check, audit, dry-run package inspection, and diff checks remain green. |

## Threat and negative cases

| Case | Expected disposition |
|---|---|
| No Angular provider | Throw a fixed adapter error; do not register. |
| Required definition absent | Fail closed; do not invent or infer metadata. |
| Duplicate agent ID | Preserve core's failure and never replace another element's ownership. |
| Definition changes repeatedly | Dispose-before-register on every completed browser render; retain one live binding. |
| View or injector is destroyed | Invoke the current core disposer once and remove the owned marker. |
| Server render | Render only the human surface; do not register agent state. |
| Root package imported without Angular | Do not resolve or execute the Angular entry point. |
| Consequential action denied by core | Preserve the denial and do not call the definition handler. |

## Frozen-contract constraints

P2.4 is an additive package subpath. It must not change the 32 frozen root
runtime exports, six frozen declaration hashes, five generated schema hashes,
contract version `0.1`, serialized fields, error codes, or default policy and
execution semantics. Angular declarations and generated partial-Ivy files are
outside the Phase 1 root contract but remain public API requiring review.

## Known limitations and open proof

Browser hydration has not been exercised. Angular documents that render
callbacks are not guaranteed to run after hydration is complete, so unit,
server-render, or ordinary client-render tests are not evidence of hydration
compatibility. P2.4 must continue to label hydration proof as pending unless an
actual hydration application test is added and passes.

The adapter also does not prove WebMCP Inspector support; that evidence belongs
to the WebMCP exporter and the Phase 2 exit gate.

## Rollback

Remove the Angular secondary export and optional peer, stop the Angular build,
and remove the directive/provider files. Existing core, WebMCP, React, and
human UI behavior require no migration because no serialized contract or
application state is changed.
