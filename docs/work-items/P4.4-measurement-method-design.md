# P4.4 Native runtime measurement method design

Status: Proposed design preparation only. No runner implementation, candidate
freeze, comparative measurement or language selection is authorized.

Date: 2026-10-04, Asia/Bangkok.
Author: `/root`, for maintainer `Pitchayut586` and independent benchmark,
security, interoperability, package/update and maintenance reviewers under the
[existing delegation](../reviews/phase4-agent-review-authorization-2026-10-03.md).

## Purpose and scope

The existing [P4.4 work item](P4.4-native-language-decision.md) and proposed
[ADR 0018](../adr/0018-native-runtime-language-decision-method.md) require
comparable real Windows measurements before choosing a native strategy. This
design specifies measurement boundaries, calculations, failure treatment and
bounded evidence admission so a future runner cannot make incomparable numbers
appear to justify Rust. It does not select candidate packages or toolchains.

P4.3 is still incomplete. Preparation of this method is not acceptance of its
adapter, permission/lifecycle cases, S2/S3/S4, or the full P4.4 gate. Measurement
entry still requires accepted P4.1–P4.3, accepted ADR 0018, actual independently
reviewed instrumentation/runner source, and a separately frozen candidate,
workload, host, budgets and evidence manifest before observing results.

## Ready contract and acceptance traceability

This documentation task changes the future evidence trust boundary, not a public
API or runtime package. Candidate/provider output is untrusted. Only the frozen
owned runner and independently reviewed source can attribute a metric to a
trusted boundary; a hash or candidate-reported number alone is not provenance.
Evidence is private development data from controlled synthetic fixtures. Secret,
credential, personal application content, raw OS identity and user-app discovery
are prohibited. Model evaluation is N/A: no prompts, discovery or model choice
change. Executable native/calculation-runner proof remains a later requirement.

## Future freeze and comparable workload

The future admission manifest must bind exact source commits/digests for the
runner, instrumentation, each attempted candidate, fixture, accepted P4.3
workload and oracles; protocol corpora; release build/lock/dependency/SBOM
artifacts; command arguments and redacted environment profile; Windows/API/build
and coarse hardware class; clock acquisition/frequency/resolution; metric inventory;
sample/order schedule; all time/resource/evidence limits; and reviewer/entry
records. No default or missing field supplies an acceptance threshold. Freeze
the actual accepted budgets and eligibility rules before any comparative run.

Use one recorded Windows host/profile and the same accepted fixture/workload,
seeds, admitted tree sizes, action mix, reset procedure, concurrency, provider
timeouts, cancellation and event-loss injection for every viable candidate.
Include all applicable accepted P4.3 semantic/security/failure cases. A smaller
benchmark subset cannot satisfy qualification; any additional microbenchmark is
labeled supplemental and cannot select a language.

Preserve at least 30 fresh candidate-process starts and 100 warm complete
capture/action/event workload cycles per candidate. One warm cycle traverses
the entire fixed ordered workload, not one chosen easy case; case-level series
retain their own 100 observations rather than pooling different cases. A process
start is not an OS reboot or cold filesystem cache. Record that limit explicitly.
Only the frozen, verified preparation before the first dispatch of a cycle is
untimed. The continuous whole-cycle timer starts immediately before that first
dispatch and ends after the last case's required verification is admitted. All
between-case fixture reset/setup, queueing, waiting, delays and planned process
restart/reinitialization remain inside it. Never pause, restart or replace that
timer with a sum of active case intervals. Preparation cannot contain unreviewed
helpers, measured-work bypass or retries.

"Warm cycles" names the campaign phase, not a claim that every case shares one
hot process lifetime. Required fatal/restart cases retain fresh process epochs
and their initialization costs inside the cycle; they cannot move replacement
worker preparation outside it. Freeze and report each case's hot/fresh lifetime
cohort before results. An optional active-time sum is a separately labeled
metric, not complete-cycle end-to-end throughput.

The planned candidate and run order is fixed before results, including any
counterbalancing/interleaving and cooldown. Record environmental interruption
as invalid/failed evidence, not an excuse to reorder a slow candidate. The same
monitor/instrumentation configuration and documented overhead apply to all.
No candidate may remove its safety/verification work to win a timing comparison.

## Timing boundaries and clocks

Use monotonic duration counters from the admitted owned process. Store integer
start/end ticks; never subtract UTC timestamps or uncorrelated runner/candidate
clock origins. The admitted schedule binds each metric/phase to its trusted
instrumentation role, process-epoch reference and clock-instance profile, not
to a candidate-selected label or frequency. Freeze the acquisition method,
units, frequency and resolution rules before data. A trusted birth record binds
each planned new process lifetime to an opaque epoch and clock instance when
created; it cannot reuse an exited process's clock origin. Both endpoints must
belong to that same instance. A row's redundant frequency must exactly equal
its immutable admitted profile. Provider/candidate declarations do not create
profiles or override their authority.

All endpoints below belong to the same named clock within each interval. An
optional candidate-internal phase is a separate series, never silently summed
into or substituted for runner end-to-end latency. Derive durations from admitted
endpoints and profiles, CPU ratios from admitted lifetime counters and the wall
window, and throughput from admitted verified-cycle counts and cycle intervals.
Do not trust row-reported derived values. Timing rows have null `value`; any
future redundant derived summary must use a reviewed exact representation and
match independently recomputed data or fail admission. Zero wall denominators
or insufficient counter resolution make a required ratio incomplete/refused,
not zero, infinity or a favorable measurement.

| Series | Start | End and authority | Included scope |
| --- | --- | --- | --- |
| Cold start | Runner immediately before creating the fresh owned candidate process | Runner accepts its source-bound ready/session/catalog plus first correct capture of the already prepared fixture | Process startup, admission, transport, first capture and validation; not fixture startup |
| Capture | Runner immediately before sending the fixed capture request | Runner admits the complete response and verifies projection/oracle parity | Queue, capture, normalize, serialize/transport, parse and validation |
| Action | Runner immediately before dispatching the authorized fixed action | Runner admits the outcome and authoritative postcondition evidence | Current policy/confirmation/identity/revision, mutation, verification and transport |
| Mutation call | Candidate immediately before the semantic provider call after final guards | Same candidate clock immediately after the call returns | Provider call only, not a verified business result |
| Verification | Candidate immediately after the semantic call returns | Same candidate clock after both fresh native state and independent fixture-state checks complete | Actual postcondition reads/comparison; no cached oracle substitution |
| Event | Runner immediately before sending the approved trusted fixture trigger | Runner admits the correlated event and authoritative refreshed state | Trigger delivery and verified event handling, not an isolated provider callback |
| Resync | Runner immediately before the fixed accepted gap/reorder/loss injection | Runner admits the required fresh authoritative state/generation | Injection, detection, refresh and verification; no local event-counter completeness claim |
| Planned crash/recovery | Runner immediately before the approved fixed fault/lifecycle injection | Same runner clock after observed old-process exit and acceptance of the required fresh generation/session/catalog and first correct capture, including old-reference refusal and retained uncertainty/reconciliation checks required by accepted P4.3 | Fault delivery, exit detection, fresh process admission/startup, reconstruction and independent postcondition verification |

The crash/recovery family binds each planned fault to its trigger, old/new epoch,
observed exit and independently verified end state. Report planned, attempted,
recovered, refused and failed case counts, and the eligible recovery latency
series; counts must reconcile with the fixed schedule. A planned terminal fault
whose accepted contract forbids recovery has its own verified terminal/refusal
endpoint and is not a recovered latency sample. A restart alone is not recovery
proof. Preserve authoritative uncertainty or reconciliation evidence whenever
required; do not claim P4.5 durable host/authentication behavior from adapter
recovery. Planned faults are fixed workload cases, not retries of an unexpected
failure. Unexpected crashes still stop at first failure.

Expected refusals/failures, cancellation, overload and uncertain outcomes have
separate labeled timing series with the required authoritative semantics. They
are qualification cases, not successful-action latency observations. Optional
internal timers cannot establish a provider effect or native authorization.

## Resource and delivery measurements

### Owned process topology and counter coverage

Freeze a bounded expected candidate-process topology: roles, parent relations,
maximum depth, simultaneous live count, total lifetime count, planned birth/exit
slots, and metric-window membership. Proposed ceilings are 32 simultaneously
live owned candidate processes, depth 4 and 16,384 lifetime instances per
candidate campaign; the actual admitted finite schedule may only lower them.
A larger topology needs reviewed method revision before data, never omission
of a helper. Freeze the lifecycle plan before creation; trusted birth records
then bind actual opaque epochs to that plan without pretending future process
identities are known in advance.

Counter authority must use runner-created retained process capabilities with
creation/lifetime identity or a separately reviewed owned-process containment
mechanism. Candidate-supplied PIDs/names, PID relookup after exit, broad process
enumeration and first-match descendant discovery are not authority. Enforce
count/depth bounds before admitting births/collection. Unplanned, missing or
escaping children, lifetime reuse, duplicate attribution and absent exit data
refuse/invalidate the candidate observation; they cannot silently disappear from
its cost. Freeze how containment/accounting detects those failures before runs.
These are design requirements, not implemented OS containment guarantees.

CPU is the delta of user+kernel CPU time of the candidate and every admitted
owned candidate child across the same fixed observation window. Each lifetime
needs an initial and final counter, including children that exit during the
window and generations replaced by planned recovery; missing final data is not
zero. Convert each counter's frozen raw unit before exact bounded summation,
and retain membership/coverage records. Report seconds
and elapsed wall seconds separately; CPU percent is `100 * cpuSeconds /
wallSeconds` and can exceed 100 on multiple cores. Fixture, runner and observer
CPU are recorded separately, not selectively charged to another candidate.
Freeze the OS counter acquisition and exited-child accounting before runs;
missing child/CPU data makes that required metric incomplete. Windows process
CPU sums execution across its threads; it is not necessarily bounded by wall
time ([Windows process time definition](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-getprocesstimes)).

Memory is the sum of resident working-set bytes across those owned candidate
processes, at the same frozen sampling cadence and idle window. Shared pages
may be counted in multiple process working sets: this is not unique physical
RAM, committed/private bytes or an unsampled absolute peak. Report idle-window
median and **sampled** peak, cadence, coverage and observer overhead. The peak
is the maximum of the per-cadence sums for the admitted membership, not a sum
of independent per-process peaks. Sequential counter reads are not atomic;
retain their sampling-window width and lifetime/exit coverage, and refuse gaps
under the frozen tolerance rather than inventing values. If private
bytes are required, make them a distinct frozen metric. Raw units are bytes;
display MiB as bytes divided by 1,048,576, without altering raw comparison.
Working sets may contain shared and private pages
([Windows working-set definition](https://learn.microsoft.com/en-us/windows/win32/procthread/process-working-set)).

Complete-cycle throughput is the count of complete verified fixed workload
cycles divided by the sum of their continuous first-dispatch-to-final-admitted-
verification runner intervals, with identical case mix/concurrency. Each
interval includes every intervening reset/setup/wait/restart described above.
Before-cycle preparation is excluded and disclosed, so this metric is not
continuous whole-campaign throughput. A separately frozen campaign-window
metric must include between-cycle preparation too. Never derive either from
a sum of individual case timings or count mutation calls/messages instead of
verified cycles. Unexpected failure prevents a qualifying throughput value;
preserve attempted/completed counts regardless.
Event loss, duplicate/reorder and resync counts are grounded in the fixed trusted
trigger/injection ledger and authoritative state, not provider timestamps or
an assumption that a local callback counter saw every notification.

Binary bytes, packaged archive bytes and installed manifest-file bytes are
separate measurements of the exact reviewed artifacts. Report bundled/runtime
dependency assumptions and compressed/uncompressed boundaries. Build wall time
uses one frozen dependency/cache profile and declared setup boundary. Dependency
counts distinguish direct/runtime/transitive/toolchain components from the
reviewed lock/SBOM. License, CVE, unsafe/native boundary, authentication/isolation,
sign/update/rollback and contributor effort remain a separately evidenced
qualification matrix; never compress them into a weighted speed score.

## Deterministic aggregation and failures

For a complete valid homogeneous series, sort exact nonnegative rational
durations `1000 * (endTicks - startTicks) / frequency` in milliseconds.
Frequency must be positive and start <= end. Do not convert large raw integers
to lossy floating point before ordering; independently review checked bounded
arithmetic. Median is the middle value for odd n, or the arithmetic mean of the
two middle values for even n. P95 is nearest-rank `x[ceil(0.95*n)]`, with one-based
indexing. It is a descriptive statistic, not a confidence bound or worst case.

For synthetic sorted durations 1..30 ms: median 15.5 ms, p95 29 ms.
For 1..100 ms: median 50.5 ms, p95 95 ms. For [1,1,2,2,9] ms: median 2 ms,
p95 9 ms. These examples specify arithmetic, not native performance proof.
Retain exact raw rational data; round only display to six decimal places and
show counter resolution. Qualification/ranking cannot compare rounded displays.

No outlier trimming, replacement sample, automatic retry or post-result warmup
is allowed by this proposed method. Expected negative cases pass only their
frozen refusal/effect criteria. An unexpected timeout, crash, wrong state,
secret leak, permission/guard failure, incomplete metric or invalid artifact
stops the affected run at first failure; preserve its original record and
withhold candidate qualification. Unknown shared-host/fixture safety stops the
campaign until a separately reviewed controlled continuation. No unchanged
retry inherits this plan's authority.

A timeout is a retained failed/censored observation with its actual boundary
and frozen limit, not a successful sample equal to that limit, zero or infinity.
Incomplete success series cannot yield a qualifying median/p95/throughput.
Optional descriptive partial values, if retained, must be labeled incomplete,
state expected/attempted/valid/failed counts and cannot rank/select candidates.
Unsupported required metrics are incomplete, not favorable zero values.

## Bounded private evidence admission

Proposed internal evidence format is JSON manifest plus ordered JSONL sample
shards, not a new public protocol schema. The future runner/validator must have
independent source and adversarial review before measurement. Hashes bind bytes,
not truth; native origins, ownership, instrumentation and original artifacts
remain separately verified. Never read current D2 partial Temp output as data
for this future campaign.

The manifest has a closed key set: formatVersion, campaignRef, methodDigest,
sourceBindings, candidateBindings, fixtureBindings, workloadBinding,
environmentProfile, clockProfiles, metricDefinitions, limits, schedule,
processTopology, entryBindings, evidenceFiles, disposition, counts and terminalStop.
Each table has an exact reviewed
closed shape in the future source freeze, not arbitrary extension objects.
Unknown/duplicate keys, unsafe numerics, invalid UTF-8, missing bindings and
unplanned observations fail admission before aggregation. This design is not
that implemented schema or a successfully admitted manifest.

Every sample row has closed fields: campaignRef, candidateRef, plannedSlot,
phase, caseRef, cycle, metricRef, processEpochRef, clockRef, startTicks, endTicks, frequency,
value, status, reason, verificationRef and artifactRefs. Timing ticks/frequency
use bounded unsigned decimal strings of at most 20 digits. Non-timing numeric
values use the same bounded integer representation with a metric-defined unit;
inapplicable fields are explicit null. Status/reason/phase are fixed reviewed
enums, never provider/exception prose. A failed row cannot include a passing
verification reference. Each planned slot is one metric observation in the
frozen ordered schedule; case and cycle counts derive from their required slots
and authoritative verification, not row count alone. Source-bound admission
enforces interval semantics, topology/lifetime membership, clock-profile
equality, planned order and exactly one row per completed valid metric slot.

### Complete versus terminal-negative disposition

A qualifying complete disposition requires every planned slot, exact required
verification/artifact references, reconciled counts, and null terminalStop.
Expected negative cases count as valid only when their frozen refusal/terminal
contract is independently verified; they are not unexpected failed slots.

A failed, invalid or aborted disposition may admit a stopped negative packet,
never a qualifying dataset. It requires a contiguous valid original prefix
through slot K and a separate trusted runner terminal record for the attempted
slot K+1, binding the last admitted slot, stop reason, available original failure
artifact/exit references and count reconciliation. Its terminal measurement
row may be absent; record that absence, not a reconstructed row. If a structured
failed/invalid/aborted row exists, it belongs only to that terminal slot, cannot
carry passing verification and cannot replace the trusted stop record.

Counts refer to metric slots: planned = attempted + unattempted; attempted =
valid + failed + invalid + aborted. A complete packet has attempted = valid =
planned and failed = invalid = aborted = unattempted = 0. A stopped packet
has valid = K, attempted = K+1 and
exactly one of failed/invalid/aborted = 1; the untouched suffix is unattempted.
No duplicate slots, interior gaps, rows after stop, contradictory exit/counts
or successful terminal verification are admitted. Stopping before any dispatch
is an admission-aborted packet with attempted = valid = failed = invalid =
aborted = 0, all slots unattempted and a trusted pre-dispatch reason; its packet
disposition is not a fictitious aborted slot. No terminal row is invented.
For a failure discovered after the final observation, preserve all rows but
mark the packet invalid with a post-run terminal record: valid slot count can
equal planned, with zero failed/invalid/aborted slots, without qualifying the
candidate. Packet-level invalidation is not a fabricated failed metric slot.
Such a record cannot recast
an earlier missing/failed slot as a completed run.

Malformed/untrusted original bytes stay retained and quarantined, not repaired
or reserialized as admitted measurements. Negative-packet integrity admission
does not imply those bytes passed row admission. If the required contiguous
original prefix cannot itself be admitted, preserve the independently bound
terminal envelope and reject dataset admission; do not fabricate prefix rows
or counts. Negative packets and incomplete series cannot produce a qualifying
aggregate or candidate ranking. The future validator must test both complete
and each terminal-negative branch explicitly.

Proposed parsing ceilings: manifest 1 MiB, each shard 4 MiB and 4,096 rows,
each row 4 KiB, each opaque label 128 UTF-8 bytes, at most 1,024 explicitly
listed shards and 256 MiB total measurement metadata. The future freeze must
check the complete planned workload fits these ceilings without excluding a
case; any needed larger design requires review before results. Reference native
artifact budgets remain those accepted in P4.3, not these metadata ceilings.
Validate manifest totals before allocation and each original regular owned
file's exact size/hash/path identity before parsing; do not enumerate arbitrary
directories or follow traversal, links, external paths or URLs from evidence.

Artifact references are fixed logical file IDs and exact SHA-256 digests into
the admitted owned campaign manifest, not caller-selected paths, raw PID/HWND,
SID, username/hostname, COM pointer, native selector, endpoint/credential, provider
text, private app state, stack trace or source exception. Freeze approved safe
host/build/hardware metadata without those identities. Retain original failed
records/exit disposition; an absent row/artifact cannot be reconstructed as a
successful sample, or reserialized and presented as original evidence.

## Review and later entry

Before any runtime work, independently review this design for comparable
endpoints/units/math, qualification-before-ranking, safety/provenance/privacy,
package/update/contributor evidence and exact original P4.4 requirements.
Separately authorized source implementation follows the original prerequisites;
before actual measurement execution, require deterministic calculation tests,
integer/clock/count/ordering/duplicate/traversal/oversize/redaction adversarial
cases and independently observed instrumentation overhead. Source implementation
is not measurement entry, and tests are not required to exist before their own
authorized implementation.

Future negative vectors include frequency substitution, wrong clock role,
clock-origin/epoch reuse after restart, mixed endpoints, raw-unit mismatch,
derived-value mismatch, zero denominator, insufficient resolution and checked
arithmetic overflow/oversize. Topology vectors include PID/lifetime reuse,
unplanned/missing/escaping child, exit before final counter capture, double
attribution and live/total/depth overflow. Evidence vectors cover missing
terminal row, pre-dispatch abort, post-run invalidation, stopped contiguous
prefix, interior gap, duplicate, count/exit contradiction, post-stop success,
failed-row passing verification and malformed original prefix. These remain
future executable requirements, not results of this design-only review.

P4.4 requires a credible authenticated-local-host/isolation/sign/update design
for each candidate; it does not require accepted P4.5 implementation before
choosing that implementation's runtime. Actual P4.5 host acceptance is later
and cannot be claimed from these qualification designs or prototype metrics.
Independent benchmark, security, packaging/update and maintenance reviews and
an explicit later strategy decision remain mandatory. Rust preference is only
the unchanged late tie-break consideration; no speed win offsets a safety failure.

This preparation edits no runtime, schema, package/dependency, accepted ADR,
fixture/golden/corpus or existing execution/evidence freeze. It grants no native
attempt, OS/desktop/security change, installation, daemon, user-app capture,
input injection, model/key/environment read, P4.4 measurement, P4.5/P4.6/P4.7
entry, publication, release, merge or whole-project Rust migration. The outstanding
[S2 host-context/controlled-continuation boundary](../evidence/p4.3-native-suite-d2-development-2026-10-04.md)
and full completion goal are unchanged.
