# P4.4 — Native Runtime Language Decision Gate

Status: Planned; measurement blocked until P4.3 evidence is accepted

Phase: 4 — Native surfaces

Required approver: Repository maintainer, technical maintainer, security owner,
and release owner

## Problem and user outcome

The maintainer prefers Rust, but preference alone does not prove that a Rust
daemon is safer, easier to ship, or materially better than .NET on Windows plus
Swift on macOS, or Node with maintained native bindings. P4.4 makes the choice
from the same real Windows fixture and adapter workload, while keeping protocol
0.1 and the web SDK independent of the outcome.

The decision must select one bounded native-host strategy or explicitly defer
selection. It never authorizes a whole-project rewrite.

## Entry gate

- P4.1 protocol accepted and frozen;
- P4.2 real Windows fixture/golden evidence accepted;
- P4.3 Windows adapter semantics and measurement workload accepted;
- ADR 0018 accepted before comparative measurements;
- candidate toolchains, packages, licenses, provenance, and exact versions
  frozen before results are observed.

## Candidate set

At minimum, the gate evaluates viable approaches from:

1. Rust native host/normalization engine with maintained Windows UIA bindings;
2. .NET Windows host with a separately evaluated Swift/macOS path;
3. TypeScript/Node host with maintained native bindings, if it passes the same
   security, lifecycle, and packaging requirements.

A candidate may be excluded before measurement only with documented binding,
license, platform, maintenance, or security evidence. A failed spike remains in
the report and cannot silently disappear.

## Frozen measurement method

- same P4.2 fixture version, Windows host, scenarios, seeds, and protocol corpus;
- release-mode builds with dependency lockfiles and reproducible commands;
- at least 30 cold starts and 100 warm capture/action/event cycles per candidate;
- identical admitted window, tree size, action mix, timeout, cancellation, and
  event-loss injection;
- record median/p95 latency, cold startup, idle/peak working set, CPU time,
  throughput, event loss/resync, binary/install size, crash/recovery behavior,
  unsafe/native boundary, dependency count, CVEs, toolchain/build duration, and
  implementation/maintenance effort;
- no discarded outlier unless the pre-accepted method names the mechanical rule;
- raw samples, environment, source commit, lockfile digest, and runner version
  retained in machine-readable evidence.

## Mandatory qualification gates

Performance cannot compensate for correctness or safety. Every selectable
candidate must first achieve:

- 100% protocol message/session corpus disposition;
- 100% P4.2 golden-tree mapping and required P4.3 semantic action cases;
- zero unauthorized consequential action and zero secret leak;
- zero unresolved critical/high security, dependency, binding, or packaging finding;
- fail-closed permission, identity, replacement, stale-state, replay, event-loss,
  cancellation, timeout, and resource-exhaustion behavior;
- a credible local-only authenticated host, process isolation, signing,
  packaging, update, rollback, and contributor-maintenance design;
- no C/assembly or unreviewed unsafe/native boundary.

## Decision rule

Rust is selected only when at least one accepted requirement cannot be met
safely and maintainably by the viable non-Rust approaches, or when evidence
shows a required single hardened cross-platform host/process-isolation property
that the alternatives cannot provide. A small synthetic speed win alone is not
sufficient.

If multiple candidates satisfy every requirement, the decision minimizes
long-term security/packaging/update/contributor risk. Maintainer preference for
Rust is a documented tie-break consideration only after mandatory evidence.
If no candidate qualifies, the result is `defer`; the gate does not lower
requirements to force a selection.

## Acceptance criteria

| ID | Requirement |
|---|---|
| AC-01 | P4.1–P4.3 are accepted before candidate measurement begins. |
| AC-02 | Candidate scope, versions, dependencies, repetitions, workload, environment, budgets, retry/outlier rules, and evidence retention are frozen before results. |
| AC-03 | Every candidate runs the same protocol corpora, golden trees, actions, failures, races, event-loss, cancellation, and resource cases. |
| AC-04 | Semantic/security qualification is evaluated before performance and cannot be offset by speed or memory. |
| AC-05 | Reports retain every attempted candidate and failed/unsupported result with exact reason. |
| AC-06 | Latency reports include cold start and median/p95 capture, action, verification, event, and resync scopes. |
| AC-07 | Resource reports include idle/peak working set, CPU, throughput, binary/install size, build time, and dependency count. |
| AC-08 | Security reports include isolation, local authentication design, unsafe/native code, binding maturity, CVEs, permission model, crash recovery, and attack surface. |
| AC-09 | Delivery reports include supported OS/toolchain matrix, deterministic builds, signing, packaging, update/rollback, license, SBOM, and contributor cost. |
| AC-10 | Rust is selected only under the accepted evidence rule; preference alone and a whole-project rewrite are prohibited. |
| AC-11 | If Rust is selected, it owns only the native host/normalization boundary; TypeScript web/framework packages and protocol schemas remain unchanged. |
| AC-12 | If another candidate is selected or the decision is deferred, the report states why and retains the Rust measurements without manipulating thresholds. |
| AC-13 | C is limited to reviewed binding gaps behind a safe interface; assembly remains prohibited without a new ADR. |
| AC-14 | The decision record binds to exact commits, corpus/golden digests, toolchains, lockfiles, raw samples, and reviewer identities. |
| AC-15 | Existing full/browser/conformance/contract/audit/package gates remain green and no experimental/native artifact enters npm. |
| AC-16 | An independent benchmark reviewer confirms comparability and calculation correctness. |
| AC-17 | Independent security, packaging, update, and contributor-maintenance reviewers report no unresolved critical/high finding for the selected strategy. |
| AC-18 | The repository maintainer explicitly accepts `rust`, `platform-native`, `node-native`, or `defer`; no implementation proceeds from an inferred decision. |

## Outputs

- frozen method and candidate manifest;
- per-candidate raw samples and comparable report;
- binding/security/packaging/update/maintenance matrix;
- independent review records;
- accepted ADR 0018 with final disposition;
- implementation authorization limited to the selected native boundary.

## Rollback and compatibility

Experiments remain outside the npm package and may be removed after evidence is
retained. Selecting a native language cannot change protocol 0.1, core schemas,
root exports, framework adapters, or web behavior. Reversing an accepted choice
requires a new ADR, migration/rollback design, and rerun of every applicable
native conformance and security gate.
