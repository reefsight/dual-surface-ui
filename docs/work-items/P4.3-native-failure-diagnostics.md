## Closed private record

Use one fixed `failure.json` only in an already successfully admitted fresh
owned first/repeat output directory, CreateNew and at most4096 UTF8 bytes.
No file is written to a raw CLI path or before output admission; early entry
refusals remain safe fixed stderr codes. Failure publication does not acquire
new filesystem/UIA authority. Reuse opened-handle/nonreparse/single-link checks.
If publication itself refuses, retain the original refusal and partial files;
never overwrite, follow another path, retry publication or turn it into success.

The exact twelve required keys, with no optional or additional keys, are:
`schemaVersion`, `kind`, `sourceDigest`, `collectorBinaryDigest`,
`fixtureBinaryDigest`, `case`, `stage`, `site`, `classification`, `code`,
`cleanupCode`, `recordedAt`. `schemaVersion` is exactly `0.1`, `kind` exactly
`p4.3-native-capture-suite-failure`. All three digest fields are lower-case
`sha256:` plus64 hex digits and must exactly match the newly admitted D1 freeze.
`case` is `bootstrap` or one of the unchanged22 case IDs; bootstrap may recur
only before SetCase, and process-restart launch retains that current case.
`stage` is exactly one of `output`, `startup`, `setup`, `capture`, `publication`,
`report`, `cleanup`. Entry failures before output admission never create a file.
`site` is explicit JSON null or one of these static host labels:

`fixture-start`, `fixture-ready`, `setup-admission`, `collector-start`,
`process-id`, `window-handle`, `control-type`, `automation-id`, `is-password`,
`is-enabled`, `is-offscreen`, `value-readonly`, `range-readonly`,
`expansion-state`, `selection-container`, `runtime-id`, `root-from-handle`,
`tree-first-child`, `tree-next-sibling`, `tree-parent`, `pattern-required`,
`pattern-operation`, `sdk-mutation`, `capture-call`, `record-read`,
`artifact-write`, `report-write`, `owned-stop`.

Null site is allowed at every stage to retain a coarse uninstrumented refusal.
Non-null stage/site pairs are closed: startup permits fixture-start,
fixture-ready, setup-admission, collector-start and record-read; setup permits
setup-admission, collector-start, record-read and all labels from process-id through
sdk-mutation; capture permits capture-call and record-read; publication permits
artifact-write; report permits report-write; cleanup permits owned-stop. Output
permits only null. Startup permits case bootstrap or process-restart only;
setup/capture/publication/report require a fixed case rather than bootstrap;
output requires bootstrap. Cleanup can retain any current admitted case.

`classification` is exactly `guard-refused`, `not-supported`,
`malformed-property`, `sdk-fault`, `timeout`, or `unexpected`.
`code` is exactly `InvalidObservation`, `AmbiguousSubject`, `ResourceExceeded`,
`Unavailable`, `Timeout`, or `Unexpected`. Actual CaptureException preserves
its exact closed code and normally classifies as guard-refused. A getter's
already-returned exact NotSupported sentinel or wrong type classifies as
not-supported/malformed-property with InvalidObservation; these two classes
require a property site from process-id through selection-container above.
An already-thrown SDK ElementNotAvailable/ElementNotEnabled exception classifies
sdk-fault with Unexpected; do not classify arbitrary InvalidOperation/Argument
exceptions as provider facts. TimeoutException classifies timeout/Timeout.
All other errors classify unexpected/Unexpected, without inspecting error text,
HRESULT, stack, Data or InnerException. InvalidObservation/other guard codes
cannot masquerade as timeout or sdk-fault. `cleanupCode` is explicit null or one
of the same six code literals, and only records a later actual cleanup refusal.
For a primary cleanup failure it remains null. `recordedAt` is an actual UTC
`yyyy-MM-ddTHH:mm:ss.fffZ` timestamp, exactly24 ASCII characters; reject invalid
calendar/time components, timezone variants or source-generated test timestamps
in production by calling UTC clock directly without a native timestamp injection
seam. A parser proves only timestamp shape/calendar, not the provenance of an
equal literal. Pure serialization/parser tests may use deterministic timestamps.

Parser limits are4096 original bytes, depth2, at most32 JSON tokens and decoded
string length128; require strict UTF8, no BOM, no trailing JSON, no duplicate
decoded keys (including escaped aliases), no malformed UTF16, exactly one flat
object with strings or explicit null only. Valid escaped strings are allowed
but cannot bypass exact enums/keys. Caller-provided pins are shape-checked;
the CLI separately admits actual fixed D1 source/binary/review freeze first.
No full output directory, PID/HWND/runtime ID, automation selector,
provider Name/value/help/text, raw exception/HRESULT/stack/module/type name or
unbounded string becomes a record field. No successful/green case tag, fake
snapshot, inferred fixture mutation count or observed OS-ownership claim.

Stage/property-site values come exclusively from static host callsites. A
provider's ProgrammaticName, property value or exception cannot supply them.
When a suite typed getter is already required by the existing algorithm, it may
classify a refused already-returned object as exact NotSupported or malformed,
or an already-thrown getter fault, without storing the value, reading it again or substituting
a default. Do not add a Name/content/pattern read to diagnose unknown safety.
No inferred unknown value becomes an admission or mutation authority.

The existing native worker is the sole failure writer. The launcher never
creates or overwrites failure.json and never infers a worker location from pipe,
deadline or exit failure. A launcher-only refusal may therefore have no record.
Each already-required operation runs inside a static stage/site context restored
on normal return. A catch at the innermost instrumented required operation
latches the first closed tuple before unwinding; it stores no Exception object
or provider value. Nested outer catches cannot replace it. A typed getter reads
once, then performs the unchanged deadline/type checks; classification merely
describes that already-observed failure, never permits continuation/defaults.
The unchanged post-read deadline check takes precedence over type/sentinel
classification: a returned NotSupported followed by ResourceExceeded is a
guard-refused/ResourceExceeded failure, not not-supported. Add that pure ordering
vector without sleeping or another provider read.
Caller-only collector instrumentation identifies capture-call, not an unseen
collector property. No new SDK calls occur for instrumentation.
The four intentionally caught expected provider-rejection probes remain normal
workload outcomes: surround the complete existing Rejected wrapper, not the
inner intentionally caught SDK throw, with the diagnostic context. A guard,
unexpected SDK throw or failed unchanged-state assertion still terminates.
The primary is the first synchronously observed unhandled refusal, not an
earliest-in-time claim about asynchronously faulted fixture stream tasks.
External worker kill, blocked cleanup, pipe overflow or early admission refusal
may leave no failure record and an unknown worker location. No artifact is
invented for those cases; launcher240-second and owned-stop limits stay fixed.

The worker creates a diagnostic context before construction but grants its
output capability only after canonical fixed-path, directory, ancestor and
empty-output admission succeeds. It then creates records and launches the
fixture as before. Constructor refusal before capability means fixed safe
stderr only; after capability it may retain a failure record. The worker runs
the suite, catches/latches any primary refusal before cleanup, performs only the
already-required owned cleanup once, latches a later cleanup code separately,
and attempts one CreateNew failure publication after cleanup. Do not use a
using/Dispose unwind that can replace the primary. Normal Execute already
stops owned resources before complete-report creation; do not run an additional
cleanup after a fully successful Execute. A stop failure during Execute becomes
the primary cleanup stage when no earlier failure exists; attempted cleanup
after it must not perform another mutation or re-open removed native peers.
Latch stopAttempted before the first cleanup call for each owned process
lifetime, including process-restart and final stop, not merely when Execute
returns. A report/stdout refusal after that stop cannot trigger another Kill or
Dispose. Independently catch each already-required collector/process/stream/
handle cleanup action so an earlier cleanup fault does not skip the remaining
already-required owned-resource closure. Each is attempted once only; retain
the first cleanup refusal in the existing primary/secondary fields and do not
repeat Kill, widen deadlines or consult/re-open provider peers. A later new
owned process gets a new stopAttempted flag; no global process lookup is added.
Publication failure emits only a fixed withheld-output refusal, retains the
original tuple/files, and cannot retry, fallback, delete or return success.
No failure artifact alone proves cleanup succeeded. Diagnostic metadata remains
a source-derived assertion, not proof of adversarial atomicity.

Success must still have exactly the original132 artifacts/report/records child,
no failure artifact. A failure record cannot be admitted by the success verifier.
Add a separate read-only original-byte failure parser/admitter; no application
launch or fixture mutation is performed by failure inspection.
The separate CLI accepts only `--failure-directory` and an already admitted
fixed first/repeat directory. Read only the opened regular single-link
failure.json with cap+1 fixed allocation/current identity/ancestor guards;
do not enumerate or decode partial provider/capture/record files. Reject an
unknown failure kind/schema rather than interpret it as a successful report.
A partial or complete suite-report.json may coexist after report-write/stdout
failure; retain it without reading, decoding or treating its presence as success.
Failure-only admission remains negative and cannot authorize success, even in
that case. Emit only the admitted closed record plus original-byte digest and
explicit `nativeAccepted:false`; no successful case count. It uses no C0 freeze
fallback, fixture launch or output write. Existing success verification retains
its exact known artifact topology and therefore rejects failure.json.

## Tests and evidence gates

1. Pure cases cover every closed stage/classification, unknown case/site/code,
   extra/missing/duplicate and escaped-duplicate keys, null/wrong types, malformed
   UTF8/UTF16/BOM, timestamp/digest shape, size/depth/token overflow and exact
   source/binary mismatch. Keep diagnostics deterministic without sleeping.
2. Fault-injected seams prove zero provider reads/mutations after refusal,
   sensitive/unknown values never enter records, error messages/stack/native IDs
   do not become data, first failure survives cleanup faults and failure cannot
   be rewritten as success. These are unit evidence, not actual OS proof.
3. File/launcher units cover unadmitted/raw output path, reparse/hardlink,
   oversized files, CreateNew collision, truncated/incomplete record and bounded
   stdout/stderr. No failed artifact is overwritten or deleted during tests.
4. Actual source review binds final changed code, design, new private verifier,
   fixtures/case order, reports and binaries. Preserve all earlier C0 approvals
   and attempts. Require current units/focused/full/type/package/contract/audit/
   managed-browser/existing deterministic conformance and P4.2 gates.
5. Only a new separately admitted execution entry may run a changed candidate.
   Stop its planned serial first/repeat at the first failure and preserve the
   new private record/original partial artifacts. Do not rerun unchanged C0 or
   widen budgets. Independently inspect actual failure record provenance before
   naming a refusal location; site alone is not a proven underlying cause.
6. If observations require a membership/safety/provider compatibility refinement,
   retain that failure and review a new design before implementation/execution.
   Diagnostics alone cannot waive all22/32 native golden/original-byte proofs,
   independent artifact reviews or the separate S2 runtime decision.

## Goal and rollback

This is bounded failure observability within S2, not a new terminal project
goal. S3/S4, real OS negatives, P4.4 Rust qualification/comparison, host/macOS
and the full Phase4 exit remain unchanged. Roll back only the new isolated
diagnostic increment by version control while retaining all earlier bytes and
failure history. No publication/main merge/release or whole-project migration.
