# P1.3 — Runtime Input Validation and Stable Errors

Status: Implemented and verified; awaiting maintainer review

Phase: 1 — Core contract and DOM reference

Required approver: Repository maintainer

## Problem and user outcome

Action metadata can declare an input JSON Schema, but the runtime currently
passes untrusted input to authorization and handlers without validating it.
Callers also receive implementation-specific error classes without a stable
machine-readable code. P1.3 makes invalid input fail closed before policy or
execution and gives every supported runtime failure a stable public code.

## Scope

- validate declared action input schemas at execution time;
- publish input schemas for inferred native actions that accept input;
- reject invalid input before authorization and handler execution;
- introduce a stable typed error base and public error-code union;
- preserve specialized error classes for ergonomic handling;
- add deterministic tests for valid, invalid, and malformed schemas.

## Non-goals and prohibited changes

- no policy engine, principal/origin rules, confirmation UI, or replay cache;
- no output validation, precondition evaluation, effect verification, or audit
  event transport;
- no structured transport failure envelope;
- no WebMCP, MCP, framework, Playwright, browser-extension, or native code;
- no package publication or version bump.

## Trust boundaries and data classification

Action input is untrusted. Schema validation runs before authorization and
execution. Validation errors expose a stable category and concise message but
must not serialize the raw input, credentials, stack trace, DOM selector, or
application internals. Credential action values remain absent from snapshots,
fixtures, and test output.

## Compatibility

Valid existing actions continue through the same authorization and handler
flow. Invalid input that could previously reach a handler is intentionally
rejected. Existing specialized errors remain exported but gain a stable
`code` property through a shared base class.

## Acceptance criteria

| ID | Requirement |
|---|---|
| AC-01 | A valid value matching a declared input schema reaches authorization and execution. |
| AC-02 | Invalid input is rejected before authorization and handler execution. |
| AC-03 | An action with no declared input schema preserves its existing behavior. |
| AC-04 | Inferred `set_value` exposes and enforces a string input schema. |
| AC-05 | Malformed developer-provided schemas fail closed before their handler runs. |
| AC-06 | Supported runtime failures expose a documented stable error code. |
| AC-07 | Error messages and tests do not echo raw action input or secrets. |
| AC-08 | Typecheck, build, deterministic tests, audit, and package dry-run pass. |

## Design

- `AgentError` is the common public base with an `AgentErrorCode`.
- Existing errors keep their class names and map one-to-one to stable codes.
- `AgentInputValidationError` uses code `invalid_input` for both value mismatch
  and unusable schemas; no raw value is included in its message.
- One strict JSON Schema 2020-12 validator instance validates action input.
- Validation occurs after surface/revision/action lookup and before the
  authorization callback.

## Rollback / disable strategy

Revert the single P1.3 commit. There is no persisted data or migration. Actions
without input schemas are unaffected, so individual custom actions can also
temporarily omit their schema during pre-release integration.
