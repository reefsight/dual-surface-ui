# P4.6 — macOS Accessibility Adapter and Permission Lifecycle

Status: Planned; implementation blocked until Windows conformance and P4.5 host acceptance

Phase: 4 — Native surfaces

Required approver: Repository maintainer, technical maintainer, security owner,
macOS platform owner, and release owner

## Problem and user outcome

Phase 4 requires equivalent semantics on macOS, not a Windows-only protocol.
P4.6 maps real AXUIElement accessibility state/actions into the same frozen core
contract and verifies user-granted permission, revocation, application lifecycle,
sensitive controls, events, sandbox/signing, and host authentication on a real
supported macOS machine.

## Entry gate

- accepted Windows golden/adapter/host conformance from P4.2, P4.3, and P4.5;
- accepted P4.4 runtime/binding strategy and macOS implementation boundary;
- a real recorded macOS host and controlled native fixture application;
- explicit approval of the macOS permission, sandbox, signing, and evidence plan.

## Scope

- real AXUIElement tree capture and normalized snapshot/delta/event parity;
- AXPress, value, selection, expand/collapse, increment/decrement, and other
  reviewed semantic actions with authoritative postcondition verification;
- Accessibility permission not-requested/denied/granted/revoked/regranted lifecycle;
- application launch/exit/relaunch, window replacement, focus/space/display
  changes, notifications, provider timeout, and lost-event resynchronization;
- secure/password/sensitive/unsupported controls and injection text;
- local authenticated P4.5 host integration, code signing/notarization/sandbox
  feasibility evidence, package exclusion, and performance comparison.

## Non-goals and prohibited changes

- no permission bypass, TCC database modification, synthetic approval, root
  helper, remote access, Apple Events expansion, screen recording, CGEvent input
  injection, shell, arbitrary process inspection, or secure-field value access;
- no claim from simulator/mock/non-macOS evidence;
- no weakening of protocol/core semantics to match platform quirks;
- no iOS/Android/mobile support implication;
- no production notarization credentials, App Store submission, public release,
  npm-native artifact, or automatic updater activation.

## Platform invariants

- Accessibility consent is user/OS authority and is rechecked at discovery and mutation.
- Denied/revoked permission exposes no catalog and invalidates affected sessions.
- AX identifiers, PIDs, object references, pointers, and application text never establish public authority.
- Elements are re-resolved inside the trusted application/window generation before action.
- Secure text fields expose classification/presence only and no write action through this scope.
- Unsupported actions fail closed; CGEvent/mouse/keyboard fallback is prohibited.
- AX notifications are hints; gaps/races/provider errors require fresh capture or resync.
- macOS roles/subroles/actions map through a reviewed table into the same core roles/actions used by Windows.

| ID | Requirement |
|---|---|
| AC-01 | Accepted Windows and native-host evidence exists before macOS implementation begins. |
| AC-02 | Tests run on a recorded real supported macOS host and controlled application; mocks/simulators cannot satisfy completion. |

## Rollback and compatibility

macOS remains a private development adapter until Phase 4 Exit approval. Rollback
removes only reviewed host/application artifacts, restores the last compatible
signed build, and invalidates sessions. Platform differences belong in bounded
internal extensions/evidence; protocol 0.1 and shared core semantics remain
unchanged. Mobile requires a separate feasibility decision.
