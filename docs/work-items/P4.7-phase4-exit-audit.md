# P4.7 — Cross-Platform Conformance and Phase 4 Exit Audit

Status: Planned; execution blocked until P4.1–P4.6 are accepted

Phase: 4 — Native surfaces

Required approver: Repository maintainer, technical maintainer, security owner,
release owner, Windows platform owner, and macOS platform owner

## Problem and user outcome

Passing individual native work items does not prove that Windows and macOS
expose the same safe agent-facing semantics or that the native host can be
packaged, updated, rolled back, and operated without weakening the web contract.
P4.7 reruns and binds every Phase 4 deliverable into one auditable exit record
before any native-preview support, version, tag, or distribution decision.

## Entry gate

- P4.1 protocol review approved;
- P4.2 Windows fixture/golden review approved;
- P4.3 Windows UIA adapter review approved;
- P4.4 runtime-language decision explicitly accepted;
- P4.5 authenticated host review approved;
- P4.6 real macOS adapter/parity review approved;
- all reviewed commits, corpus/golden digests, OS/toolchain versions, package
  manifests, and reviewer identities frozen in the audit manifest.

## Scope

- clean-checkout rerun of deterministic, browser, protocol, fixture, native,
  cross-platform, security, performance, package, signing/update, and audit gates;
- Windows/macOS semantic parity matrix for equivalent controls/actions/failures;
- OS permission prompt/denial/revocation/regrant evidence;
- secure/sensitive/unsupported/integrity/sandbox failure evidence;
- local authentication, authorization, process isolation, restart/reconnect,
  replay, cancellation, resource, audit, signing, update, rollback, and uninstall evidence;
- accepted runtime decision compliance and no whole-project migration drift;
- npm/public API/schema compatibility and no-native-artifact proof;
- unresolved finding register, limitation matrix, support matrix, operational
  rollback plan, and explicit Phase 4 Exit Review proposal.

## Non-goals and prohibited conclusions

- no inferred approval from green automation;
- no production support, npm publication, native binary distribution, `0.4`
  release, Git tag, deployment, signing-key use, or updater activation;
- no mobile support, remote access, input-injection fallback, secure-desktop
  control, credential access, or unsupported application claim;
- no equivalence claim from mocks, one OS, one control type, or unit tests alone;
- no hiding failed runs, unsupported cases, platform differences, flaky events,
  performance regressions, or unresolved findings;
- no lowering thresholds or rewriting evidence after results are observed.

## Required audit execution

The final audit script/manifest must enumerate every command rather than rely on
an aggregate success flag. At minimum it includes:

```text
clean source and generated-artifact drift checks
all P4 canonical evidence validators
npm run typecheck
npm run test:gate
npm run test:conformance
npm run test:browser -- --workers=1
npm run contract:check
npm audit --audit-level=high
npm pack --dry-run --json
native protocol message/session/property/package gates
Windows fixture/adapter/host real-machine gates
macOS fixture/adapter/host real-machine gates
cross-platform parity and performance gates
authentication/isolation/soak/audit/update/rollback/uninstall gates
secret, private-evidence, binary, and signing-material scans
independent review-record validation
git diff --check
```

## Outputs

- machine-readable Phase 4 audit manifest and per-command results;
- cross-platform semantic parity report and digest;
- security/privacy/permission/isolation control matrix;
- performance/resource/stability/package/update report;
- support/limitations and operations/rollback documentation;
- independent review records;
- Phase 4 Exit Review with an unselected maintainer decision checkbox.

## Exit decision and rollback

Technical readiness does not authorize release. The maintainer may accept,
reject, or require changes. Acceptance permits a separately approved `0.4`
native-preview release process; it does not publish automatically. Rejection or
rollback disables distribution/updates, restores the last accepted package,
invalidates native sessions, retains audit evidence, and leaves the web SDK and
protocol compatibility unaffected.
