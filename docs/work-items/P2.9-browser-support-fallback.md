# P2.9 — Browser Support and Graceful Fallback

Status: Automated browser gates verified; native WebMCP and Inspector evidence pending

Phase: 2 — Web standards and framework adoption

Required approver: Repository maintainer

## Problem and outcome

Phase 2 has deterministic Node/jsdom evidence for the WebMCP exporters,
framework lifecycles, drift checking, and the three example workflows. It does
not yet prove that the packed browser code behaves correctly across real
browser engines or that a supported Chrome build retains, displays, invokes,
and unregisters the tools through its native WebMCP implementation.

P2.9 establishes a conservative support matrix and real-browser lifecycle
suite. Unsupported or unavailable WebMCP must preserve the ordinary human UI,
must not install hidden automation, and must never be reported as native
WebMCP success. Phase 2 remains open until the required native Inspector/manual
evidence and automated compatibility gates exist.

## Evidence vocabulary

Every result must use exactly one of these evidence tiers:

1. **Native WebMCP** — the browser's actual `document.modelContext` registers,
   enumerates, invokes, and unregisters the package-generated tool. Inspector
   or equivalent browser-owned manual evidence is required in addition to
   application-state verification.
2. **Browser with test shim** — a minimal injected `modelContext` records
   registration and AbortSignal lifecycle while the built package runs in a
   real browser engine. This proves package and browser lifecycle behavior; it
   does not prove browser-native registration, agent discovery, Inspector
   display, or browser confirmation UX.
3. **Unsupported/no native API** — the real browser does not expose the
   required API in the tested configuration. The expected result is a typed
   unsupported no-op with the visible human workflow intact. This is successful
   fallback evidence, not successful native WebMCP evidence.

Skipped tests, inferred support from a version number, raw inline probe code,
jsdom, screenshots without authoritative state, and exporter-side observations
are not native WebMCP evidence.

## Scope

- Add a development-only Playwright browser runner and pin its package version.
- Serve built package files and browser fixtures from a loopback HTTP origin
  using a path-traversal-safe, dependency-minimal fixture server.
- Use a second loopback port for a genuinely different origin in cross-origin
  frame tests.
- Load the built root, domain, and WebMCP entry points in browser fixtures;
  inline reimplementations cannot satisfy package evidence.
- Run deterministic package/lifecycle coverage in Playwright-managed Chromium,
  Firefox, and WebKit.
- Run all three P2.8 workflows through visible human controls and through the
  actual imperative exporter using a deterministic test shim, with
  authoritative application state as the success oracle.
- Add an opt-in Chrome-native suite and a headed Inspector/manual checklist.
- Cover unsupported feature detection, partial registration rollback,
  navigation, framework-style dispose/remount, stale tools, same-origin frames,
  cross-origin frames, secret exclusion, and character budgets.
- Publish the evidence-backed matrix in `docs/BROWSER_SUPPORT.md`.
- Record exact browser version, engine, channel, OS, configuration, date,
  command, result, and evidence tier for every claim.

Playwright is a test driver in this work item. It is not the Phase 3 Playwright
adapter and cannot become an unannounced runtime fallback.

## Browser-runner architecture

The deterministic runner uses Playwright Test projects for managed Chromium,
Firefox, and WebKit. A fixture page imports the built ESM package from the local
HTTP server. Before application bootstrap, the runner may install a small
`document.modelContext` shim that implements only registration, abort-driven
unregistration, active-catalog inspection, and invocation. The shim must not
grant permissions, synthesize confirmation, retry stale calls, or bypass the
core execution path.

The native Chrome project must not inject the shim. It uses the actual
`document.modelContext`, `getTools()`, and `executeTool()` where available, and
it records the browser-owned result separately from the Inspector/manual
observation. Native tests fail or remain explicitly pending when the API is
unavailable; they must not silently pass through `test.skip()` and be counted
as Phase 2 completion.

The runner must preserve artifacts only for failed runs or for the explicit
native evidence record. Traces, screenshots, HTML reports, profiles, and
downloaded browsers are development artifacts and must not enter the npm
package.

## Required lifecycle cases

### Navigation and remount

- A hard navigation destroys the prior document and the previous tool is no
  longer available from the new document.
- A single-page route transition disposes its exporter before mounting the next
  surface; only one current registration remains.
- A clean remount does not duplicate a name or retain an old revision.
- Application-owned `pagehide`/unmount integration unregisters tools without
  moving business logic into the adapter.
- Chrome 153 no longer promises that unregistering cancels an already-started
  execution. Tests therefore distinguish catalog removal from execution
  cancellation and continue to rely on core preconditions and verification.

### Stale tools

- A semantic mutation after registration makes the captured invocation return
  `stale_revision` before policy confirmation or business execution.
- Refresh removes the old catalog entry and registers a tool bound to the new
  revision.
- The refreshed tool can succeed only when current authorization,
  confirmation, preconditions, idempotency, and effect checks pass.
- Disposal removes discoverability; tests do not treat direct calls to a
  retained test callback as browser registry behavior.

### Frames and origins

- A top-level surface does not traverse an iframe and silently claim its DOM.
- A same-origin child document owns its own surface and registration lifecycle;
  any parent discovery is browser-native behavior, not adapter aggregation.
- Declarative compatibility continues to reject a form in any frame and leaves
  every attribute and the human submit path unchanged.
- Cross-origin tool registration is unavailable without the `tools`
  Permissions Policy.
- Even when a host delegates the permission, this package does not pass
  `exposedTo`; a parent origin must not gain implicit discovery or invocation.
- Cross-origin failures disclose no tool input, result, credential, audit
  payload, or hidden application state.

### Graceful fallback

- Missing `document.modelContext.registerTool` returns `supported: false`,
  performs no registration, and does not mutate the DOM.
- Unknown declarative capability leaves the visible form editable and manually
  submittable; annotations remain inert and reversible.
- Registration rejection rolls back every exporter-owned registration rather
  than leaving a partial catalog.
- No Playwright, vision, mouse, keyboard, DOM-submit, or automatic dual-
  registration fallback is installed.
- Applications may explicitly choose the Phase 1 core path or retain the human
  path; the adapter never chooses a less secure route on their behalf.

## Official standards and browser references

- [Chrome WebMCP overview](https://developer.chrome.com/docs/ai/webmcp)
  documents the testing flag and Model Context Tool Inspector workflow.
- [Chrome imperative API](https://developer.chrome.com/docs/ai/webmcp/imperative-api)
  documents registration, `getTools()`, `executeTool()`, lifecycle events,
  same-origin discovery, cross-origin permission/exposure, and Chrome 153
  unregister behavior.
- [Chrome declarative API](https://developer.chrome.com/docs/ai/webmcp/declarative-api)
  documents form annotations and browser-synthesized tools.
- [Chrome WebMCP tool security](https://developer.chrome.com/docs/ai/webmcp/secure-tools)
  documents origin exposure and safety annotations.
- [WebMCP Community Group draft](https://webmachinelearning.github.io/webmcp/)
  is the current draft contract and links its Web Platform Tests.
- [Playwright browser projects](https://playwright.dev/docs/browsers) documents
  the managed Chromium, Firefox, WebKit, Chrome, and Edge project boundaries.

WebMCP is experimental and the sources can change. The evidence record must
pin the source access date and browser version rather than convert a moving
draft into an evergreen support promise.

## Explicit exclusions

- No Phase 3 Playwright adapter, MCP exporter, browser extension, model eval,
  vision fallback, mouse/keyboard injection, or external-agent transport.
- No cross-origin `exposedTo` API or permissions delegation feature.
- No automatic navigation observer in the core and no hidden fallback.
- No automatic observation of CSSOM-only, media-query, or animation-driven
  visibility changes; host code must dispose/remount declarative annotations at
  that lifecycle boundary.
- No back-forward-cache support claim in this work item.
- No mobile, Android, iOS, branded Safari, production deployment, or general
  browser-performance claim.
- No browser support inferred solely from Playwright WebKit, Chromium, a user-
  agent string, or a successful build.
- No change to the frozen Phase 1 root contract or schema unless a separately
  reviewed compatibility defect requires it.

## Rollback

Remove the P2.9-only browser runner, fixture server, browser fixtures, tests,
scripts, support matrix, and evidence record. Existing core, exporters,
framework adapters, examples, and package runtime dependencies remain intact.
Downloaded browsers and test artifacts are local development state and are not
part of the package rollback.
