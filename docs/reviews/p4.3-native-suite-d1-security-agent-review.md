## Security properties inspected

- The diagnostic channel is exactly twelve flat required keys and fixed values:
  unchanged case IDs/bootstrap, seven stages, explicit static sites, six closed
  codes/classes, three exact trusted pins, nullable secondary cleanup code and
  actual UTC time. Both parsers reject additional/missing/decoded duplicate keys,
  malformed UTF8/UTF16, BOM, trailing JSON, nested containers and non-string/null
  scalars. Limits are4096 original bytes, depth2,32 tokens and128 decoded string
  characters. Production time is read directly from UTC without a native clock
  injection parameter; parser shape/calendar validity is not clock provenance.
- [ReadRequired](../../experiments/windows-uia/managed-reference/CaptureSuite/FailureDiagnostics.cs:55)
  performs the existing pre-check, one already-required read, post-check and type
  refusal. The post-read ResourceExceeded wins over returned NotSupported.
  Classification stores no returned object, default, content or exception. Fixed
  callsites do not stringify provider objects or inspect Message, HRESULT, stack,
  Data, InnerException, provider ProgrammaticName or exception type names for
  output. Exception-type dispatch is limited to the closed host/SDK categories.
- The innermost At catch latches a validated tuple before unwinding. Outer
  catches cannot replace it. Main latches before cleanup rather than relying on
  a using/Dispose unwind. Later actual cleanup faults affect only the secondary
  code when the primary was not cleanup. A primary cleanup record requires a
  null secondary code. Neither null nor artifact presence proves cleanup success.
- [Stop](../../experiments/windows-uia/managed-reference/CaptureSuite/Program.cs:337)
  sets the per-lifetime stop latch before any of the five independent closures;
  each existing action is caught once, without short-circuiting. A report/stdout
  error after stop does not cause another Kill/Dispose. Restart explicitly begins
  a new owned lifetime. Cleanup uses the existing owned process/collector/streams,
  not a discovered user process or re-opened provider peer. Stream failure may be
  synchronously observed only at cleanup; metadata does not assert earlier
  asynchronous causality. Existing5000ms owned-stop and10/30/240-second budgets
  were not widened.
- The four expected provider rejection outcomes remain inside the complete
  [Rejected wrapper](../../experiments/windows-uia/managed-reference/CaptureSuite/TrustedSetup.cs:107).
  Diagnostics surround that wrapper, not the intentionally caught SDK throw.
  Guard discovery/fencing faults and unchanged-state assertion failures still
  terminate. No new SDK read, mutation, native query, pattern, fallback or safety
  default is introduced by the wrappers. Collector-internal failures remain
  coarse `capture-call`, without a fabricated property location.
- Only the worker owns publication capability. It is granted after canonical
  fixed-path/ancestor/directory/empty-output admission and pin validation, before
  creating records/launching the fixture. One failure publication uses the fixed
  filename, CreateNew and existing opened regular/single-link/final-path checks,
