## Interoperability assessment

The drafts use the actual `walk-child-guard` negative only to locate the
attempted required-handle read. They do not infer a control type, depth,
ordinal, HWND absence, root identity, Desktop/OS cause or safe windowless
wrapper. The diagnostic objective is distinguished from semantic correction
and native acceptance.

The observation matrix preserves explicit Int32 zero, explicit nonzero,
unsupported, null, wrong type, provider error and deadline failure rather than
equating their authority. This matches the important current source distinction:
typed zero can reach the logical-node return in RequirePeerBoundary, whereas
the unsupported sentinel is refused before that function. Converting the
sentinel to zero would change the boundary; neither draft permits it. A typed
zero cannot establish a native root, and nonzero handles retain fresh native
boundary/liveness/root checks.

The proposed member route is explicitly an unselected alternative. A later
design must name a trusted mechanism tying the permitted member to the exact
live admitted root, process birth, user/session/desktop and generation.
Provider PID, identifiers, type/name and parent/runtime-ID equality alone are
not accepted as that mechanism. Parent observations can change or be absent
from the view; runtime identifiers are opaque, scoped and reusable. The
drafts do not invent atomic multi-property observations or claim that primary
API documentation itself proves arbitrary provider forgery. Reciprocal/current
graph checks are requirements to design, not a substitute for the missing
trusted fact.

The required coverage is broader than patching the observed child caller.
It includes setup Guard, Identity, Same, Qualify, Chain, Fence, discovery and
selection, plus collector root/member, selected-peer ancestry, current-state
and publication paths. The current collector requires a typed handle through
RequireBoundary and repeats those boundaries in identity/comparison and
selection/current fences. The drafts correctly require all affected paths,
provisional-read permissions, nonzero intermediate handles and independent
auxiliary roots to be specified before content, pattern access or setup
mutation can be authorized.

Dynamic reparenting, cross-root ambiguity, duplicates/cycles, stale-but-callable
peers, replacement and changes among observation kinds remain explicit future
proof/test obligations. No new getter is authorized by naming these cases;
every proposed call must first enter the reviewed ordering and shared-budget
inventory. Existing basic-safety/redaction behavior is not repurposed as
permission for unknown HWND observations.
