## Initial findings and actual design resolutions

The initial proposal was not approved while its privacy/lifecycle contract was
underspecified. Findings were sent to root before implementation. Root supplied
successive revisions; only the exact final bytes above receive this disposition.

1. **D1-SEC-D01, Medium — unfrozen diagnostic channel/schema.** An inclusive
   list of possible keys and classifications was insufficient to independently
   constrain serialized failure data. Final design fixes twelve required flat
   keys, explicit null policy, static site/stage/case sets and legal cross-field
   combinations. Digest pins must match the independently admitted D1 freeze.
   Code/classification relationships refuse contradictory provider/timeout/guard
   claims. Bound4096 original bytes/depth2/32 tokens/decoded strings128;
   require strict UTF8, no BOM/trailing JSON, decoded-key uniqueness and valid
   UTF16. The normal typed return is not a failure category. **Resolved in
   design**, not an implemented parser or redaction test result.
2. **D1-SEC-D02, Medium — primary refusal masking during unwind/cleanup.** C0's
   outer catch follows using/Dispose unwind; a cleanup exception can obscure an
   earlier failure unless the new lifecycle is explicit. Final design latches
   the first synchronously observed unhandled closed tuple at the innermost
   required operation, before unwinding, without retaining an exception/value.
   Outer scopes cannot replace it; later actual cleanup refusal uses only the
   secondary closed code. Expected provider-rejection probes are wrapped as
   complete intentionally caught operations, so their expected exceptions never
   become a false terminal primary. Post-read ResourceExceeded precedes sentinel
   classification, preserving unchanged guard semantics. Each process lifetime
   marks stopAttempted before cleanup; already-required resource closures are
   independently caught and attempted once. Report/stdout refusal after Stop
   cannot trigger another Kill/Dispose or native-peer access. **Resolved in
   design**; implementation must prove these orderings in its source/pure units.
3. **D1-SEC-D03, Medium — failure writer/output authority ambiguity.** The first
   proposal did not choose between worker/launcher writers or define the exact
   construction/admission point granting the path capability. Final design has
   one writer: the existing native worker. Its context exists before constructor
   entry, but output capability is granted only after canonical fixed-directory,
   ancestor and empty-output admission. Earlier failures emit fixed stderr only.
   Launcher exit/pipe/kill observations cannot invent a worker location or write
   a competing record. After required cleanup, one CreateNew publication is
   attempted; collision/failure retains original tuple/files, with no retry,
   alternate path, deletion or success. New fixed D1 report/freeze/entry paths and
   seventeen source paths prohibit C0 fallback or caller-selected review paths.
   **Resolved in design**; the actual filesystem/constructor source remains
   independently reviewable before any D1 execution.

An additional lower-risk observability/lifetime edge was identified: report
publication can leave a partial or complete suite-report.json before failure,

shape/calendar, not whether an equal literal came from that clock.

## Required implementation invariants and accepted lower risks

The twelve keys and enums are a private closed record, not a new public schema.
Only static host labels and already-observed refusal categories may enter it.
Classify an already-required getter once; do not request any extra property,
pattern, Name, value, HelpText, TextPattern, OS/provider probe or sensitive data
after refusal. No provider ProgrammaticName, exception text/type name/HRESULT,
stack/Data/InnerException, native ID/handle/path or arbitrary string may become
site/category data. Required safety, defaults, membership, mutation guard,
oracle separation, workload and original10/30/240-second limits stay unchanged.

The independent failure CLI admits the actual fixed D1 source/binary/reviewer
freeze before opening the one regular single-link failure file in the fixed
owned first/repeat topology. Cap+1 allocation, ancestor/current identity checks
and original-byte parsing remain mandatory. It must not enumerate/read other
partial captures, fixture records or report contents. Its output contains only
the admitted closed record, original-byte digest and `nativeAccepted:false`;
no green tag, successful case count, caller authority or failure-to-success
translation. Existing positive verification remains exact and separate.

Accept these explicitly bounded limitations, without waiving later gates:

- No captureId or cleanup-success field is required for this narrow first-failure
  location design. The fixed case/stage/site tuple can be coarse and cannot
  distinguish every occurrence of a shared capture callsite. Null site means
  unknown/coarse. A missing cleanupCode never proves cleanup succeeded.
- An unchanged collector refusal remains capture-call, not an inferred internal
  property cause. A diagnostic tuple is a source-derived assertion; it does not
  prove underlying cause, atomic provider state or a complete event history.
- Primary means first synchronously observed unhandled refusal, not earliest
  asynchronous error. External kill, pipe overflow, early admission or blocked
  cleanup/publication may leave no record; absence is unknown, never success.
- CreateNew/regular-handle/ancestor checks retain their sequential cooperative-
  filesystem limitation, not hostile-local/admin atomicity. Existing worker kill
  bounds do not prove per-getter allocation containment, OS cleanup or isolation.
- Expected trusted negative probes and parser/fault-injection units are not S3
  receipt/policy/executor proof or real OS permission/session negatives.
