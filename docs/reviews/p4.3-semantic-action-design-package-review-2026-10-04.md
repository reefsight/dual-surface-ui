## Findings at the initial binding

### AS-P01 - Medium: exact replay needs a current-revision and requestId decision table

References: initial brief lines 194-211 and 189-192;
[src/native-protocol/session.ts](../../src/native-protocol/session.ts), lines
183-191, 203-215, 221-231 and 305-314;
[protocol replay contract](../protocol/native-protocol-0.1.md);
[session replay tests](../../test/native-protocol-session.test.ts), lines 310-340.

The brief permits matching keyed retries to return a recorded admissible
outcome after identity/permission/disclosure checks and relies on the existing
third-revision rule. That rule alone does not prevent an exact historical
replay from moving protocol state backward. Static trace: action A completes
r1 -> r2, another action/snapshot advances the same surface to r3, then exact
completed request A is repeated. The verifier exempts that completed request
from ordinary stale-revision admission, retains its required exact response
fingerprint, and records r3 as the replay's pending surface revision. An exact
old r2 outcome satisfies current == pending.surfaceRevision and the response
path then assigns r2 to the surface. This is a source-derived counterexample,
not an executed test, new native evidence or request to change frozen P4.1.

The design must add an independent host fence refusing historical replay when
fresh trusted current surface revision differs from the recorded outcome
revision, before emitting that old response. It must not rewrite a cached
outcome, refresh its revision or emit a changed response for an already-completed
requestId merely to satisfy the verifier. Define a terminal refusal/resync and
later fresh-session path where an exact admissible response cannot be supplied.

Also make the exact cases explicit: same completed requestId/key/canonical
request and exact response; same key under a new requestId with old revision
(ordinary protocol stale rejection, not a bypass); new requestId/key with a
current but changed bound request (conflict, zero calls); changed request or
response fingerprint; uncertain tombstone; lost permission/generation; capacity
and current-revision advance. Add deterministic transcript/host negative vectors
without modifying the frozen corpus. Protocol verifier failures close its
session, so the table must distinguish an admitted pending request's fixed
request-error from a closed verifier refusal: do not feed a response into a
closed session or imply it was transcript-admitted.

Status: open at the initial cutoff. Root was notified before writing this report.

### AS-P02 - Medium: current-state-only catalog conflicts with already-satisfied intents

References: initial brief line 79 and lines 90-93; ordered boundary lines 138-155;
[src/internal/action-lifecycle.ts](../../src/internal/action-lifecycle.ts),
current target action selection and revision rechecks.

Expand/Collapse exposes only the action appropriate to explicit current state,
yet the prose separately permits an already-satisfied expand/collapse intent
to succeed after policy and postcondition checks with zero mutating calls.
On a current expanded node the advertised action is collapse, so a fresh expand
intent has no executable catalog entry. If state changed during a wait, the
existing observed-revision fence denies it rather than silently accepting a
satisfied intent. Those are different policies and the design must choose one.

The minimal compatible choice is to retain current-state-only descriptors:
a satisfied opposite intent is action_not_found or stale as appropriate, never
a newly invented successful no-op. Exact recorded replay is a separate zero-new-
call path, not a newly authorized invocation. Alternatively, any explicit
state-independent intent profile requires its own catalog, descriptor-count,
revision, policy/effect and test definition before implementation.

Status: open at the initial cutoff. Root was notified.

### AS-P03 - Medium: unchanged fixture cannot provide ComboBox expansion's claimed oracle

References: initial brief lines 79, 85-88 and 260-263;
[fixture manifest](../../fixtures/native/windows-app/manifest-0.1.json), combo action none;
[fixture Program.cs](../../fixtures/native/windows-app/Fixture/Program.cs),
lines 66, 70, 105-107 and 191-205.

The general ExpandCollapse row requires the desired state and membership to
agree with authoritative fixture state while allowing a separately reviewed
ComboBox profile, and later native requirements mention authorized expansion.
The immutable recorder stores selected combo item; its expanded field belongs
only to the Group Expander. It does not record ComboBox.IsDropDownOpen.
Therefore it cannot independently establish the ComboBox open/closed effect.

Keep ComboBox expansion/collapse outside the executable S3 profile as trusted
synthetic setup, or explicitly design/review a limited observation-only proof
using fresh UIA expansion plus admitted owned popup/container membership and
unchanged relevant recorder fields. The latter is not dual authoritative
fixture proof of popup expansion and cannot be described as equivalent.
Neither option authorizes changing the accepted fixture/golden or silently
expanding inside a SelectionItem request. Freeze the chosen scope before source
implementation and actual execution entry.

## Other package/protocol observations

The proposal correctly separates descriptive P4.2/S2 comparisons from a
trusted executable profile table and explicitly preserves scalar Value/Range
and target-based SelectionItem differences without editing goldens. Selection
is observation, not a fictitious container mutation. Unknown basic safety and
unknown per-pattern writability cannot grant an action. Caller input cannot
supply policy, principal, effects, consent or native identity.

Existing core success has action/target/previousRevision/revision and
targetPresent. The result schema requires node when targetPresent is true and
forbids it when false; later implementation must honor that conditional, not
treat node as unconditionally optional. Failed outcomes contain current
surface/revision and an exact constant code/message, with no added uncertainty
field. Keeping private mutation-may-have-started evidence and verification_failed
only when a trustworthy current revision remains available is compatible in
principle; lost correlation cannot be transferred onto a replacement surface.
Provider exceptions alone do not prove no effect, and independent proof may
establish success only without reviving invalidated original authority.

Private 64-entry replay retention is stricter than the verifier's 4,096 completed
requests and is not a public limit change. Retained entry payloads must obey the
stated bounded input/response caps before storage. A tombstone cannot be evicted
to authorize duplication. Confirmation is a private bounded single-use receipt,
not fixture-modal consent or peer authentication. S3's injected cancellation
minimum cannot advertise wire cancellation/events before their separate evidence.

The proposed source stays under experiments/windows-uia rather than src or
exports. Current npm files admit dist, schemas, fixtures/native-protocol, README
and LICENSE; the experiment leak checker rejects the whole Windows research
tree. Current .gitignore and browser rules exclude experiment bin/obj, private
native evidence and SDK/cache paths. These are read-only configuration checks,
not a fresh npm pack/browser execution. A later source candidate must prove
those exclusions with real final-source package/browser gates.

Before any S3 source, the design requires completed original positive S2
first/repeat evidence, authentic artifact reviews and separate S2 acceptance,
then independently approved final S3 design and separate entry. Before native
results it calls for a new explicit source/fixture/binary/case/order/budget/
original-byte grammar/verifier/reviewer/execution freeze; D2 cannot be reused.
All22 S2 scenarios/32 captures stay prerequisites, not renamed S3 action proof.
All source and artifact reviews, failed runs and fresh terminal gates remain
separate from later S3 and full P4.3 decisions. No inherited source approval or
new native authority was found in the initial proposal.
