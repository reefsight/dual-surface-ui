## Security assessment and original acceptance criteria

The important distinction is unsupported structural metadata versus action
authority. A bounded admitted graph may preserve an explicitly unknown node
without authorizing that node or treating unknown as false. The existing P4.3
mapping rules already require explicit unknown semantic-state handling and allow
safe metadata for unsupported providers. AC-07 requires unsafe/unsupported
targets to fail closed; it does not require one unsupported structural wrapper
to erase every otherwise independently admitted target.

| Boundary | How the revised design preserves it |
|---|---|
| OS admission and target safety, AC-03/06/07 | User/session/desktop/process/window/root and current graph checks remain mandatory. A target requires explicitly known nonsensitive, enabled and onscreen observations. Unknown structural ancestors confer no safety authority. |
| Redaction and public authority, AC-04/08/13/15 | No Name/help/value content, native authority, generic injection, new public schema or provider formatting is introduced. Sensitive and required-unknown nodes receive no pattern reads or receipts. |
| Ambiguity and lifecycle, AC-06/07/12 | An unresolved same-ID/type/container unknown-safety candidate blocks discovery; every separately encoded safety-property transition invalidates prior receipts. Current rooted membership and stale-peer/window checks remain mandatory. |
| Resources and authentic evidence, AC-09/17/18 | Unknown wrappers still count toward unchanged graph/read/hash budgets. Fixture/golden/package isolation and actual independent source/native reviews remain required; this design decision satisfies none of the executable completion criteria by itself. |

Known password nodes remain pattern-free. Unknown password/enabled/offscreen
nodes are bounded structural identity/parent records only, never actionable
candidates. An eligible child cannot inherit safe status from a parent, nor
replace its own required observations with a container's type, ID or label.
An unknown ancestor is not blanket permission; future context/policy checks
remain separately required before any guarded execution.

Unknown read-only status is separately stored for Value and RangeValue and
cannot authorize its write family. Unrelated semantic patterns retain their
own requirements. Reading pattern availability/read-only metadata for a
known-safe node is not permission to read Value.Value or execute a pattern.
No peer escapes the decision-only boundary.

## Design history: ambiguity and lossy property state

The original proposal did not expressly retain unresolved qualification when
pattern reads were suppressed. The independent accessibility reviewer raised
the Medium ambiguity gap: a matching unknown sibling's unobserved patterns
cannot be treated as known absent to select a known-safe sibling.

Resolved in the revised design: same correlation, reviewed type and current
container with unknown required safety blocks discovery even alongside a
known-safe pattern-bearing sibling. A different-type structural wrapper may
coexist. This is conservative refusal, not a first-match or safe-looking-match
fallback.

The revised proposal also requires separate Value/Range read-only observations
and independent fingerprint fields. A single OR/combined state can hide one
property's transition while the other remains true/unknown. Distinct per-property
encoding preserves the stated invalidation obligation. Unknown-plus-pattern
forgery rejection and corresponding regression cases are now explicit.

## Mandatory implementation and evidence checks

The following are obligations of the approved design, not passing evidence:

- Only reference equality with the exact framework NotSupported sentinel may
  create Unknown. Null, strings, numbers, arbitrary objects and provider faults
  remain capture failures. Do not stringify unsupported values or call provider
  equality/formatting. Keep strict Boolean rejection for uses needing a bool.
- For nullable Boolean representation, use exact known-value predicates:
  Sensitive == false, Enabled == true, Offscreen == false, and the requested
  Value/Range read-only flag == false. Expressions such as Sensitive != true
  or ReadOnly != true can accidentally admit null/Unknown and are forbidden.
  Do not rely on implicit defaults, null-coalescing or type-based safety.
- Both collection and catalog must enforce eligibility. Injected/copied pattern
  lists on nodes with unknown required password/enabled/offscreen flags must
  be rejected; collector suppression alone is not a sufficient defense.
  Known-password-plus-pattern contradictions also must not authorize a receipt.
  This invariant is distinct from an available Value/Range pattern whose own
  read-only observation is unknown: that family remains unwritable, while
  unrelated independently eligible patterns need not disappear.
- Test no pattern reads for each unknown required flag and known sensitivity,
  not merely an empty stored list. Unknown nodes must still undergo ordinary
  process/parent/root/duplicate/cycle/depth/child/string/aggregate budget checks.
  Capture or copy failure still invalidates all old bindings.
- Test same-ID/type/container unknown siblings separately for password,
  enabled and offscreen, a different-type unknown wrapper that may coexist,
  duplicate containers, and adversarial unknown-plus-pattern input. Suppressed
  reads mean unavailable qualification, not proven pattern absence.
- Test known false/true/unknown transitions independently for all fields,
  including both read-only families, old-receipt denial after recovery and
  fresh receipt discovery only after all required observations become known
  safe. Read-only state of one family must not hide another family's transition
  or be copied into its writable authority.
- Keep the diagnostic categories closed and privacy-safe. Preserve all failures,
  re-review the actual source delta and bind fresh serial native first/repeat
  evidence to it before any identity-slice acceptance. Missing explicit safety
  on a requested action target is a terminal unavailable target, not grounds
  to modify the accepted fixture, substitute defaults or widen deadlines.

### Checked implementation of the design

- The three required structural safety properties and two per-family read-only
  fields are nullable Boolean records with no implicit false conversion.
  ObserveBoolean maps only reference equality with the exact NotSupported
  sentinel to null; all other values go through strict RequireBoolean.
  SafetyBoolean retains one ignoreDefaultValue:true property read and only
  closed local diagnostic categories.
- ObservePatterns invokes its callback only for explicitly nonsensitive nodes
  whose enabled/offscreen flags are both known. Known disabled/offscreen nodes
  may have availability inspected, but are not operable; this is not relaxed
  action eligibility. Unknown essential flags and known sensitivity skip every
  pattern availability/read-only call. No Name/help/value content is introduced.
- CopyAndCheck independently rejects any nonempty pattern list on a node with
  an unknown password/enabled/offscreen flag. A supplied known-sensitive pattern
  list cannot authorize a receipt because RequireOperable refuses it. Bounded
  defensive copies, rooted graph, cycle/duplicate/container and resource checks
  still apply to unknown structural nodes and their descendants.
- Qualified collects correlation/type/current-container matches first and
  refuses any required-unknown candidate before using pattern availability.
  Thus an unknown same-type sibling cannot disappear from ambiguity. A
  different-type unknown wrapper remains structural and may coexist.
- RequireOperable uses Sensitive is false, Enabled is true and Offscreen is
  false as exact necessary predicates. Value and RangeValue each additionally
  require their own read-only flag to be explicitly false; one family cannot
  borrow another's writable state. Unrelated patterns keep their own checks.
- Fingerprints independently encode Enabled, Offscreen, Sensitive, ValueReadOnly
  and RangeReadOnly as 1, 0 or ?. Each field is delimited and included. Unknown
  transitions cannot be hidden by an OR/combined state. Observation/hash changes
  and malformed/provider/copy faults still invalidate all previous bindings;
  recovery does not revive old references.
