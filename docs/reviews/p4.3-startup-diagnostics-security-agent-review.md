## Security assessment

1. **Failure-only and original decision preservation.** Program lines 88–90
   call StartupWait only around the two actual startup waits; construction of
   NativeObservation follows outside their catches. Lines 174–190 preserve the
   original predicate and use a best-effort TryPublish followed by bare `throw`.
   No diagnostic field controls admission, deadline, case continuation, report
   publication or repeat. Mutable Scenario/Stage cannot trigger a diagnostic
   for a later admission/provider failure. TryPublish encloses path, collection,
   encoding, creation, write and disposal faults in its optional catch.
2. **Closed output and bounded encoding.** StartupDiagnostics lines 42–61
   reject all stages except `launch-window`/`launch-state` and validate every
   category before serialization. Output has exactly nine string fields:
   `schemaVersion`, `kind`, `stage`, `process`, `window`, `stateRecords`,
   `resetAckRecords`, `cpu`, `resident`, with fixed version/kind. The serializer
   constructs a flat object, so depth is structurally below 3; it does not
   serialize arbitrary objects or exception/provider text. The 1024-byte check
   happens before any file is created, and the allowed literals bound encoding
   allocation independently of a malformed incoming string's length.
3. **Owned, read-once metadata; faults stay unknown.** Collect invokes each
   of its six optional getters once. The Program call supplies only the retained
   owned Process and its already-owned record directory. The Refresh/HasExited
   query is inside the optional catch; a Refresh fault produces `unknown`, not
   a fabricated alive/exited result. Each CPU/working-set getter is read at most
   once; exceptions and negative counters yield unknown. CPU buckets exactly
   implement zero, (0,100 ms), [100,1000 ms), and >=1000 ms. Resident buckets
   implement [0,64 MiB), [64,256 MiB), and >=256 MiB. No numeric counters,
   PID/HWND, user paths, token/SID, runtime IDs, memory contents, provider reads,
   raw streams or new selectors are added. Record checks enumerate bounded
   filenames only; presence is not validated Loaded/readiness.
4. **Publication cannot overwrite prior evidence.** TryPublish lines 71–80
   resolves and checks the owned evidence-root prefix and root/directory alias
   flags, validates/encodes first, then uses the fixed `startup-diagnostic.json`
   with CreateNew and FileShare.None. An existing file or publication fault
   returns false. No cleanup/deletion of real failed-run evidence is introduced.
5. **Safeguards and truthful context unchanged.** The diff leaves startup/
   observation 10 seconds, unit worker 30 seconds, native worker 240 seconds,
   Wait predicates, admission/catalog/collector, assertions, case order and
   serial first-failure stop unchanged. No retry/cooldown, privilege change,
   input injection, fixture rebuild, stream parsing, public API/schema or SDK
   packaging exposure is added. The three literal window-replacement wait
   Stage labels add future context without changing their predicates or
   diagnosing past failures. Existing setup actions are unchanged; the new
   diagnostic path calls no UIA/provider/action API.
6. **Unit fixture cleanup is narrow.** The new tests cover metric boundaries,
   exact fields/string types/depth/cap, both stages, malformed categories,
   stage rejection before observations, one-call optional faults, no overwrite,
   and same-exception bare rethrow. The cleanup target is an explicit resolved

## Accepted lower risks and remaining limits

- Filesystem prefix/attribute checks are not an atomic directory-handle fence.
  Ancestor/reparse changes or other same-user interference can race subsequent
  IO. This remains a controlled development evidence directory, not a hostile
  filesystem/ACL isolation guarantee. CreateNew prevents ordinary replacement,
  but a write/dispose failure can leave an incomplete newly-created diagnostic;
  that file is not an authoritative report or a success artifact. No recovery
  or overwrite is attempted.
- Optional observations occur sequentially after a failed wait and are not an
  atomic snapshot. Process/window/record categories may disagree or change; a
  window or record appearing late cannot convert the original failure to success.
  Metric buckets and record presence do not establish managed/WPF phases,
  scheduling, deadlock, IO, antivirus, load, or the startup failure's cause.

  internal allocation or existing ReadToEndAsync allocations. The unchanged
  outer worker deadline contains a blocking optional call; it does not prove

  Existing owned-process disposal/stream completion paths are unchanged, not
  newly fault-injection-certified by this static review.
