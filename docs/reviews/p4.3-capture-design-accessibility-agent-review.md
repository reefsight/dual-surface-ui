## Initial findings and verified design resolutions

### AI-P43-S2-01 — Medium: selected-value wire meaning and comparison were unspecified

Initial brief, Selection/ComboBox/Tab mapping and inverse-comparison clauses:
`state.value` was relationship-derived but its public representation and
inverse-translation scope were not fixed. The golden normalizer explicitly
joins private selected fixture IDs (`scripts/p4.2-fixture-contracts.mjs:117`).
Publishing those IDs would conflict with AC-04. Replacing them by Name loses
identity for the two equal `Duplicate label` list options; collapsed ComboBox
selected options are absent from its visible golden list. Broad string masking
could also hide a wrong textbox value or substitute an unproved relationship.

**Resolved in revised design, lines 117-136, 153-174, 234-236 and 245-263.**
The public selected value is the stable per-generation opaque item reference,
equal to its node ID when published. A nonvisible selected peer can have only a
separately proven, bounded private current relationship/reference; it shares
the 256 binding cap and grants neither visibility nor execution. References
retire on removal/replacement/container change and are not regenerated per
capture. The private inverse table is bijective; only the three reviewed
selection-container value slots may translate it. Arbitrary text/edit/range
values, names, unknown roles and unmatched strings cannot be rewritten. Missing
or duplicate inverse entries fail. The added negative obligations cover equal
labels, private collapsed peers, stale references, inverse collisions and
selector-looking ordinary values. This resolves the design ambiguity; it is
not implemented relationship or leak-test proof.

### AI-P43-S2-02 — Medium: publishable semantic subjects lacked explicit qualification

Initial role/type mapping alone did not state which provider wrappers/chrome
belong in the public semantic subject list. Mapping every visible Text wrapper
could publish a duplicate Combo subject or unreviewed chrome and then tempt an
oracle-driven filter to hide extra nodes. `Group/button` and `Text/status` also
must remain subject-specific reviewed mappings, not authority inferred from
provider text or type. The accepted manifest and normalizer qualify specific
reviewed subjects; ADR 0017 requires current type/pattern/container-qualified
ambiguity handling rather than first-ID matching.

**Resolved in revised design, lines 99-110 and 231-263.** Trusted subject
definitions are frozen from the reviewed manifest, qualified by private
correlation, reviewed type, required pattern families and current container.
Remaining or unknown-basic same-type/container ambiguity refuses capture.
Different-type Combo Text wrappers/unreviewed chrome remain private structure,
not extra public subjects. Every qualified subject has exactly one inverse
entry; the golden/oracle expected-node list is never a runtime publication
filter. Missing/extra/duplicate semantic subjects and wrong roles/names/
states/descriptors/schemas must fail verifier mutations. This preserves the
special expandable/status/sensitive mappings without trusting labels as
authorization. Actual source qualification still needs independent review.

### AI-P43-S2-03 — Medium: unknown enabled/offscreen content gating was ambiguous

The initial brief explicitly suppressed all content/pattern reads for unknown
password classification, but its unknown-enabled/offscreen paragraph mentioned
optional-field omission and no descriptors without clearly retaining S1's
structural-only/no-pattern rule. An implementer could read Name, value or
selection through a node lacking required basic classification.

**Resolved in revised design, lines 64-71, 80-98 and 122-130.** Any unknown
password/enabled/offscreen basic flag yields private structural membership
only: no Name/value/selection/content/pattern reads, public node or descriptors.
Known disabled/offscreen observations remain distinct and use the reviewed
read-only/exclusion policy. Exact NotSupported is not malformed/null and is
never a default false; malformed state refuses capture. Selected peers outside
the copied main tree independently require the same explicit basic flags
before content/pattern reads. Required getter-not-called adversarial tests are
now explicit. This resolves the design finding, not executable redaction proof.

## Other substantive compatibility checks

- **Read-only versus descriptive actions.** Lines 183-190 and 245-263 require
  actual model-facing `actions: []`/`snapshots` capability, and a distinct private
  comparable descriptive catalog. Neither schema validation nor descriptor
  parity establishes any of the seven action effects, policy, confirmation or
  executor safety. The manifest's `combo` has Selection/ExpandCollapse but no
  action descriptor; pattern support alone cannot add a golden action. Value
  and Range descriptors retain their exact observed writable/schema requirements.
- **Core/protocol boundary.** `src/types.ts:51-86` permits string state.value
  and opaque string node IDs without new fields. The unchanged core schema,
  `captureCanonicalSnapshot` (`src/delta/canonical.ts:451-502`) and native data
  admission (`src/native-protocol/data-validation.ts:62-79,119-153`) still check
  copied strict shape, unique node IDs, surfaceRef equality, action/schema and
  byte limits. The design's 256 nodes, 64 descriptors and 262,144-byte snapshot
  are stricter than existing public limits. Optional focus is omitted and not
  read; unexpected focus cannot be masked. A validated development envelope
  is not a negotiated or deployed native protocol host.
- **Host-owned revisions.** Lines 153-174 bind stable references to private
  instance/container/generation; semantic fingerprint includes actual copied
  semantics and private relations, excluding generatedAt, fixture/oracle
  counters, events, case IDs and measurement times. Time-only captures must
  remain stable; semantic/relationship/generation changes advance or invalidate.
  The accepted resettable fixture revision is not live revision authority.
- **Additional top-level subjects.** Lines 42-59 now specify a bounded native
  thread-local enumeration only on the admitted main's owning thread, current
  owned PID/desktop, at most one qualifying direct-owner-main subject, and an
  exact second candidate/identity fence. No desktop-wide UIA/EnumWindows or
  arbitrary process-thread enumeration is permitted. Multiple/missing subjects,
  incomplete enumeration, overflow, foreign ownership or different-thread popup
  fail rather than select the first ID. `WindowsAdmission.cs:26-42` and its
  current OS token/session/input-desktop checks remain the predecessor boundary;
  this modal/popup delta still requires actual source review and native proof.
- **Combined resources and failure handling.** Lines 194-222 combine main and
  auxiliary nodes into 256, auxiliary nodes into at most 64, roots into two,
  native enumeration into two capped 64-candidate passes, and all operations
  into one 10-second observation/text/binding budget. No fresh per-relation
  clock or separate unbounded binding map is allowed. Managed growth and capped
  output are checked before publication; provider/COM getter allocation and
  per-call latency are explicitly not guaranteed. Existing 30/240-second owned
  workers and CreateNew/failure retention remain unchanged.
- **Adversarial evidence.** Unknown/malformed properties, all enum/range
  states, callback-not-called redaction, copied immutability, container swap,
  inverse collision, additional/missing wrappers, invalid comparator mutations,
  cycle/budget/output caps and timestamp-only revisions are required unit/
  fault-injection obligations. They do not prove actual OS transitions. Actual
  first/repeat all-22 plus expanded-popup artifacts, unchanged validators,
  redaction bytes, final-source full gates and actual separate reviews are still
  required before S2 runtime acceptance.

Primary APIs were checked directly: unsupported properties return NotSupported
with true default suppression and current values can later change
([Microsoft current-property API](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.automationelement.getcurrentpropertyvalue?view=windowsdesktop-10.0)).
GetSelection's empty default is not presence proof
([Microsoft GetSelection](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.selectionpattern.selectionpatterninformation.getselection?view=windowsdesktop-10.0));
explicit [SelectionProperty](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.selectionpattern.selectionproperty?view=windowsdesktop-10.0)
and [SelectionContainerProperty](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.selectionitempattern.selectioncontainerproperty?view=windowsdesktop-10.0)
identify provider relationships, not security membership. The return from
[EnumThreadWindows](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-enumthreadwindows)
does not itself distinguish callback stop from no windows;
[GetWindow](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getwindow)
enabled-popup lookup selects the first such window or returns the subject,
not uniqueness proof. The design's ownership, unknown-state, uniqueness and
fencing rules are conservative project policy, not guarantees from these APIs.
