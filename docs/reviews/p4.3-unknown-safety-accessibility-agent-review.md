## Initial disposition and findings

Initial design disposition: **changes_required** for accessibility and
interoperability, limited to the clarification below. No Critical or High
finding. One Medium design clarification remains open at this cutoff.

### AI-P43-U01 — Medium: unknown qualification is not pattern absence

At proposal lines 108-115, unknown-safety nodes suppress pattern reads and
cannot receive receipts. That is appropriate, but it does not establish that
such a node lacks a requested pattern. The proposal does not explicitly fence
remaining semantic ambiguity when an unknown node and a known-safe candidate
share the trusted target definition's correlation, reviewed control type and
current container. Excluding the unknown node from qualified candidates could
then manufacture a uniquely qualified safe target from incomplete observation.

Required clarification: a current-container node with matching correlation and
reviewed type but unknown required safety observations must prevent a receipt
being minted for the matching definition, unless a separate trusted host
contract unambiguously excludes it. Do not query its patterns to rescue the
match. An unknown different-type wrapper may remain structural without creating
a same-type target ambiguity. Duplicate container correlation must continue to
refuse rather than taking the first container.

Required executable definitions before source acceptance: known-safe
Button/Invoke plus a same-ID/type/container sibling with unknown password,
enabled or offscreen state denies discovery; a different-type unknown wrapper
coexists without pattern reads; unsupported-only target cannot get a receipt;
malformed/null flags still abort and invalidate. These are later unit/native
checks, not results from this design review.

### AI-P43-U02 — Low: retain each observation's identity in fingerprints

Proposal lines 116-123 should make per-property transitions explicit. Preserve
the distinction of known true, known false and unknown for each password,
enabled, offscreen and applicable Value/RangeValue read-only observation. Do not
collapse which property's support changed into one aggregate nullable flag or
serialize unknown as omitted/default false. Where both write patterns exist,
Value-unknown/Range-known and Value-known/Range-unknown must not silently become
the same observation. Both write families may conservatively remain denied;
unrelated patterns still require the independent known-safe target flags.

## Preserved trust boundary

Subject to AI-P43-U01, the proposed separation is compatible with the existing
criteria: bounded structural membership is not action eligibility or safety
authority. Only the exact UIA unsupported sentinel becomes explicit internal
unknown; raw null/wrong types/errors remain capture failures. Unknown basic
safety or known password nodes have no pattern reads/actions/receipts. Every
target requires its own known nonsensitive/enabled/onscreen observations plus
unchanged OS/window/root/graph admission. An unknown ancestor cannot certify a
child, nor become an actionable container by virtue of its position/type/ID.

Keeping structural nodes also preserves complete budget/cycle/parent checks
instead of silently truncating the current membership tree. Fingerprint changes
must continue to invalidate old bindings and recovery must never revive them.
This retains ADR 0017 decisions 3-4, 6, 8-10 and P4.3 AC-03/04/06-09/12/13/15;
AC-02/05 and the remaining runtime criteria are not satisfied by this design.

Primary Microsoft basis was independently read in the preceding API research:
[current property values](https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.automationelement.getcurrentpropertyvalue?view=windowsdesktop-10.0)
preserve explicit false with default suppression;
[managed implementation](https://source.dot.net/UIAutomationClient/System/Windows/Automation/AutomationElement.cs.html)
also shows supported-property enumeration is not current support proof and
probes patterns. An unsupported value must not become default authority.
These API facts do not confer provider trust or prove the proposed policy.
