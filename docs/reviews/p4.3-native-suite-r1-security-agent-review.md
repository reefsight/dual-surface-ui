## Finding and actual resolution

R1-SEC-SRC-01 was Medium: the initial fixture restart lacked the design's
immediate executable-closure and fixed dev-configuration absence recheck.
`Program.Main` admits the freeze once before constructing the native suite.
`FixedCaptureSuite.Launch`, used for both bootstrap and `process-restart`, then
starts the fixture directly. The PowerShell launcher re-admits before every
suite worker and lane, but cannot recheck the in-worker fixture restart.

The design includes the fixture in its every-worker rule. A changed fixture
DLL or required companion, or a newly present fixed
`.runtimeconfig.dev.json`, between the two explicitly owned fixture lifetimes
could therefore reach the second `Process.Start` without current closure/absence
admission. This was a deterministic admission-order gap, not proof of hostile
host compromise, a diagnosis of the earlier desktop refusal or a reason to
relax an OS guard.

The intermediate correction was actually inspected at Suite20
`sha256:8b8bb218c8c4982756d395ba5d2f9484e0a61c2d6f9622fcfeb600f221c34d39`:
the new pure callback gate performs the existing full fixed admission and
requires equality of all three original pins before fixture launch. Both
bootstrap and restart pass through the sole wrapped `Process.Start`.
Inspection also found that the newly inserted full admission could exhaust
the shared budget before that callback: the enclosing `Within` checked only
before and after its complete operation. Approval remained withheld until an
immediate deadline recheck was added, preserving the finding's original budget
condition rather than accepting a budget reset or longer limit.

The final helper checks the same `SetupBudget` before admission and again after
successful admission/equality, immediately before calling the launch callback.
Any admission exception, changed source/binary/fixture pin or exhausted deadline
therefore prevents `Process.Start`. The checks remain inside the original
ten-second `Within` and `fixture-start` diagnostic stage. Existing first-failure,
startup, scenario and cleanup behavior is unchanged. This is a time recheck
before mutation, not a hard cap on synchronous filesystem or OS call latency.

Seven pure C# gate cases cover matching pins/two time checks, each of the three
pin mismatches, an admission exception and failure at either time check. Static
Node assertions bind the actual sole call site and original budget callback.
The final source and these tests were read in terminals `7e3e6e`, `6befea`,
`acfa94` and `1f0d03`; the independent final checks below validate their static
ordering. R1-SEC-SRC-01 is resolved by actual changed source, with no remaining
Critical, High or Medium security finding. Managed execution of the final tests
still requires its own producer result; source inspection is not that result.
