## Important measured provider behavior

1. A removed WPF button peer remained callable and changed the synthetic count.
   The capture records its before/after probe, proves removal from the current
   tree, and restores the scenario. A future adapter must reject stale
   tree/revision bindings before invoking; it cannot rely on a provider error.
2. Destroyed-window metadata remained readable. The capture independently
   verifies native destruction without persisting the handle, and requires a
   different current window identity.
3. ComboBox wrappers can share an AutomationId with a pattern-bearing item.
   Operations require the correct pattern, not merely an ID/name match.
4. Owned dialogs are searched within the launched fixture's subtree and by
   exact process/ID among direct desktop children. Other app subtrees are not
   traversed or persisted.
5. Clipping uses WPF's supported `FromClip` provider behavior. Default WPF
   visibility semantics are not misrepresented as viewport clipping evidence.
6. Reset Invoke is asynchronous. A monotonic acknowledgement, not revision
   zero, confirms completion. Read handles allow delete-sharing, and the writer
   atomically publishes bounded immutable versions instead of replacing an
   open destination. File sequence is private, never semantic identity.

## Reviewer checklist and bounded decision

- Accessibility: inspect every raw-to-normalized mapping, pattern qualification,
  clipped/collapsed nodes, duplicate labels, and modal identity.
- Security: inspect sensitive reads, state/JSON budgets, salt lifetime, event
  metadata, process ownership, teardown/deadlines, cache/browser/npm exclusion,
  and the absence of a production control channel.
- Interoperability: verify core-schema validity and unchanged protocol 0.1;
  reject any fixture-specific native handle, enum/serializer default, or
  implementation language leaking into the public contract.
- Package: rerun the exclusion check with built native artifacts and the
  proposed golden present; confirm no npm publication or new runtime export.
- Record reviewer identity/role, review date, source commit, manifest/semantics/
  golden digest, findings and disposition. Resolve all critical/high findings
  before maintainer acceptance. Do not invent reviewer sign-off from test logs.

## Canonical review record and commands

The [canonical record](p4.2-independent-review.json) is deliberately `pending`:
all four scope reviewers/dates and the maintainer identity/date are null. Empty
findings and a zero counter mean no review has been recorded, not that a review
found no issues. Its closed, versioned schema is
`fixtures/phase4-exit/contracts/p4.2-independent-review-0.1.schema.json`.

An actual independent reviewer must record the accessibility, security,
interoperability and package decisions, public reviewer ID, independence basis,
review date and findings. One qualified independent reviewer may cover multiple
roles. The maintainer records a separate acceptance decision after those reviews.
Never copy synthetic test identities or an implementer's self-review into an
independent approval. IDs and independence declarations are governance records,
not cryptographic signatures; the validator cannot establish that a reviewer
actually performed a review. Authenticity depends on actual independent reports,
trusted maintainer authorization and repository change control. The maintainer
explicitly authorized independent agent review in the
[dated delegation](phase4-agent-review-authorization-2026-10-03.md); reports must
identify agents as agents, not suggest personal human review. Acceptance recorded
on the maintainer's behalf must cite that delegation separately.
Text fields must contain no credentials or user
data; they are bounded but are not automatically redacted.

```text
npm run phase4:p4.2-review:contract-check
npm run phase4:p4.2-review:validate
```

The contract check verifies schema, frozen evidence bindings, both captures,
current source blobs and Git ancestry, then reports `review_contract_verified`
with `gateReady: false`. Exit 0 on this preflight is never approval. The approval
command currently reports `gate_not_ready` and exits 3 when invoked directly
through Node (npm may wrap that as exit 1).

Only the canonical file can produce `gate_ready`. An optional
`.phase4-preflight/drafts/<name>.json` is a review preflight, never acceptance.
Other paths/flags, reparse-point paths, malformed/non-UTF-8/over-32-KiB records,
unknown fields, missing roles and changed bindings fail closed. Reads and output
are bounded, and failures never echo review text or arbitrary file paths. This
is offline repository tooling, not a service hardened against concurrent hostile
filesystem mutation; run it in a trusted checkout.

Review dates cannot precede the frozen evidence commit or be in the future;
maintainer acceptance cannot precede any scope review. All four scopes must be
approved and declare independence. Open **or accepted** critical/high findings
block acceptance; resolved findings require a resolution, IDs must be unique,
and the declared counter must equal the actual unresolved severe count. A
changed fixture or golden needs a versioned, explained re-freeze and re-review,
not a manual digest edit to bypass this contract. The proposed golden remains
immutable; the separate approved review record would accept its exact digest.

Accepting P4.2 does not select Rust/.NET for the bridge, accept ADR 0017, approve
the Phase 4 Exit Gate, or authorize publication/deployment. Subsequent work must
follow the existing P4.3 entry decision and native-language measurement gate.

## Limitations

Evidence covers this recorded Windows host at DPI 96 / scale 1 and its recorded
locale/layout. It is not a multi-DPI, other-Windows-version, macOS, production
app, secure-desktop, adapter-performance, or native-daemon security claim.
Host focus and asynchronous event counts can vary and are retained in raw
reports but excluded from the semantic digest. Old-provider availability and
its synthetic probe may vary with provider/GC lifetime; raw outcomes and probe
state are still validated in each run, while current-tree semantics and binding
invalidation must remain identical. No screenshot-based visual
equivalence or native bridge implementation is claimed.
The event report covers property changes; it is not a general structure-event
subscription claim. Structural/restart changes are verified through fresh
trees, provider/native-window checks, and authoritative fixture state.
