## P43-S3-SEC-D01 - Medium: historical replay can regress current revision

Design references: semantic-action brief lines 196-211, especially the matching
keyed retry and unchanged protocol-transcript obligations. The brief binds a
ledger entry to the original revision and requires current identity/permission
and disclosure checks, but does not explicitly require a fresh authoritative
terminal-revision fence before returning a historical outcome.

The unchanged verifier cannot currently be assumed to supply that fence.
`src/native-protocol/session.ts:183` looks up a completed request. Lines
185-215 admit an exactly identical keyed replay and skip the ordinary stale
request-revision check for it. Lines 221-231 then store the surface's current
revision as the new replay's `pending.surfaceRevision`. Lines 244-245 require
the identical recorded response fingerprint. In the action-response branch,
lines 301-314 accept the response when current revision equals that new pending
revision and set the surface map to the old cached outcome revision.

Static adversarial sequence:

1. Catalog current surface at `revision-1`.
2. Action `action-1`, key `idem-1`, succeeds from `revision-1` to `revision-2`.
3. A valid contiguous surface-change event advances the same surface to
   `revision-3` **before** replay begins.
4. Replay the identical original `action-1` request, still bound to
   `revision-1`, and the identical recorded response ending at `revision-2`.
5. The replay's pending revision is `revision-3`, so the race check passes and
   the map is overwritten with `revision-2`. A new request ID at `revision-2`
   then passes the stale gate; one at actual `revision-3` is treated as stale.

This is a deterministic source trace, not an executed reproducer or evidence
that a native operation occurred. It demonstrates why the design's phrase
"recorded admissible outcome" needs an explicit host condition rather than
relying on the current replay path or the ordinary third-revision race rule.
Generation identity alone is insufficient: semantic state can advance without
changing the surface/window lifetime generation.

Required design refinement:

- Before historical disclosure, freshly prove current trusted identity,
  permission/policy, disclosure eligibility, exact generation/binding, and that
  the current authoritative host revision equals the stored terminal outcome
  revision. Copy all facts needed for this decision; do not use cached peers.
- If that admissibility fails, do not invoke again, manufacture a revision,
  retag a result onto a replacement surface or change the cached response to
  satisfy correlation. Specify the fail-closed session invalidation/resync
  boundary explicitly; an exact completed-response fingerprint cannot simply
  be replaced by a newly invented failed response under the same request ID.
- Distinguish exact same-request-ID transcript replay from a new request ID
  carrying an old key. No old-request-revision bypass is allowed for the latter;
  updated revision/content must conflict with the original ledger binding,
  not cause another mutation.
- Add copied/pure design vectors for revision advance before replay, a third
  revision during disclosure, policy/permission revocation, generation change,
  exact response replay, new-request-ID stale-key and capacity/uncertainty cases.
  Assert zero additional mutating calls and no session-state rollback.

Root acknowledged this finding and plans a design revision. No revised bytes
are accepted by this initial report.

## P43-S3-SEC-D02 - Medium: hard worker loss has no defined uncertainty owner

Design references: semantic-action brief lines 152-160, 176-190, 196-211 and
238-240. The brief correctly marks mutation-may-have-started before the provider
call, retains completed/uncertain ledger outcomes, and forbids a timed-out retry.
It also recognizes that the cooperative deadline cannot interrupt a blocked
native call and that the exact owned supervisor may need to terminate the worker.
It does not define how the uncertainty/tombstone survives when that worker cannot
return or publish its volatile private ledger.

Adversarial design sequence:

1. An admitted consequential request reserves a worker-private key entry and
   may enter its sole pattern call.
2. The call blocks or has a possible effect and no admitted terminal response.
3. The hard supervisor deadline terminates the exact owned worker. Its private
   attempt latch/ledger cannot be assumed available after termination.
4. If recovery merely creates another worker/session or discards a missing
   ledger entry, a reconnect/key retry can incorrectly be treated as an action
   that never started. Saying "possible effects remain preserved" does not
   identify the bounded surviving authority that prevents this path.

This is an unresolved design/lifecycle proof obligation, not an observed worker
crash, provider timeout, data loss or duplicate native effect.

Required design refinement:

- Define bounded supervisor-owned in-flight uncertainty **before dispatch**,
  or conservatively mark the sole pending admitted attempt as possible-effect
  whenever a worker ends without an admitted terminal response. Do not rely on
  after-call publication by the blocked worker.
- On such loss, close/invalidate the original protocol session/generation and
  all its action bindings. A replay key, reconnect, new worker or missing file
  must not revive the old operation or imply that it made zero calls.
- Retain the bounded tombstone/negative evidence outside the failed worker for
  this controlled attempt, without raw input/peer/native-ID/error channels.
  Refuse capacity before dispatch; do not evict live uncertainty to permit a
  duplicate. Define expiry as authority retirement, not retry permission.
- A conservative terminal session closure is sufficient for this S3 minimum;
  this need not invent persistence, authenticated IPC, full S4 reconnect or
  another helper process. Explicitly limit any later fresh session/manual action
  claim; it cannot become an automatic continuation of the uncertain old one.
- Add hard-kill/no-output/malformed-terminal/late-return and recovery vectors
  proving no second call under the old request/key and no false cancelled or
  no-effect outcome. Keep hard/cooperative deadlines unchanged.

Root was notified before report creation. This initial candidate does not
resolve the obligation by asserting private-state retention alone.

## Sound boundaries to preserve through refinement

The initial proposal correctly retains several substantive security boundaries:

- Preparation does not bypass failed S2 runtime. S3 source implementation waits
  for real S2 first/repeat/artifact acceptance and a separately bound S3 entry.
- Executable profiles are minted from trusted current bindings and a closed
  package-owned profile/effect table, not descriptive golden metadata or model
  input. S2 public snapshots remain action-free and no fixture/golden/public
  schema alteration is implicit.
- Every target needs explicit known nonsensitive/enabled/onscreen flags,
  action-specific writable observations, current admitted window and fresh
  qualified graph/container membership. Unknowns and retained callable peers
  do not authorize a call. Same-ID/type/container ambiguity cannot be resolved
  by first match or an assumed safe sibling.
- Policy defaults deny, risk is host-owned, marked confirmation cannot be
  bypassed by allow, and a fixture modal/caller flag cannot mint a receipt.
  Async waits must discard peers and redo complete binding, safety, revision,
  policy/receipt/effect authority before the sole final fenced call.
- Inputs are bounded semantic values, not operation delegates/selectors.
  Selection is observational; SelectionItem is target-based. Toggle is exactly
  one transition, numeric clamping/implicit ComboBox expansion is forbidden,
  and no injection fallback exists.
- Provider return, event, submitted value or apparent task completion cannot
  establish success. Fresh UIA plus separate authoritative fixture state must
  prove the exact effect and unrelated-field exclusions. Possible mutation is
  not a no-effect failure; replacement cannot revive old authority.
- The resource profile preserves S2 graph/text/binding bounds, one serialized
  mutation, no implicit queue, bounded ledger/receipt capacity and one shared
  cooperative deadline across all waits/calls/proofs. Blocking-provider and
  hostile-provider/ABA limitations are stated, not claimed solved by type safety.

These are reviewed design statements, not source implementation or measured
native evidence. The later exact descriptor/effect/input/case matrix, callback
grammar, source manifest, binaries and original-byte artifact verifier still
require independent source review and their own entry/freeze. Existing core
helpers must not be copied as implicit native authority: the native design's
strict callback decisions, fresh peer isolation and no fabricated last-known
revision after uncertainty remain stronger explicit obligations.

### D01 resolved in the final design

The final replay section requires freshly proved identity, current
permission/policy and disclosure eligibility, exact generation/binding, and
current authoritative host revision equal to the stored terminal outcome
revision. It repeats that fence after any wait and before disclosure, forbids
historical rollback, and expressly says generation equality is insufficient.

The closed decision table distinguishes identical completed-request replay,
changed request/response fingerprints, a new request ID with an old revision,
a new ID with changed current bound content, inadmissible historical disclosure
and capacity refusal. The latter paths make no new mutating call. An inadmissible
completed result closes/invalidate the old session and bindings rather than
rewriting its cached response or manufacturing an outcome. It also distinguishes
a verifier exception, which closes its session, from an admitted matching wire
`request-error` for a pending request. A negotiated invalidation event may be
used only where allowed; no capability or event is invented to escape that rule.

The required vectors now explicitly include revision advance before replay,
policy/permission revocation, new-ID stale-key versus changed-content conflict,
the third-revision race and zero-new-call assertions. Those statements resolve
the design gap. They do not prove a future host implements the ledger or fresh
authority checks, or that the public verifier alone enforces disclosure policy.

The design identifies the pre-existing public verifier defect as a separately
reviewed pure correction and fresh-gate prerequisite before S3 entry, not a
native executor implementation. My separate source review is
`docs/reviews/native-protocol-replay-revision-security-review-2026-10-04.md`,

### D02 resolved, including intermediate ordering clarification

The revision assigns the bounded attempt slot to the exact owned supervisor
before dispatch, not the worker's volatile ledger. Until an entire terminal
response is admitted, loss/termination/no output/malformed output is
conservatively possible-effect. It closes the original session/generation and
retires all bindings. A bounded redacted tombstone survives outside the worker;
capacity refusal occurs before dispatch, live uncertainty is not evicted,
expiry retires authority, and a missing file/ledger or replacement worker cannot
resume the old key. Late returns cannot publish into the closed session.
Supervisor loss permits no automated resume; later manual fresh authority is
not claimed a safe retry. Full durable/authenticated/cross-process recovery
remains outside S3.

Root independently raised an ordering concern in the first full revision:
ordered steps two/three already needed native proof and policy waits, while
step four still said to reserve the supervisor slot before worker dispatch.
I assessed the actual wording, agreed that the enforcing boundary was ambiguous,
and withheld final design disposition pending a precise revision. An
implementation could otherwise accidentally reserve only after proof in an
already-launched mutation-capable worker or imply worker-private ownership.
This was a clarification of the original D02 obligation, not an observed source
or native worker defect; its provenance is root self-check plus independent
review, not an invented initial security discovery.

The final ordered boundary now reserves after pure request admission in step
one, **before any mutation-capable worker launch/dispatch**. Steps two/three run
under that same supervisor reservation, without moving native proof into the
supervisor. Step four verifies the still-current original slot/binding and
consumes confirmation once; it cannot create a replacement reservation. This
is consistent with the later conservative supervisor-loss rule and one-slot,
one-mutation resource profile. No after-call worker publication is assumed.

Required hard-kill/no-output/malformed-terminal/late-return/recovery and
before/after-call cancellation vectors make this obligation testable later.
An attempt conservatively marked possible-effect need not actually have made
a call; that uncertainty is deliberate, not a false zero-call assertion or a
reason to retry it. The closed supervisor design resolves D02 for this scope.
