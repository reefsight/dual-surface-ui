## Findings and disposition

No new Critical, High or Medium source security defect remains in this final
candidate. The following are actual reviewed safeguards, not statements that
their Windows behavior has been exercised by this reviewer.

### Admission authority and condition preservation

`NativeCaptureHarness/OwnedWindowsAdmission.cs:16` defines a private optional
enum-only trace. Its closed table contains exactly 12 checks, 17 guards and 40
allowed pairs. Invalid enum values or pairs are refused before label-array
indexing. No process, SID, token value, HWND, thread ID, desktop name, native
error, provider value, exception or operation delegate is given to the observer.
The callback has no return authority. Every trace refusal still throws the
original `CaptureException(Unavailable)` even if the callback throws.

I compared the full admission diff with committed pre-D2 source. Guard operands,
evaluation order, short circuits, native queries, access flags, buffer sizes,
pointer bounds and cleanup calls are unchanged. The added check markers do not
introduce a native query. In particular:

- Subject/worker/current-subject token reads still reject elevation/UIAccess,
  require the exact four-byte scalar representation, and use bounded SID buffers
  and pointer/body checks. SID and identity values remain private.
- Process birth/liveness, identity/session, WTS active-session, station,
  ordinary worker/input/main desktop and anchored main-owner checks are retained.
- The original `desktop == 0 || ObjectName(desktop) != "Default"` short circuit
  at `OwnedWindowsAdmission.cs:176` is unchanged. Its combined refusal is now
  correctly labelled `desktop-name-or-null`, not a false assertion that a name
  was observed. Station `name-value` applies only after the existing name query
  returned; query refusal is separately labelled.
- The constructor clears its observer in `finally` at line 97 on success,
  guard refusal, deadline and SDK/managed fault. Later `Observe`, context and
  native-peer checks therefore cannot add constructor detail, even though their
  unchanged refusals use the same internal helper. Both constructor callsites
  in `CaptureSuite/Program.cs:170` and `:256` are existing owned-process admission
  sites; no new constructor, process authority or window traversal is added.

The trace is naturally used for one refusal on one constructor unwind. This is
not a claim that arbitrary adversarial/reentrant callbacks are supported; the
only production callback is the trusted fixed serial diagnostics latch.

### Immutable primary and coarse fault fallback

`CaptureSuite/FailureDiagnostics.cs:77` validates both the pair and the existing
callsite context before assigning one immutable first-primary record. It has no
IO, clock, deadline, log, SDK, provider or native call. Invalid context/pair throws
before assignment; the trace suppresses that callback fault and still throws
`Unavailable`, which the enclosing `At` synchronously latches as coarse failure.
No half-populated pair or permissive fallback is published.

The only eligible contexts are `bootstrap/startup`,
`process-restart/startup`, and `window-replacement/setup`, all at
`setup-admission`. The latter two already existed. First-primary checks in both
the ordinary latch and observer prevent an outer exception or secondary cleanup
fault from replacing the inner tuple. Main catches/latches before owned cleanup
(`CaptureSuite/Program.cs:43`); cleanup still independently attempts each
required closure once per owned lifetime. Expected provider-negative probes are
not marked as diagnostic failure, and SDK/managed exceptions or deadlines not
raised through an explicit constructor guard retain null detail.

### Private D2 grammar and redaction

Managed `FailureDiagnostics.ParseCore` and the separately implemented JS
`parseNativeSuiteD2Failure` admit a distinct D2 kind with exactly 14 flat scalar
keys. Both detail fields must be explicit null together or an allowed pair with
`guard-refused`/`Unavailable` and the exact eligible context. Wrong pairs,
contexts, kinds, missing/extra fields, duplicate decoded keys, malformed UTF-8 or
UTF-16, BOM, nested data and stale pins are rejected. The exact 12-key D1 parser
and reader remain separate; D1 encoding cannot silently discard D2 detail.

The original limits remain 4,096 original bytes, depth 2, 32 tokens and 128
UTF-16 characters per string. A normal 14-field D2 record uses 30 tokens.
Production UTC is obtained only when the admitted worker attempts publication;
parser calendar/format acceptance does not prove clock origin or failure time.
No provider/error stringification, secret field or raw identifier output channel
is added. Refusals and publication-withheld notices stay fixed literals.

`scripts/p4.3-native-failure-diagnostics.mjs:261` admits the actual new fixed
freeze first, then explicitly calls only the D2 reader. It does not guess a kind
from an untrusted file or fall back to D1. The lower-level D1 reader remains an
explicit historical/private API, not execution authority.

## Limits and required next gate

This review performed source reads, diffs, manifest reconstruction and workspace
binary/report hashes only. I did not run managed/JS/heavy tests, SDK commands,
native fixtures, UIA or OS probes, enumerate user processes/windows, read Temp
artifacts, inspect environment/secrets/keys, install software, alter Git, commit
or push. Hash agreement and root-produced pure tests are not real desktop/session
admission proof, native failure-diagnostic production proof or native semantics.

Accepted lower risks/limitations remain:

- A closed guard identifies its source group, not the failed operand, observed
  desktop/token value or exact OS cause. No extra diagnostic read is justified.
- SDK/managed faults, deadlines, later checks, callback failure, early capability
  failure or an external kill may yield only coarse metadata or no record.
  Absence/null detail is not success or evidence that a guard passed.
- First-primary latching relies on the fixed trusted serial caller. Arbitrary
  concurrent/reentrant observer clients and a hostile callback are outside scope;
  the callback is not caller/model authority.
- Filesystem checks and native liveness/context fences are sequential, not atomic
  hostile-admin protection or an ABA-safe executor. Immutable source pins do not
  sign authorship or reproduce compiler output.
- Cleanup metadata records an actual later closed refusal only; a null value or
  absence of a record does not prove cleanup success. The source approval does
  not establish real OS denial behavior, provider allocation limits, S3 atomic
  mutation, action execution correctness, broader host compatibility or full P4.3.

checkpoint, terminal fresh required project/browser/conformance/package/contract/
