### P43-ID-SEC-001 — High: provider-supplied ancestry could grant membership

The original catalog only checked that parent IDs existed and trusted a supplied
ancestor list. A target and another node could parent each other, while the
target's fabricated ancestors named the desired container. Qualification could
then accept a disconnected/cyclic target despite no rooted membership. This
would be a High guard flaw if used as pre-mutation authority.

Resolved in source: `IdentityCatalog.cs:110` privately copies bounded nodes;
`:137` requires unique instances and exactly one root; `:141` requires a Window
root; `:142` walks every parent chain with cycle/depth/missing-parent checks;
`:156` checks fan-out. `:161` resolves one current container instance and derives
membership from that checked graph, qualifying type/pattern before ambiguity.
No caller-supplied ancestors remain. Self-parent, disconnected-cycle,
multiple-root, missing-parent, duplicate-instance, duplicate-container and
duplicate-qualified-target unit cases cover the source obligations. Native
mutation safety is still not accepted because this is a decision-only catalog.

### P43-ID-SEC-002 — Medium: malformed observations could survive recovery

Null receipts/revisions could escape as ordinary exceptions, and null
observations/nodes/pattern collections or collection failures did not reliably
invalidate existing bindings. After restoring a healthy observer, a previously
issued receipt could remain live following a failed observation.

Resolved in source: `IdentityCatalog.cs:61` bounds/validates receipt shape;
`:110` handles malformed observations with fixed guard categories;
`:106` invalidates on both guard failures and other observer/copy failures.
Old receipts remain invalid after recovery. Malformed receipt requests are
denied locally; they do not need to revoke an unrelated valid receipt. Unit
cases include null fields, wrong root, negative epoch, indexed-list fault,
provider disconnect and over-deadline recovery. Exception text is not returned.

### P43-ID-SEC-003 — Medium: IReadOnlyList was not a private snapshot

The original validation/hash/qualification passes reused externally backed
lists. Mutating a pattern array between passes could make the receipt describe
a different observation from the one validated.

Resolved in source: `IdentityCatalog.cs:114` bounds count before allocating,
`:119` reads each node into the private copy, `:123` bounds and copies each
pattern list, and `:135` stores a private read-only pattern array. Strings and
records used thereafter are immutable; qualification and hashing use only that
copy. A concurrent mutation during collection is not evidence of one atomic
provider-time snapshot, but it cannot subsequently alter the checked graph.
The copied-pattern-array and indexed-list-fault recovery cases are present.

### P43-ID-SEC-004 — Medium: unknown receipts could force native observation

Well-shaped but locally unknown opaque references originally caused a fresh
native observation before local refusal. Untrusted receipt floods could induce
unnecessary COM work.

Resolved in source: `IdentityCatalog.cs:65` checks the current surface/revision
and locally known binding before `Fresh()`, then `:68` rechecks after fresh
observation/invalidation. The unknown-receipt-no-observation unit case counts
observer calls. Legitimate known receipts still require fresh checked evidence.

### P43-ID-SEC-005 — Medium: destroyed-window case did not prove destruction

The earlier native harness waited for a different main window, but that alone
did not prove the old native window ceased to exist. Its case label could have
overstated the independently observed stale-metadata condition.

Resolved in source, executable proof pending: `Program.cs:127` retains only the
owned former handle, `:130` waits for a different current main window, and `:131`
waits for `WindowsAdmission.OwnedFormerWindowDestroyed` (`WindowsAdmission.cs:45`)
to observe `!IsWindow(oldWindow)` before the old metadata probe. Failure remains
bounded and terminal. `Program.cs:149` now asserts the exact expected GuardCode,
not just Allowed=false. Replacement, reset and window cases also perform healthy
rediscovery. No destroyed-window native success is claimed on the blocked host.

## Authority, native buffers and disclosure assessment

`WindowsAdmission.cs:17` accepts only the harness-created Process and stores its
birth time and private admitted token identity. Each current-window observation
checks process lifetime/birth, matching worker/subject user, integrity and
session, non-elevation/non-UIAccess, active local session, interactive station,
worker/input/subject thread desktop, native liveness and window-owning PID.
The UIA collector starts from that admitted window, rejects foreign-process
nodes and checks current parent relationships. A COM peer/runtime ID is never
the sole admission authority. Desktop/session checks are observations with
races, not OS enforcement against a hostile same-user administrator.

Token scalar allocations are exactly four bytes with exact returned-length
checks. Variable SID fields first require the bounded size-query failure and
`needed <= 4096`, then allocate exactly that size. Returned length, SID pointer
offset, header, revision, subauthority count and total copied length are checked
before SID-byte reads/copy (`WindowsAdmission.cs:118`–`:150`). Private SID strings
are compared but never serialized. Safe token handles and allocated buffers are
released; owned input-desktop/WTS handles are released, borrowed thread desktop
handles are not closed. The reviewed size-query/length handling is consistent
with Microsoft's [GetTokenInformation contract](https://learn.microsoft.com/en-us/windows/win32/api/securitybaseapi/nf-securitybaseapi-gettokeninformation).

The worker requires desktop name Default plus an explicit UOI_IO result;
Microsoft documents that flag as indicating the desktop receiving user input.
A familiar desktop name alone therefore does not establish ordinary input
authority. [GetUserObjectInformationW](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getuserobjectinformationw).

`NativeObservation.cs:45`–`:60` reads explicit password/enabled/offscreen flags
and reviewed pattern availability/read-only flags, not Name, help text,
Value.Value or password content. The provider-selected text/runtime arrays
stay internal and are checked before host normalization; the report carries
only literal case IDs, closed categories and bounded metadata. Random private
salt hashes native correlation IDs; receipts contain fresh random references,
not selectors, OS handles or executable peers. `Program.cs:46` emits a fixed
local stage/category, not exception text, stacks or raw authority. There is no
network listener, generic injection, shell interpolation, privilege change or
client-supplied native selector path. Fixture setup calls are trusted literal
scenario preparation, not a public executor.
