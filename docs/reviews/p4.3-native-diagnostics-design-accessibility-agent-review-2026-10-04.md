Additional callsite/ordering requirements were also resolved explicitly:

- Setup now permits `collector-start`, covering the existing window-replacement
  construction rather than mislabeling it startup or rejecting its diagnostic
  tuple. Startup remains bootstrap/process-restart only; output is bootstrap
  only; null site deliberately preserves coarse uninstrumented locations.
- Existing post-read deadline checks precede sentinel/type classification. A
  returned NotSupported followed by ResourceExceeded remains
  guard-refused/ResourceExceeded, not a fabricated unsupported-property cause.
  The design mandates a pure ordering vector with no sleep or second read.
- Cleanup-once is per owned process lifetime/resource, not once for the whole
 22-case workload. `stopAttempted` is latched before stop; each already-required
  collector/process/stream/handle action is independently caught and attempted
  once so an earlier fault does not skip remaining closure. Report/stdout faults
  after stop cannot trigger another Kill/Dispose. New owned restart lifetime
  gets a new flag; no lookup, peer reopen, retry or deadline expansion is added.
- Timestamp provenance is correctly limited: production obtains UTC directly,
  while the parser validates only shape/calendar and cannot distinguish an
  identical source-generated literal. Deterministic timestamps are test-only.

The underlying cleanup hazard is supported by the primary [C# language
specification](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/language-specification/statements):
using disposal occurs in a finally boundary, and an uncaught exception from
finally can replace an exception already propagating. The [using
reference](https://learn.microsoft.com/en-us/dotnet/csharp/language-reference/statements/using)
likewise documents disposal on exceptional exit. These facts justify explicit
primary latching; they do not establish that C0's actual refusal was masked.

## Required diagnostic sequencing

The final design preserves the reviewed accessibility trust boundary:

1. Admit the actual new source/binary/report freeze before fixture launch. Create
   a context before suite construction, but grant its sole output capability
   only after canonical fixed path, ancestor/directory and empty-output proof.
   Before that capability, retain only fixed safe stderr; never reconstruct or
   re-admit a raw CLI path in a catch.
2. Scope each already-required operation with static host stage/site values.
   Clear/restore context on normal return; latch the first synchronously
   observed unhandled refusal before any cleanup. A collector call remains
   `capture-call`, not an invented property inside unchanged componentaf7.
3. Classify only the original getter result or thrown error, after unchanged
   guard ordering. Exact NotSupported is different from malformed/null/wrong
   type; known typed unsafe state remains a guard refusal, never a safe default.
   Do not read provider Name/content/patterns to explain unknown safety, call
   getters twice, derive labels from ProgrammaticName, inspect exception text or
   serialize values/native identity.
4. After terminal refusal, perform only already-required owned cleanup. No
   provider read, semantic mutation, removed-peer call, oracle recheck or new
   admission probe is authorized for diagnosis. Preserve the primary tuple and
   first actual cleanup code without any cleanup-success claim.
5. Attempt one bounded CreateNew failure publication through the admitted
   capability after cleanup. Publication refusal retains the original tuple and
   partial files, emits only a fixed withheld-output refusal and stays failed.
   No fallback path, retry, deletion or successful report replacement is allowed.
6. Read-only failure inspection admits only the fixed opened regular single-link
   failure file under actual D1 pins. It neither enumerates nor decodes partial
   provider/capture/fixture files, and cannot launch or mutate an application.

The12 exact required keys, fixed stage/site/case relationships, classification/
code relationships and explicit null fields are sufficiently closed for this
design. The4096-byte/depth2/token32/string128 bounds admit the flat record without
an unbounded payload. Expected properties and the two supported SDK exception
classes are static host classifications, not selectors or authority. Unknown
SDK errors remain unexpected; InvalidOperation/Argument exceptions are not
silently attributed to provider behavior. The future source review must verify
these constraints in actual catch/getter/cleanup callsites, not just in a parser.
